08 — Roadmap

OneLedger grows through six capability groups: foundations, the daily-use financial core, verified history, planning and resilience, analysis, and optional private intelligence. Every approved product outcome has one permanent Phase N.M identifier.

This roadmap owns what the product must deliver and how success is judged. The master implementation plan owns build order and dependencies. Current state and the next action live only in implementation progress. Discoveries and deferred work live in the project register until approved.

Sequencing principle: usefulness early. Each outcome must leave the product more useful on its own. No calendar estimates are implied; acceptance is based on observable financial behavior and evidence.

Outcome map

GroupProduct result
Phase 0.xA private, exact-money ledger foundation with accounts, manual entry, owner authentication, FX history, and safe document storage.
Phase 1.xA complete daily-use financial core: statements, classification, transfers, cards, positions, investments, income, forecast, and documents.
Phase 2.xFull historical coverage, explainable wealth history, classification learning, and visible data quality.
Phase 3.xCommitments, cash planning, goals, emergency resilience, and protection administration.
Phase 4.xBudget, recurring, salary, investment, and remittance analysis, with optional source automation.
Phase 5.xOptional intelligence introduced only after an explicit privacy and safety decision.

Phase 0.x — foundations and manual ledger

PhaseOutcomeSuccess criteria
Phase 0.1Local runtime and repository safeguards The web, API, and database run locally; secrets and real statements are excluded; migrations apply from an empty database.
Phase 0.2Household data and authorization boundary Household-scoped data is isolated; every financial route requires the owner; unauthenticated queries reveal no household rows.
Phase 0.3FX and reporting foundation The configured reporting pair has dated history back to the approved anchor; carried rates and sources are visible; money remains exact across database, API, and UI.
Phase 0.4Accounts and manual ledger Every supported account class follows the signed-balance convention; opening balances and manual transactions reconcile; historical values remain frozen.
Phase 0.5Import and document foundation Originals are stored privately under content identity; extraction layouts are data; stored documents remain traceable without exposing source identifiers.

Phase 1.x — daily-use financial core

PhaseOutcomeSuccess criteria
Phase 1.1Statements land in the ledger A supported statement parses, normalizes, deduplicates, reconciles, enters review, and commits atomically. A mismatch blocks import and an induced failure leaves no partial rows.
Phase 1.2All supported statement layouts Every gathered statement format, including encrypted and irregular layouts, imports and reconciles; unsupported scanned input fails clearly; passwords never persist.
Phase 1.3Classification and transfers Deterministic rules explain their result; owner-confirmed transfers and card payments appear in neither income nor spending; one hand-checked month agrees exactly.
Phase 1.4Cards, net worth, and trends Card dues agree with statement evidence; signed balances produce net worth in both reporting currencies; monthly flows and trends preserve transfer exclusions.
Phase 1.5Statement-guided onboarding and owner decisions An unknown account is proposed once from masked statement evidence, subsequent statements resolve to it, and unresolved classifications are reachable and safely reusable.
Phase 1.6Investments Holdings reconcile to transaction units; purchases link to funding; allocation totals correctly; a known cash-flow series matches independent XIRR evidence within 0.01%.
Phase 1.7Salary and a thin forecast Payslip income reconciles to the ledger; confirmed commitments move an assumption-labelled 30/60/90-day projection; a forecast never posts a transaction.
Phase 1.8Layout mapper and documents A synthetic unseen statement can be mapped and imported without code changes; documents are searchable; every imported row links back to its document, page, and row.

Group exit: all supported accounts and statements are represented, the owner can complete the monthly import and review flow, positions and flows reconcile to evidence, and the application supports daily use without hidden coverage gaps.

Phase 2.x — verified history and data quality

PhaseOutcomeSuccess criteria
Phase 2.1Complete historical coverage All available statements back to the approved history anchor import and reconcile; missing periods and unsupported evidence remain explicit.
Phase 2.2Wealth history and attribution Month-end positions store their evidence dates and rates; the attribution waterfall separates flows, market movement, FX translation, other external changes, and visible residuals.
Phase 2.3Classification learning and review depth Corrections propose narrow rules with accurate affected counts; confidence and coverage are visible; past data never changes silently.
Phase 2.4Data quality and recovery A diagnostics view identifies coverage and reconciliation gaps; current backups restore into an isolated database and reproduce recorded structural evidence.

Phase 3.x — planning and resilience

PhaseOutcomeSuccess criteria
Phase 3.1Commitments and actions Dated and recurring obligations have a source-linked lifecycle; actual settlement clears the obligation once; recurring obligations retain only their next occurrence.
Phase 3.2Cash forecast and monthly review Account-and-currency projections show the lowest balance and date, incomplete coverage, and assumptions; card settlement is counted once and shortages appear in the paying account.
Phase 3.3Goals and emergency reserve Eligible resources cannot be reserved twice; goal progress separates contributions from market/FX movement; reserve coverage uses an explicit essential-spend baseline.
Phase 3.4Protection and administration Policies, maturities, claims, reimbursements, renewals, and owner-entered deadlines reuse the document and action system; partial settlements retain the correct remainder.

Phase 4.x — analysis and optimisation

PhaseOutcomeSuccess criteria
Phase 4.1Budgets and recurring discovery Budget versus actual supports category, bucket, rollover, and variance; discovered cadence or price changes remain proposals until confirmed.
Phase 4.2Salary analysis Compensation, cash received, bonuses, and increment history reconcile to payslip and ledger evidence without inventing missing periods.
Phase 4.3Investment analysis Returns, benchmarks, allocation drift, and contribution effects reconcile to transaction-level holdings and dated prices.
Phase 4.4FX and remittance analysis Provider cost and effective-rate history use evidenced amounts and dates; internal transfers remain outside spending.
Phase 4.5Optional email ingestion A dedicated mailbox can supply statement attachments without broad mailbox access or stored bank credentials; every import retains the normal review boundary.
Phase 4.6Conditional loan support Activated only when the owner confirms a real loan. Schedules reconcile to lender evidence; events regenerate future terms; prepayment analysis states liquidity and interest assumptions.

Phase 5.x — optional private intelligence

Deterministic product capabilities do not depend on this group. No model receives financial data until the explicit privacy and safety gate in Phase 5.1 is accepted.

PhaseOutcomeSuccess criteria
Phase 5.1Privacy, safety, and runtime decision Permitted data, redaction, local-versus-remote execution, telemetry, abstention, and query safety are approved and tested before any intelligent feature is enabled.
Phase 5.2Ask My Finances Natural-language questions compile to constrained queries against the normalized ledger, never raw statements, with visible sources and safe failure.
Phase 5.3Classification fallback The deterministic engine has priority; the fallback proposes bounded classifications, abstains when uncertain, and cannot write directly to the ledger.
Phase 5.4Financial insights Anomalies and trends cite clean historical evidence, distinguish observation from advice, and remain silent when coverage is inadequate.
Phase 5.5Scenario simulator Multi-variable projections identify every assumption and never alter recorded financial history.
Phase 5.6Tax reporting Reports derive from proven investment-lot and residency evidence, expose their period and assumptions, and remain exportable for independent review.
Phase 5.7Portfolio rebalancing Target allocation, drift, and tax-aware suggestions are advisory only and reconcile to the owner's holdings.
Phase 5.8Automated imports Supported aggregators or open-banking sources use revocable tokens, never stored banking credentials, and preserve dedupe, reconciliation, and review.

Scope control

  1. New ideas enter the project register. They reach this roadmap only after owner approval.
  2. Approval requires an explicit scope and sequencing decision; implementation does not begin from a note alone.
  3. A new institution layout remains data and must not introduce institution-specific code.
  4. Paid infrastructure is considered only when its owning outcome needs it.
  5. Work that does not fit a reviewable branch is decomposed before implementation.

Outside the approved roadmap: mobile applications, multi-user collaboration, stored bank credentials, automatic payments or trades, receipt OCR, advisor access, business accounting, and unsupported complex instruments. Any promotion follows the same register and owner approval path.

Implementation progress

This roadmap contains no live completion claims. Read implementation progress for current state and the project register for deferred or unapproved items.
