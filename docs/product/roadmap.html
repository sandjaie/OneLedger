08 — Roadmap

Phase 0 → Phase 1 (ten milestones) → Phase 2 → V2.

Sequencing principle: usefulness early. The milestones are ordered so the tool becomes worth opening at M2, not at M10. A personal project that only pays off at the end usually doesn't reach the end.

No time estimates. They would be fiction for a project built in evenings around a job. Each milestone instead has a definition of done that is objectively checkable, and milestones are sized so that one is completable in a small number of sessions.

M6, M7 and M10 are independent of one another and can be done in any order, or interleaved according to which is most useful at the time.

M8 (Loans) is descheduled. No loan appears in any of the 71 statements gathered, and Q18 is unanswered. Building an amortisation engine for a loan that may not exist is the clearest possible case of speculative work. The milestone stays specified below, ready to be scheduled the moment a loan is confirmed — the schema (loan, loan_schedule_entry, loan_event) still ships in Phase 0 migrations, so scheduling it later costs no migration.

Phase 0 — Foundations

Everything needed before feature work has somewhere to land.

Deliberately lean. CI, the VPS deployment and the backup script are not here — there is nothing yet to regress, deploy or lose. They land in M1 and M2, where they start earning their keep. Nothing is dropped; it is sequenced.

Deliverables

  • Monorepo skeleton per architecture.html §3.
  • The full docker compose stack — web, api, db — running locally. The same file deploys later (ADR-0018).
  • Migrations 0001–0004: extensions, reference data, identity, RLS, accounts, FX rates.
  • Google OIDC implemented in the service; a signed session cookie; one app_user row.
  • RLS enabled on every household-scoped table, with a test proving isolation.
  • FX backfill: 36 months of USD/INR from ECB back to 01 Jan 2024, AED/INR derived through the peg (ADR-0013).
  • Next.js app shell: layout, navigation, auth guard, currency toggle in the header.
  • The Python service skeleton — FastAPI, uv, ruff, mypy --strict, pytest, and the require_owner() dependency that every route depends on (ADR-0017).
  • .gitignore excluding pdf-statements/, *.pdf and .env; pre-commit secret scan.

Done when

  • docker compose up gives the whole stack — web, api, db — with no network dependency.
  • Google sign-in works locally; a non-permitted account is rejected by the service, not just the UI.
  • Settings › FX shows a rate for 2026-09-03 with its source and carry-forward status.
  • Settings › FX shows a rate for 2024-01-01 — the backfill reaches the anchor.
  • A query as an unauthenticated role returns zero rows from every table.
  • No real statement is reachable from git status.

Phase 1 — The Ledger

The release described in the brief: Accounts → Statement Import → Transactions → Categories → Credit Cards → Monthly Cash Flow → Investments → Loans → Net Worth.

M1 — Accounts and manual transactions

The skeleton everything else hangs from.

Build

  • Account CRUD across all types; institution picker; currency and country.
  • Opening balance with date. Computed balance = opening + Σ transactions.
  • Signed-balance convention implemented and tested for asset and liability accounts.
  • Manual transaction entry with the FX freeze applied on save.
  • Transaction list: filter, sort, search, inline category edit.
  • Seed taxonomy loaded; category management screen.
  • Accounts overview grouped by class, showing totals in both currencies.

Done when

  • Every account type creates and lands in the correct net-worth bucket.
  • A liability account's balance moves the right way for a purchase and for a payment.
  • Balance equals opening + Σ(amount) to 4 dp for both classes.
  • A manually entered AED transaction shows the correct frozen INR value.
  • 100 manual transactions can be entered and filtered without noticeable lag.

M2 — Importer, UAE card statements, end-to-end

The first milestone that makes the tool genuinely useful. Deliberately narrow: one layout, all the way through, rather than four layouts half-done.

Re-planned twice. It originally read "CSV/Excel, one institution"; Q7 established that no institution provides CSV or Excel — every layout is PDF. Then ADR-0016 made layouts data rather than code, so this milestone's deliverable is the generic engine plus the mapping UI, proven by mapping one layout. The card statements are that layout: cleanest of the four, they declare their own reconciliation anchors in a header block, and one profile covers both cards — 38 of the 71 files.

Build

  • The generic extraction engine, driven by a statement_layout row (ADR-0016). No bank name in code.
  • The layout mapping UI: find the header row, auto-propose column bands from its x-positions, show the parsed result live, let the user drag and relabel, save the profile.
  • Field-name synonyms so auto-proposal works across layouts (Narration/Particulars/ Description, Withdrawal/Debit).
  • pdfplumber extraction — columns by x-position, never regex over flattened text.
  • One layout mapped end-to-end — the credit-card statements, being the cleanest and covering the most files. Mapped through the UI like any future bank, not written as code.
  • The first two quirk handlers: filter_script:arabic and continuation:no_date_and_no_amount.
  • Normalization: dates, signs (CR suffix, inverts_sign = True), currency, description cleanup.
  • Dedupe: document checksum + transaction fingerprint.
  • FX enrichment with fetch-on-missing.
  • Reconciliation, blocking on mismatch (I8).
  • Original stored on the documents volume; document, import_batch, staged_transaction written.
  • Review screen: list, categorize, accept, reject, import.
  • Commit in a single database transaction with post-commit balance verification.
  • The /import screen: multi-file drop, per-file status, nothing written until Stage batch.
  • Deferred in from Phase 0: CI (lint, type-check, test, migrations-from-empty) and scripts/backup-db.sh. Real data lands in the ledger here, so this is where losing it starts to matter.

Done when

  • A layout can be mapped through the UI, saved, and reused with no code change.
  • Auto-proposal identifies the header row and proposes usable column bands without hand-editing.
  • All 38 card statements import end-to-end with no manual correction of dates or amounts.
  • Reconciliation passes for every one.
  • Re-importing the same file imports zero rows and names the earlier import.
  • An overlapping statement imports only the new rows.
  • A deliberately corrupted amount blocks the batch and names the divergent row.
  • The commit is atomic — an induced failure mid-import leaves zero rows.
  • A backup has run and been restored into a scratch database.

M3 — The remaining layouts

Mostly a mapping exercise, not a coding one. If M2 built the engine correctly, this is three passes through the mapping UI plus whatever quirks the real statements expose. Layouts are described here by their characteristics, because that is what the engine reacts to — the bank names are the user's data, not the product's.

Build

  • Coordinate extraction hardened for the space-less layout — measured: word grouping does not rescue it in any language, column banding does.
  • Multi-line description handling as a profile rule, not per-layout code.
  • Password-protected PDF support; the import screen prompts per file, nothing persisted.
  • Map the remaining three layouts, in ascending difficulty:
    1. Declares OPENING BALANCE — reconciliation is straightforward. 2 accounts.
    2. Running balance only — reconciliation asserts row-to-row continuity instead. Reverse-chronological, two physical lines per transaction. Extracts the embedded remittance INR amount and rate into raw_row (04 §5).
    3. Encrypted, and extracts with no spaces — column bands are the only workable approach. Hardest of the four; done last deliberately.
  • Redacted fixtures for each, with a golden-output test.
  • Diagnostics panel: extracted rows beside the computed running balance, divergence highlighted.
  • Scanned-PDF detection with a clear "not supported" message rather than garbage output.
  • Each new quirk is a considered addition to the vocabulary, not a reflex. If the list starts growing per-bank, ADR-0016 has failed and needs revisiting with a superseding ADR.

Done when

  • All four layouts import a real statement and reconcile — none of them named in code.
  • Each has a fixture test that fails if the engine or a saved profile regresses.
  • An encrypted statement imports without the password touching disk.
  • All 71 gathered statements import; every account reconciles across its full period.
  • A layout invented for the test — a synthetic statement in an unseen format — can be mapped and imported without touching the codebase. This is the real acceptance test for ADR-0016.

M4 — Classification engine

Build

  • The full cascade (override → user rule → merchant alias → prior match → seed rule).
  • Rule CRUD with a live preview of affected transactions.
  • ~120 seed rules for UAE, India and global merchants.
  • Merchant normalization with aliases.
  • Learn-from-correction prompt with affected count and opt-in retroactive apply.
  • Confidence scoring driving review-queue grouping.
  • Bulk recategorization.
  • Settings › Rules: coverage, hit counts, override counts, top unclassified descriptions.

Done when

  • Seed rules classify ≥ 70% of a real first import.
  • Every classified transaction can name the rule that classified it.
  • Creating a rule from a correction shows an accurate affected count and applies correctly.
  • Rules never silently change past data.

M5 — Transfers

The point at which the numbers become trustworthy. Before this, every spending figure is wrong.

Build

  • Matching engine with the weighted scoring in transfers-and-reconciliation.html §3.
  • FX-aware amount matching with a 5% remittance tolerance.
  • Kind-specific date windows.
  • Transfer confirmation in the review queue; nothing auto-links.
  • Manual linking and unlinking from the transactions screen.
  • Pending (one-sided) transfers, re-matched on later imports.
  • FX spread and total cost computed per transfer.
  • v_transaction_reportable enforced; static check that reports never read the base table.

Done when

  • A real remittance is detected above 0.90 and appears in neither spending nor income.
  • A card payment is detected and excluded.
  • Two unrelated same-day similar amounts are not linked.
  • Unlinking a remittance increases reported spending by exactly the source amount.
  • Monthly spending, after transfer exclusion, matches a hand-tallied figure for one real month.

M6 — Credit cards

Build

  • Card statement parsing into card_statement records.
  • Statement balance, minimum due, due date, credit limit, utilisation.
  • Card payment reconciled against the statement balance; paid-in-full detection.
  • Card detail view: current outstanding, cycle spending, utilisation, what's due when.
  • Upcoming-payment surfacing on the dashboard.

Done when

  • Utilisation matches the card statement.
  • A payment appears in neither spending nor income.
  • Cycle spending equals the statement's declared total debits.
  • A card carrying a revolving balance is visually distinct from one paid in full.

M7 — Investments

Build

  • security, holding, investment_transaction, price_snapshot.
  • Indian mutual fund support keyed on AMFI scheme code; daily NAV import from the AMFI file.
  • CAS (CAMS/KFintech) parser if one is available — otherwise manual and broker-statement entry.
  • Equity and ETF holdings, Indian and international.
  • XIRR by Newton–Raphson with bisection fallback.
  • Asset allocation aggregation across the seven classes.
  • Investment purchase linked to its funding bank debit.
  • Portfolio screen: holdings, allocation, returns, XIRR.

Done when

  • XIRR for a known SIP series matches a spreadsheet XIRR() within 0.01%.
  • Allocation sums to 100% and reconciles to total portfolio value.
  • A USD holding contributes correctly to both INR and AED views.
  • Σ investment transaction units equals holding units for every holding.
  • Buying a fund shows as one linked event, not two unrelated rows.

M8 — Loans — descheduled, pending Q18

Kept fully specified so it can be picked up unchanged. Not scheduled: no loan is evidenced in the gathered statements.

Build

  • loan, loan_schedule_entry, loan_event.
  • Amortisation generation from terms; versioned regeneration on any event.
  • EMI transactions matched to schedule entries; actual principal/interest split recorded.
  • Prepayment handling with schedule regeneration.
  • Floating rate changes as events.
  • Loan detail: outstanding, paid to date, interest paid, remaining tenure, payoff date.

Done when

  • Generated schedule matches the lender's amortisation table within rounding.
  • Interest paid in a period equals the sum of interest components of actual EMIs.
  • A prepayment regenerates the schedule and shows the revised payoff date.
  • Outstanding principal matches the lender's statement.

M9 — Net worth and the dashboard

The morning screen.

Build

  • Signed-balance net worth across all accounts, both currencies.
  • Liquid net worth (excluding property and locked retirement accounts).
  • Month-end snapshots with the rates used, stored.
  • Net worth trend chart.
  • Attribution per multi-currency-and-fx.html §7, including the FX translation line and a visible residual.
  • Monthly cash flow: income, spending, net, 12-month trend.
  • Savings rate and investment rate, tracked separately.
  • Need / Want / Investment / Debt split.
  • The dashboard: net worth, liquid, investments, debt, month income, month spending, savings rate, investment rate, 12-month chart.
  • Manual valuation snapshots with staleness indicators.

Done when

  • Net worth on any past date equals the sum of signed balances on that date, in both currencies.
  • Attribution components plus residual equal the actual change exactly.
  • Residual is under 1% for a period with complete data.
  • Spending for a month equals the sum of reportable transactions, exactly.
  • Dashboard is interactive in under 2 seconds cold.

M10 — Documents vault

Build

  • Document library: filter by institution, type, period, account.
  • Bidirectional traceability — document ↔ transactions.
  • Non-statement uploads: insurance, property, tax, FD certificates.
  • Checksum-based duplicate prevention at upload.
  • Deletion blocked while transactions reference a document.
  • Receipt attachment on transactions.

Done when

  • Every document is retrievable and openable.
  • Every imported transaction links back to document, page and row.
  • Re-uploading a stored file is detected before parsing.
  • Disk usage on the box is visible, documents and database separately.

Phase 1 exit criteria

All scheduled milestones done (M8 excepted while descheduled), plus:

  1. 36 months of real statements across all four layouts, imported and reconciled — back to the 01 Jan 2024 anchor (ADR-0013).
  2. Monthly import + review completed in under 20 minutes.
  3. Net worth agrees with a manual tally to within 1%.
  4. Monthly spending agrees with a hand-checked month, exactly.
  5. Zero infrastructure spend.
  6. Restore from backup verified against a scratch database.

Phase 2 — Analysis

Phase 1 answers what happened. Phase 2 answers what it means. It requires no schema redesign — the tables are already defined in data-model.html §14.

Module Content
Budgets Budget vs actual by category and by bucket; rollover; variance alerts
Recurring expenses Automatic discovery from amount/merchant/cadence patterns; "committed spend before discretionary" for the month ahead; price-increase and zombie-subscription detection
Salary analytics Payslip parsing into line items; annual compensation vs actual cash received; bonus and increment history
Investment analytics Portfolio XIRR, per-class returns, allocation drift vs target, SIP performance, benchmark comparison
FX & remittance analytics Annual cost by provider, effective-rate history, cheapest-channel comparison
Goals Target amount and date; progress from actual contributions; required run rate
Loan simulator "If I prepay AED 50k: new payoff date, interest saved, liquidity after." Built on M8's schedule engine
Email ingestion Auto-fetch statement attachments from a dedicated mailbox

Entry condition: Phase 1 exit criteria met, and the ledger has been maintained for at least two months. Analysis over an incomplete ledger produces confident nonsense.

V2 — Intelligence

Everything AI lives here (ADR-0004). The privacy decision is explicitly deferred and must be made before any of this starts.

Module Content Prerequisite
Ask My Finances Natural language → SQL against the normalized ledger. Never reads raw statements Stable schema; query safety layer; privacy decision
AI classification fallback Step 7 of the cascade, after everything deterministic abstains Rule engine ≥ 90%; redaction spec; cost measured
Financial insights Anomaly detection, trend narration, proactive observations ≥ 12 months of clean data
Scenario simulator Multi-variable what-ifs across loans, investments and cash flow Phase 2 loan simulator working
Tax reporting India ITR support: capital gains, foreign asset schedules. UAE context Investment lot tracking (M7) proven over a full year
Portfolio rebalancing Target allocation, drift alerts, tax-aware rebalancing suggestions Phase 2 investment analytics
Automated imports Account aggregator (India), open banking (UAE) where available, still token-based Never credential storage

Ask My Finances is the payoff for Phase 1's discipline. It is feasible only because the ledger is normalized — the model writes a query against a clean schema rather than reading thousands of statement pages. Attempting it before Phase 1 would be both expensive and unreliable.

Scope control

Phases have a fixed size. Adding something means removing something.

Rules

  1. A new Phase 1 idea goes to Phase 2 by default. Promoting it requires demoting something.
  2. AI in Phase 1 or 2 is blocked by ADR-0004. Not a judgement call during the build.
  3. A new institution parser is always allowed — it is additive and doesn't touch shared code.
  4. Anything requiring paid infrastructure goes to a "when hosted" list, not into a phase.
  5. If a milestone hasn't finished after three sessions, it was too large. Split it rather than pushing through.

Explicitly parked — reconsidered only after Phase 2:

Mobile apps · multi-user · bank API integration · receipt OCR · shared/collaborative features · export to advisors · crypto beyond manual valuation · options and derivatives · business accounting.
