Master implementation plan

This is OneLedger's single delivery map. It translates the approved outcomes in the product roadmap into one dependency-aware Phase N.M sequence. Dated specifications and plans define one outcome in implementation detail.

This page contains no live completion status. Read implementation progress for the current position and next action. Read the project register for deferred, conditional, or unapproved information.

Constraints inherited by every phase

  • Money is exact: NUMERIC in Postgres, Decimal in Python, strings on the wire, and display-only in TypeScript. The API contracts and data model own the details.
  • Original and frozen reporting amounts never change after import. Balance translation uses an explicit as-of date and does not rewrite historical flows.
  • Reports consume v_transaction_reportable; confirmed transfers and card payments do not become income or spending.
  • Every imported row traces to its document, page, and source row. A statement that does not reconcile cannot commit.
  • Every financial route passes the owner authorization boundary. Household-scoped tables retain row-level security. The security specification owns the never-store list.
  • No institution, country, or currency becomes a required code identifier. Layouts and financial entities remain data.
  • Migrations are forward-only and applied by Flyway; an applied migration is never rewritten.
  • No intelligent feature begins before Phase 5.1. No feature performs automatic payments, trades, or unreviewed ledger writes.
  • The active-checkout, branch, review, diff-budget, and release rules remain owned by Git workflow and Development cycle.

Phase 0.x — foundations and manual ledger

Purpose: establish a private local ledger whose service boundary, data model, money semantics, and source storage are safe enough for feature work.

  • Phase 0.1: compose runtime, repository skeleton, secret scanning, real-data exclusion, and migrations from empty.
  • Phase 0.2: tenancy, row-level security, the owner service boundary, revocable sessions, and protected routes.
  • Phase 0.3: configured reporting currencies, the approved history anchor, source rates, peg derivation, carry-forward labeling, and exact wire values.
  • Phase 0.4: household settings, all required account types, signed balances, opening evidence, manual transactions, and category management.
  • Phase 0.5: content-addressed document storage, extraction-layout data, normalization primitives, dedupe primitives, and private diagnostics foundations.

Boundary: Phase 1.1 starts only when supported documents have a safe storage and ledger destination. Owner-operated identity checks remain explicit evidence gates and never become synthetic claims.

Phase 1.x — daily-use financial core

  • Phase 1.1: complete parse-to-commit flow, review routes and screens, atomic commit, post-commit balance verification, duplicate handling, and one supported profile.
  • Phase 1.2: remaining supported profiles, encrypted input, multi-line rows, coordinate-banded extraction, running-balance reconciliation, and redacted golden fixtures.
  • Phase 1.3: explainable deterministic classification, personal reusable rules, confirmed transfer linking, pending counterpart review, and reportable-flow protection.
  • Phase 1.4: statement-derived card facts, dues and payment state, signed net worth, monthly income/spending/net, savings rate, and a twelve-month trend.
  • Phase 1.5: masked account proposals from statement evidence, encrypted local identity recovery, deliberate reveal, and owner decisions for unresolved classifications.
  • Phase 1.6: securities, holdings, transaction-level units, dated prices, funding links, allocation, XIRR, owner-entered fallback, and supported statement imports.
  • Phase 1.7: entered and text-PDF-imported payslip line items, net-pay linking to a salary credit, owner-entered commitments, and a thin per-account forecast whose dates, coverage, and assumptions are visible.
  • Phase 1.8: a mapping screen over the existing header discovery, proposed column bands and live preview, profile save/reuse, a filterable document library, row provenance links, and per-document parse status and reconciliation verdict.

Boundary: the owner can maintain the complete application through supported inputs, understand missing coverage, and verify positions and flows. Detailed historical depth is deliberately owned by Phase 2.x.

Phase 2.x — verified history and data quality

  • Phase 2.1: close supported historical coverage back to the approved anchor and surface every unavailable account or period.
  • Phase 2.2: dated month-end positions and an attribution waterfall that exposes FX translation, market movement, external change, and residuals independently.
  • Phase 2.3: correction-driven rule proposals, confidence, rule analytics, coverage, and review prioritization without retroactive silent change.
  • Phase 2.4: a diagnostics surface, backup coverage for database and documents, an isolated restore drill, and recorded structural verification.

Boundary: the ledger supports planning only after history, uncertainty, reconciliation gaps, and recoverability are visible rather than assumed.

Phase 3.x — planning and resilience

  • Phase 3.1: commitments with recurrence, certainty, source, settlement, and a single action lifecycle.
  • Phase 3.2: deterministic per-account and per-currency projections with lowest balance/date, gaps, cancellation behavior, and monthly review.
  • Phase 3.3: exclusive resource reservations, goal contributions and shortfall, eligible emergency resources, and an explicit essential-spend baseline.
  • Phase 3.4: policy coverage and renewals, maturities, claims, reimbursements, deadlines, and linked documents/actions.

Boundary: projections are never postings or bank-confirmed cash. Every result shows evidence dates, incomplete coverage, and owner-controlled assumptions.

Phase 4.x — analysis and optimisation

  • Phase 4.1: budgets, rollover and variance plus owner-confirmed recurring discovery, price changes, and inactive-subscription candidates.
  • Phase 4.2: compensation versus cash received, bonuses, increments, and deeper payslip history.
  • Phase 4.3: portfolio and class returns, benchmarks, contribution effects, and allocation drift.
  • Phase 4.4: evidenced provider costs, effective-rate history, and remittance comparison.
  • Phase 4.5: least-privilege attachment ingestion from a dedicated mailbox while preserving ordinary import review.
  • Phase 4.6: when activated, loan terms, schedules, actual events, prepayments, rate changes, and liquidity-aware simulation.

Conditional activation: Phase 4.6 starts only after the owner confirms a real loan and supplies evidence. Its absence does not block Phase 5.x.

Phase 5.x — optional private intelligence

  • Phase 5.1: approve data boundaries, redaction, telemetry, execution location, query safety, evaluation thresholds, abstention, and owner controls.
  • Phase 5.2: constrained natural-language queries against the normalized ledger, with sources and no raw-document access.
  • Phase 5.3: a measured classification fallback after deterministic rules abstain, producing proposals rather than writes.
  • Phase 5.4: evidence-linked anomaly and trend observations.
  • Phase 5.5: assumption-visible scenarios across cash, investments, and any activated debt engine.
  • Phase 5.6: independently reviewable tax exports from proven lot and residency evidence.
  • Phase 5.7: advisory-only allocation and tax-aware rebalancing suggestions.
  • Phase 5.8: revocable-token imports that retain dedupe, reconciliation, and owner review.

Dated specification and plan contract

Before any unimplemented Phase N.M begins, its specification and execution plan are written against the current tree. Together they state:

  • the exact workspace, branch, base, and pull-request target;
  • outcome, affected files, dependencies, contracts, invariants, and security requirements;
  • required failing-test behavior, validation commands, and objective acceptance;
  • task boundaries that fit the repository diff budget.

Execution plans are instructions, not status trackers. Repository reality may require an implementation detail to change, but the roadmap outcome, specification contract, and acceptance boundary remain authoritative. A deviation is recorded in the pull request and progress tracker, never by rewriting a dispatched plan as history.
