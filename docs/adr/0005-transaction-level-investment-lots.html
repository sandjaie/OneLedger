ADR-0005 — Track investments at lot level, not snapshot

Status: Accepted · Date: 2026-09-04

Context

Two ways to track a portfolio:

  • Snapshot: "I have put in ₹8L; it is worth ₹10.2L." Two numbers per holding.
  • Lot level: every purchase, SIP instalment, redemption and dividend, with units and NAV.

Snapshot is dramatically less work — no CAS parser, no unit reconciliation, no NAV history.

But snapshot cannot produce XIRR, and XIRR is the only correct return measure for a SIP. Absolute return on a series of monthly contributions is close to meaningless: it treats money invested last month the same as money invested three years ago.

Decision

Track at lot level. Every investment transaction is stored with units, NAV, charges and tax withheld, linked to the bank transaction that funded it.

Rationale

XIRR cannot be backfilled. This is the decisive point. Absolute return can be computed from lots at any time; XIRR cannot be computed from snapshots at any time. Choosing snapshots means either never having XIRR, or re-entering the entire investment history later — by which point there is more of it.

The same data serves capital gains. India taxes short- and long-term gains differently, with per-lot holding periods. Tax reporting is a V2 goal, and it is only possible with lot-level data captured from the start.

The incremental cost is smaller than it looks. A CAS covers every Indian mutual fund holding across AMCs in a single document. One parser gets most of the portfolio. Broker statements cover equities. The work is concentrated in one milestone rather than spread everywhere.

It is consistent with the rest of the design. The ledger stores events and derives state everywhere else. Storing a snapshot for investments would be the one place state is stored directly, which is exactly the modelling inconsistency that produces reconciliation gaps.

Alternatives considered

Snapshot only. Rejected: no XIRR, ever, without re-entering history.

Hybrid — snapshots as baseline, lots where convenient. Superficially pragmatic. Rejected because it produces two code paths and two accuracy levels in the same portfolio view, and "which holdings have real XIRR?" becomes a question the user has to hold in their head. Worse than either pure option.

Consequences

Good. True XIRR per holding and per portfolio. Correct average cost. Capital gains basis available when tax reporting arrives. Investment purchases link to their funding debits, so a SIP appears as one event rather than two unrelated rows.

Costs. M7 is the largest Phase 1 milestone. Unit reconciliation (Σ transaction units = holding units) becomes an invariant that must hold, and a corporate action — a bonus, a split, a scheme merger — needs explicit handling rather than being absorbed silently into a snapshot.

Mitigation for opaque holdings. EPF, PPF and NPS do not produce lot-level statements and are handled by valuation snapshots (ADR-0006). Those contribute to net worth and allocation but carry no XIRR — which is correct, because the data to compute one does not exist.
