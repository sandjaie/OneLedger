ADR-0012 — Statement layouts are data, not code

Status: Accepted · Date: 2026-09-05 · Supersedes: the parser-registry design in architecture.html §3 and statement-ingestion.html §3–§4

Context

The specification defines a parser per statement layout as a TypeScript module — uae-card.ts, uae-current.ts, axis.ts, hdfc.ts — selected by a registry that matches content fingerprints.

That makes the set of supported banks a property of the deployed code. Adding a bank, or importing an old statement from an account long since closed, requires editing source, running tests and deploying. For a personal tool intended to run for a decade across an unknown future set of institutions, that is the wrong boundary. The user's objection was direct: the app should be agnostic; opening a new account or finding an old statement should not require a code change.

Most of the system was already agnostic. institution is a table, not an enum. account_type enumerates types, not banks. security is keyed on ISIN or AMFI scheme code. Categories, merchants and rules are user-editable rows. Parsers were the only hardcoded thing, and they were hardcoded because a PDF statement has no universal format — something must know where the columns are.

The question is whether that something is code or data.

Decision

A statement layout is a row in statement_layout, created through a mapping UI. No parser is written in code.

One generic extraction engine reads any layout profile. On encountering an unrecognised statement, the import screen:

  1. Finds the header row — the line whose words match known field synonyms.
  2. Auto-proposes column bands from those words' x-positions.
  3. Shows the parsed result, live, beside the original.
  4. Lets the user correct the mapping by dragging band edges or relabelling a column.
  5. Saves the profile. That layout is supported from then on, with no code change and no deploy.

Rationale

All four real layouts declare a header row. Verified against the 71 gathered statements:

UAE card       Transaction Date · Posting Date · Description · Amount
Axis           Tran Date · Chq No · Particulars · Debit · Credit · Balance · Init.Br
UAE current    Date · Description · Debits · Credits · Balance
HDFC           Date · Narration · Chq./Ref.No. · ValueDt · WithdrawalAmt. · DepositAmt. · ClosingBalance

Auto-proposal is therefore not a hopeful heuristic — it has a concrete anchor in every layout actually in hand, and a synonym table (Narration / Particulars / Description; Withdrawal / Debit) covers the naming variation between them.

Reconciliation is what makes a generic mapper safe. A mis-mapped column produces rows that do not bridge the declared opening and closing balance, and Invariant I8 blocks the import. The generic engine is trustworthy precisely because a mapping error fails loudly rather than corrupting the ledger silently. A hand-written parser has exactly the same protection and no more.

The work is comparable, and it is paid once. The mapping UI is roughly the size of the four hand-written parsers it replaces — but it covers the fifth bank, and the twelfth, for free.

It matches how the rest of the product already works. Classification rules, merchant aliases and the category tree are all user-editable data with a UI for editing them. Parsers were the outlier.

What the profile holds

detection      fingerprints[]              regexes matched against page 1
geometry       header_row_pattern
               columns[]                   {field, x_min, x_max, label}
semantics      date_format                 'dd/MM/yyyy' | 'dd-MM-yyyy' | 'dd MMM yyyy'
               sign_convention             debit_credit_columns | signed | cr_suffix | balance_delta
               inverts_sign                true for credit-card statements
               chronological_order         ascending | descending
row assembly   row_start_rule              has_date_and_amount | has_date
               continuation_rule           how a wrapped description is joined
exclusions     skip_line_patterns[]        legend pages, footers, page furniture
balances       opening_balance_pattern
               closing_balance_pattern
               has_running_balance         true where no opening/closing is declared
quirks         quirks[]                    a small, additive vocabulary — see below
metadata       metadata_patterns           card limit, statement date, due date, minimum due

The quirks vocabulary — the honest limit

Two things resist pure configuration, both observed in the real statements:

  • filter_script:arabic — the UAE card statements are bilingual, and Arabic text interleaves with English in extraction order.
  • continuation:no_date_and_no_amount — a description wrapping across two or three physical lines, where only the first carries a date and an amount.

These are profile flags, not code — but the vocabulary of flags can only grow by someone adding a handler. That list is kept deliberately small and additive, and a new entry is a considered change, not a reflex. If it starts growing per-bank, the decision has failed and should be revisited with a superseding ADR.

Alternatives considered

Keep hand-written parsers. Most robust, since arbitrary logic is available for a gnarly layout. Rejected: every new bank and every old statement from an unsupported one needs a code change and a deploy, which is exactly the coupling being removed.

Config rows edited as JSON, no mapping UI. The same data-driven engine at a fraction of the build cost. Rejected as a false economy: hand-authoring x-coordinate bands against a coordinate dump is fiddly enough that it would be avoided, and a feature that is avoided is not a feature. The UI is what makes the data-driven engine actually usable.

Full auto-detection with no confirmation step. Rejected on principle. A silently wrong column mapping is precisely the class of failure this product exists to prevent, and it contradicts Invariant I7 — nothing derived is presented as if observed. Auto-proposal plus explicit confirmation is the same shape as the review queue, and for the same reason.

Consequences

  • No bank name appears in application code. The four known layouts become rows the user creates on first import, not modules that ship.
  • transaction.parser_name / parser_version become statement_layout_id and layout_version. The provenance question — "which layout produced this row?" — is answered by a foreign key rather than a string, and the profile that produced it can be inspected.
  • Layouts are versioned as data. When a bank changes its statement format, reconciliation fails, the user re-maps, and the profile's version increments. Rows already imported keep pointing at the version that produced them.
  • The mapping UI is a Phase 1 deliverable, and it moves M2's centre of gravity: M2 builds the generic engine and the mapping UI, then maps one layout. M3 becomes mapping the remaining three — a UI exercise, not a coding one.
  • Seed data stays, as deletable suggestions: the institution list and the ~120 merchant classification rules. Those are a starter dictionary the user owns, and they are what produce ≥70% auto-classification on the first import rather than 200 uncategorised rows (ADR-0008). They are rows, editable and deletable, and nothing structural depends on them.
