ADR-0014 — One VPS, one compose file

Status: Accepted · Date: 2026-09-05 · Supersedes: Supabase + Vercel + a local importer · Revises: ADR-0004 (its "via Supabase Auth" clause)

Context

The original sketch chose Supabase plus Vercel because both have free tiers, and "zero infrastructure spend" was a stated requirement. Every subsequent decision inherited that frame, and two of them bent around it:

  • ADR-0013 introduced a FastAPI service, which does not fit Vercel as a persistent process. That left three unattractive options: split the read path so only import runs locally, host the service on a fourth provider, or accept that importing needs the laptop.
  • Keeping statements off third-party hosts — the privacy property in security-and-privacy.html §8 — was only achievable by keeping parsing off the deployment entirely.

Both problems come from the same source: the deployment is assembled from other people's free tiers, so the pieces cannot sit together.

A single small VPS — DigitalOcean, Hetzner, Railway — running the whole stack in one compose file costs roughly $5–12 a month and removes the constraint that created the contortions.

Decision

Target deployment: one VPS, running one docker compose stack.

services:
  caddy    reverse proxy · automatic TLS
  web      Next.js
  api      FastAPI
  db       Postgres 18
volumes:
  pgdata      the ledger
  documents   original statements

Supabase is dropped. Postgres is a container. Google OAuth is implemented directly in the service. Documents live on a volume.

Nothing is deployed yet. Phase 0 and Phase 1 run locally. This ADR records the target so that the local build does not accumulate work that would have to be undone to reach it.

Rationale

Local development and production become the same stack. The compose file that runs on your laptop is the compose file that runs on the droplet. Deployment stops being an architecture and becomes a git pull.

The privacy property gets stronger, not weaker. Statements on a machine you control is a materially different thing from statements transiting Vercel or Supabase. This is the first arrangement in which the whole system can run in the cloud and honour security-and-privacy.html §8 without a special case.

It removes the vendor coupling before it is paid for. Supabase's real value is Auth, Storage and RLS through auth.uid(). Building Phase 0 on those and then moving to a VPS means rewriting sign-in, document storage and every policy — paying for auth twice to use it once. For a single pinned user, Google OIDC in FastAPI is on the order of 60 lines.

Several documented risks simply cease to exist: the free-tier storage ceiling, the inactivity pause on idle Supabase projects, and the free-tier headroom arithmetic in architecture.html §9. You size the box.

The cost requirement changes

prd.html §6 states "Cost: Zero. Free tiers only. Any feature that requires payment moves to a 'when hosted' list." That is no longer true, and the requirement is amended rather than quietly abandoned:

Cost: zero while local. Approximately $5–12 per month once hosted, for one small VPS. No per-service, per-seat or usage-based pricing — the bill does not grow with the ledger.

The property that mattered was never literally zero; it was predictable and trivial, with no vendor able to change the terms underneath the project. A fixed monthly VPS satisfies that better than a stack of free tiers does.

Consequences

Authentication is ours to build. Google OIDC: redirect, exchange the code, verify the id_token against Google's JWKS, check the address against ALLOWED_USER_EMAIL, issue a signed httpOnly session cookie. ADR-0004's substance is unchanged — Google OAuth, no passwords, no signup, no registration, one pinned account — only the mechanism moves from Supabase Auth into the service.

RLS loses auth.uid() and gains a session variable. Policies read current_setting('app.user_id', true), which the service sets per transaction. RLS remains defence in depth as established in ADR-0013; this only changes where the identity comes from.

Backups become entirely yours, and matter more. One box is one point of failure. The existing requirement — nightly pg_dump, weekly document sync, monthly off-box copy, quarterly tested restore — stops being belt-and-braces over a managed service and becomes the only thing standing between you and losing the ledger. The quarterly restore test is now the single most important operational task in the project.

You administer a machine. Unattended upgrades, a firewall, fail2ban or equivalent, TLS via Caddy, and an SSH key rather than a password. Small, but not nothing, and it is work that Supabase and Vercel were doing.

Documents affected: the PRD's cost requirement, architecture (§1, §4, §7, §8, §9, §10, §11), the data model's RLS section, security and privacy, API contracts, the roadmap, and the Phase 0 plan — which now builds against plain Postgres from its first migration.

Alternatives considered

Vercel plus a hosted Python service. Keeps a free tier for the web app. Rejected: it spreads one small system across three providers, still puts statements on hosts you do not control, and the Python provider's free tier is the least stable part of the arrangement.

Split the read path — dashboard from Vercel against Supabase, import local only. Genuinely workable and it preserved zero spend, which is why architecture.html §11 recommended it before this decision. Rejected because it institutionalises two data-access paths and permanently ties importing to one machine, in exchange for saving a few dollars a month.

Self-host on hardware at home. Free after the hardware, and maximally private. Rejected as the target: residential uptime, dynamic addressing and the exposure of opening a home network are real costs, and a VPS is cheap enough that they are not worth paying. Nothing about the compose file prevents it later — that is the point of the shape.

Kubernetes, or managed containers. Rejected without much deliberation. One user, one machine, four containers.
