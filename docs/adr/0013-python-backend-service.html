ADR-0013 — A Python backend service

Status: Accepted · Date: 2026-09-05 · Supersedes: matching in Postgres and parsing in the browser · Revises: the original sketch (its "no hosted API server" clause)

Context

Two decisions taken earlier the same day carried costs that were stated plainly in their own text:

  • One decision moved the classification cascade and the transfer matcher into Postgres. Stated cost: "matching logic is SQL, which is harder to unit-test than Python and less pleasant to debug."
  • Another moved parsing into the browser. Stated cost: "roughly 200 lines of word-grouping helper that pdfplumber would have provided free."

Both costs existed only because there was no backend. Matching went into SQL because two clients — a local importer and the web app — each needed it, and SQL was the one place both could reach. Parsing went into the browser because the alternatives were a CLI, which had been rejected as the wrong interface for a monthly task, or a hosted server, which would have put statements on a third-party host.

Neither was the best available design. Each was the best design available without a backend. The question was never asked directly until now.

A further correction matters here: the claim that Python parses these documents better than TypeScript was measured and found false — on the hardest of the four layouts pdfplumber recovers no more than pdf.js does. Parsing quality is not the argument for this decision, and it should not be recorded as though it were.

Decision

A Python backend service owns all business logic. React owns the interface. Postgres owns the truth.

React / Next.js        UI only — review queue, dashboards, layout mapping
      │  HTTP
FastAPI (Python)       parse · normalize · dedupe · FX · reconcile · stage
                       classification · transfer matching · XIRR · amortisation
      │
Supabase Postgres      source of truth · constraints · triggers · the invariants

It runs on localhost during Phase 0 and Phase 1. Statements are parsed on your own machine and never transit a third-party host, which is the property the original sketch was protecting — preserved here without the CLI that made importing a terminal command.

Rationale

It dissolves two costs rather than trading between them. Matching becomes Python: one implementation, one caller, unit-tested normally instead of through database fixtures. Parsing becomes pdfplumber: no word-grouping helper to write, no Web Worker, no glyph arithmetic.

Iterating a parser against 71 real files is the work that actually consumes time, and a REPL with a breakpoint over a directory beats DevTools on a page by a wide margin. This is the strongest practical argument and it was under-weighted when parsing moved to the browser.

It removes a client from the contract. The premise for matching in Postgres was two clients needing identical semantics. With one backend that premise is gone, and with it the reason to express the trickiest logic in a language chosen for reach rather than for expressing it.

OCR and spreadsheet parsing become additive. Neither applies today — every institution is PDF-only, and scanned statements are out of scope — but both are Python-shaped, and the service existing means they would not require a new component.

Import stays a UI action. You drop files into the web app; it posts them to the local service. The requirement that displaced the original local CLI is fully met.

What does not change

Everything in the product specification is untouched, because these are database and product decisions rather than backend-language ones: the eight invariants, signed balances, frozen dual-currency amounts, transfers as first-class entities, statement layouts as data (ADR-0012), the review queue, and the dashboard.

The invariants in particular stay enforced in Postgres — constraints, triggers and the reporting views — not in Python. A backend is a convenient place to put logic and a poor place to put guarantees.

Alternatives considered

Keep the browser parser and add Python only for parsing. Rejected: two parsers is the duplication both of those decisions were written to prevent, and it would surface as rows importing differently depending on which path ran.

Python full-stack, with HTMX or Jinja templates. One language end to end, no npm, no build step — genuinely attractive for a solo project. Rejected on two screens: the review queue and the layout mapping UI. Reviewing 200 rows and dragging column bands are the interactions that decide whether this tool survives contact with a monthly routine, and both are better served by React.

Stay on Next.js Server Components reading Supabase directly. The status quo. Rejected because it is what forced the two contortions above, and because the logic it pushes into SQL and the browser is logic that wants to live somewhere testable.

Consequences

Row Level Security stops being the security boundary. The current posture is that the browser holds only the anon key and RLS enforces isolation, so a forgotten WHERE returns nothing rather than everything. With a backend, Python holds the credentials and enforces authorization in code — as most applications do, and as this one now will. RLS is retained as defence in depth, not removed, but it is no longer the thing standing between a bug and a leak. Given that multi-tenancy is permanently out of scope this is an acceptable trade; it is recorded as a decision rather than allowed to become a side effect.

The service-role key returns to the threat model. Parsing in the browser removed it, which was a real gain, and this reverses that gain. It lives in the service's local .env, never in the browser bundle, and security-and-privacy.html §6 is updated accordingly.

Hosting is now an open question rather than a settled one. Vercel plus Supabase free tiers were the answer to the zero-spend requirement. A persistent FastAPI service does not fit Vercel; it wants Fly, Railway or Render, whose free tiers are thinner and change more often. Phase 0 and Phase 1 run locally, so this is deferred rather than incurred — but it is the one genuine risk this decision creates against a stated non-functional requirement, and it should be decided deliberately when the cloud matters, not discovered at deploy time.

Two processes to run locally — next dev and uvicorn — where there was one.

Documents affected: architecture, data model (the RLS section), statement ingestion, classification, transfers, security and privacy, API contracts (which now describes a real API surface), testing, and the roadmap. The schema itself is unchanged.

On the churn

This is the fourth structural decision recorded in a single day, and the largest. That is worth noting honestly rather than glossing.

Each was prompted by something real — a duplicated engine, an import experience that belonged in the UI, a hardcoded set of banks, and now a missing backend — and they have converged rather than oscillated. Critically, no application code exists, so the cost of this decision is rewriting prose. The same decision taken at M5 would cost a rewrite of the ledger's entire ingestion path. Deciding it now is the cheap moment, and it is the last structural question outstanding.
