ADR-0004 — Google OAuth, single user, household-capable schema

Status: Accepted; the mechanism is revised by ADR-0014 — Google OIDC in the service rather than Supabase Auth · Date: 2026-09-04

Context

This system holds an entire financial life. Authentication is a security-critical decision, and authentication flows — registration, invitation, password reset — are where a large share of auth vulnerabilities live.

Separately: the ledger is one person's today, but a spouse's accounts could reasonably be added later. Retrofitting a tenancy dimension across forty tables is a genuinely painful migration.

Decision

Still in force, but read "Supabase Auth" as "the API service". ADR-0014 removed Supabase; the service now verifies Google's id_token against Google's JWKS itself and issues its own signed session cookie. Every property this ADR decided — no passwords, no signup, one pinned address — is unchanged. Only the component performing the check moved.

Authentication: Google OAuth via Supabase Auth. No passwords. No signup flow, no public registration, no invitations, no password reset. The permitted account is pinned by email in configuration; any other Google account is rejected at the application layer even if Supabase authenticates it successfully.

Tenancy: household_id on every household-scoped table, and owner_person_id on accounts and holdings, from the very first migration. RLS policies key on household_id. One household row, one person row, one app_user row in Phase 1.

No multi-user behaviour is built. No user management, no roles beyond owner, no sharing.

Rationale

Not building signup is a security control, not a shortcut. Credential stuffing, password reset poisoning, enumeration through registration, invitation token flaws — none of these exist if the flows don't. This is the single largest structural advantage a single-user system has, and it would be careless not to take it.

MFA belongs on the Google account, where it is already configured and already managed. Reimplementing it here would be strictly worse.

The tenancy columns are nearly free now and expensive later. They cost a NOT NULL UUID per table today. Added later they cost a migration touching every table, every query, every RLS policy, and a backfill against live data.

RLS is enabled from day one even with one user for three reasons: a forgotten WHERE returns nothing instead of everything; the anon key is public by design and RLS is what makes that safe; and the policies are already correct on the day a second person is added.

Alternatives considered

Email/password. Rejected: a password to store, hash, rotate, reset and leak, for zero benefit over an OAuth provider already in daily use.

No auth at all (localhost only). Simplest. Rejected because the dashboard should be reachable from a phone, and because an unauthenticated deployment is one misconfiguration away from public.

Full multi-user now. Rejected: builds user management, invitations and permission checks for a system with one user, and reintroduces the auth-flow attack surface the decision above removes.

Single user with no tenancy columns. Simplest schema. Rejected on migration cost — the one decision here that would be genuinely expensive to reverse.

Consequences

Good. No password anywhere in the system. Minimal auth surface. Household support is a feature flag and a second app_user row rather than a migration. RLS is correct before it is needed.

Costs. Google is a hard dependency for access — losing that account means losing access until the Supabase auth provider is changed. Accepted; the alternative is a password. Also, one NOT NULL UUID per table serving no present purpose, which will look like over-engineering right up until it doesn't.
