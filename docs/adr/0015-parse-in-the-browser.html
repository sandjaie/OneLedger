ADR-0015 — Parse statements in the browser; retire the Python importer

Status: Superseded by ADR-0017 · Date: 2026-09-05 · Partially supersedes: ADR-0002 (its third component only)

This decision no longer holds. It is kept as the record of what was decided and why it changed — deleting it would leave the current architecture looking arbitrary. The decision in force is ADR-0017.

What changed: this ADR chose PDF parsing in the browser with pdf.js. Parsing now happens in the API service with pdfplumber. Everything below describes the system as of 05 September 2026, not the one being built.

Context

ADR-0002 chose three components: Next.js on Vercel, Supabase, and a local Python CLI that parses statements on the user's own machine. Its case for the third rested on four claims:

  1. Free-tier hosted functions are bad at PDF parsing — cold starts, execution ceilings, ~256 MB.
  2. Statements must not transit a third-party host.
  3. Parser debugging is far easier with a breakpoint than with deploy-and-read-logs.
  4. The importer is where the interesting Python lives: Pydantic models, a parser registry, a rules engine, a matching algorithm, XIRR, a CLI.

Claims 1–3 were and remain sound. Claim 4 stopped being true the same day it was written: ADR-0014 moved the rules engine and the transfer matcher into Postgres, because they were otherwise specified to exist twice. What remained in Python was four PDF parsers, normalization, a dedupe hash and reconciliation arithmetic — a thin case for a separate language, a separate runtime and an install step, in service of a task performed monthly.

The user's objection was direct: importing should be part of the web UI. It is the right objection. A file picker is the correct interface for "import this month's statements"; a terminal command is not.

Decision

Parse in the browser, with pdf.js. Retire the Python importer entirely.

Two components, not three:

   ┌──────────────────────────────────────────────────────────┐
   │  Next.js (App Router) · React · TypeScript               │
   │                                                           │
   │  Upload → parse (pdf.js, in a Web Worker) → normalize     │
   │         → dedupe → FX freeze → reconcile → stage          │
   │         → review → commit                                 │
   │                                                           │
   │  Bytes never leave the page.                              │
   └──────────────────────────┬───────────────────────────────┘
                              │  anon key + user JWT, RLS-scoped
   ┌──────────────────────────▼───────────────────────────────┐
   │  SUPABASE                                                 │
   │  Postgres · Auth · Storage                                │
   │  match_classification_rules() · score_transfer_candidates()│
   └──────────────────────────────────────────────────────────┘

Rationale

The browser is the local machine. The privacy property ADR-0002 was protecting — statements never transit a third party — is preserved exactly. It is arguably strengthened: the bytes never leave the page context, so there is not even a local process holding decrypted content on disk. Claims 1 and 2 above are satisfied without a separate runtime.

pdf.js provides what the parsers actually need. getTextContent() returns text items with a transform matrix (x/y), width and height. That is precisely the coordinate-based extraction 05 §4 mandates, and the only reason HDFC's space-less text is parseable at all. getDocument({ password }) handles the encrypted Indian statements natively.

The service-role key largely leaves the system. The Python importer wrote with SUPABASE_SERVICE_ROLE_KEY — a key that bypasses RLS entirely, held in a .env on a laptop, and the highest-value secret in the threat model (09 §6). The browser writes as the signed-in user with the anon key under RLS. A key that no longer needs to exist cannot leak.

One language, one repository, one mental model. For a system maintained solo in evenings, the cost of a second runtime is paid on every context switch, not once at setup.

Verified, not assumed: Frankfurter returns access-control-allow-origin: *, so FX backfill runs client-side with no server at all (checked 2026-09-05).

Alternatives considered

Keep the local Python CLI. pdfplumber is more ergonomic than pdf.js on well-formed layouts — words and tables come free — and claim 3 (breakpoint debugging) still favours it. But see the measured correction below: on the hardest of the four layouts it recovers no more than pdf.js does. Rejected because the import experience is the recurring cost of using this product (05 preamble: "if importing a month of statements is painful, the ledger goes stale and everything built on top of it becomes decoration"). A monthly terminal command is friction in exactly the wrong place.

Server-side parsing on Vercel or Supabase Edge Functions. The familiar shape, and it delivers the same web UI. Rejected: statements would transit a third-party host, contradicting a stated product principle rather than merely a preference, and it reintroduces precisely the cold-start and execution-ceiling problems ADR-0002 correctly identified.

Browser first, Python retained for bulk backfill and parser development. Superficially the best of both. Rejected as the exact duplication ADR-0014 was written to eliminate — two implementations of every parser, guaranteed to diverge, with the divergence surfacing as rows that import differently depending on which path was used.

Pyodide, running pdfplumber in WebAssembly. Would keep the nicer library and the Python. Rejected: a ~10 MB runtime download for a page whose whole point is being quick to open, plus a fragile dependency chain, to avoid writing ~200 lines of word-grouping helper.

Correction — measured, 2026-09-05

This ADR originally presented the cost of choosing pdf.js as the loss of what pdfplumber gives "for free". Tested against the actual statements, that is overstated.

On the encrypted, space-less layout — the hardest of the four — pdfplumber recovers no more than pdf.js does:

extract_text()  → PageNo.:1 Statementofaccount
extract_words() → ['PageNo.:1', 'Statementofaccount', 'AccountBranch', ':',
                   'PERUMBAKKAMNOOKAMPALAYAMROAD', 'HDFCBANKLTD,FIRSTFLOOR,MALLES']

The producer emits no space characters and the glyph runs are contiguous, so there are no gaps to split on in any language. The word-grouping work would have been required in Python too, for that layout.

What actually resolves all four layouts is column banding by x-position, which is language-neutral and is what ADR-0016 specifies. The header words carry clean coordinates — Date=40, Narration=144, ValueDt=362, ClosingBalance=564 — and that is precisely the auto-proposal anchor. Bilingual Arabic is 10% of extracted words and separable by Unicode range rather than by position: one regex, in either language.

Where Python would still be ahead, stated fairly: spreadsheet parsing (openpyxl / pandas over SheetJS), OCR if scanned statements ever come into scope, and extract_table() for ruling-line tables. None of the three applies here — Q7 established every institution is PDF-only, scanned PDFs are explicitly out of scope, and no layout in hand uses ruling lines.

The decision stands on its original reasoning: import belongs in the UI rather than a monthly terminal command, the browser preserves the privacy property, and the service-role key stops existing. Parity on extraction means none of that is bought at a cost in fidelity.

Consequences

  • pdf.js gives positioned glyphs, not words. A shared lib/pdf/words.ts groups text items into words and lines by coordinate proximity before any parser sees them. Roughly 200 lines, written once, and the four parsers build on it. This is the real cost of the decision.
  • Parsing runs in a Web Worker, so a 200-row statement does not freeze the tab.
  • The oneledger CLI does not exist. Everything it was specified to do becomes UI: import → the import screen; fx backfill / fx check → Settings › FX; doctor → Settings › Data Quality (already specified there); parse --show-rows → a diagnostic panel on the import screen; recompute → Settings buttons calling the corresponding Postgres functions.
  • PDF passwords never touch disk. No OS keychain integration is needed and no password scheme is modelled — when a file fails to open, the import UI shows a password field for that file, held in memory for the duration of the parse and not remembered afterwards. Simpler and safer than the keychain design it replaces.
  • scripts/backup-db.sh remains, as shell and pg_dump. Backups were never Python.
  • AMFI's NAV file sends no CORS headers (verified 2026-09-05), so M7 needs one small server-side proxy — a Supabase Edge Function — for daily NAV. That is the only server-side code the system requires, and it handles public reference data, never a statement.
  • Python leaves the project. The learning goal recorded in ADR-0002 is explicitly dropped: it was a means, not an end.
