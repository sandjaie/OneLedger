ADR-0008 — Seed taxonomy with Need/Want/Investment/Debt buckets

Status: Accepted · Date: 2026-09-04

Context

Two related questions:

  1. Does the product ship with a category tree, or does the user build one?
  2. The brief asks for both a detailed category view and a Needs/Wants/Investments/Debt view. Are those one classification or two?

Decision

Ship a curated two-level taxonomy, freely editable — add, rename, merge, deactivate. The category tree is universal: Housing, Utilities, Groceries, Transport, Health, Education and the rest are what spending looks like anywhere. The merchant rules that fill it are not, so they ship as packs — one global pack always loaded, plus a per-country pack for each country the household selects at setup.

Every category carries a bucket: need, want, investment, debt_service, income or ignore. One classification pass produces both views.

Rationale

Reports must work on the first import. An empty taxonomy means the first import produces a list of uncategorized transactions and no insight at all — the least motivating possible first experience, at exactly the moment motivation matters most.

The rules must be regional to be useful. A generic taxonomy has "Utilities" but no DEWA, "Transport" but no Salik or Careem, "Investments" but no SIP or NPS. Around 120 seed rules mapping the merchants one household actually encounters is what makes the first import land at ~70% classified instead of ~20%. That argument is about a region, not about these two: the packs are db/seeds/rules/regions/<iso2>.yaml, and AE and IN are simply the two that exist because they were needed first.

Bucket-on-category means the coarse view is free. The alternative — asking the user to classify each transaction twice, or maintaining a separate mapping — is redundant work for a mapping that is stable. "Groceries is a need" does not change transaction by transaction.

The bucket is a default, not a verdict. Whether dining out is a need or a want is genuinely personal. Shipping an opinion and letting it be overridden is better than either shipping no opinion or insisting on one.

Two levels, not more. One level loses "Food & Dining → Coffee", which is precisely the drill-down the brief asks for. Three levels invites over-classification and produces reports too sparse per node to say anything.

Alternatives considered

Fully user-defined. Perfectly fitted to how the user thinks. Rejected: the first several imports become taxonomy design work, and early reports are noise until the tree settles. The editability of the seed set captures most of the benefit at none of the cost.

Flat categories, no subcategories. Simplest queries and UI. Rejected: "how much did I spend on coffee last year" is a stated goal and needs the second level.

Separate bucket mapping table. More flexible — the same category could bucket differently in different periods. Rejected as flexibility nobody asked for, at the cost of a join in every report and a second thing to keep consistent.

Consequences

Good. Meaningful reports from the first import. Both the detailed and coarse views from one classification. Regional relevance out of the box for a country with a pack. Seed rules can be versioned and updated independently of user rules, and a new country is a new file rather than a change to any existing one.

Costs. The seed taxonomy needs maintaining — new merchants appear, and merchants rename; now once per pack. A country with no pack gets the tree and the global merchants only, and its first import lands well below 70% classified. That is a worse first experience, not a broken one: the rule-from-correction flow (classification.html §4) is how the pack gets written, and contributing it back is a pull request with one file in it. The taxonomy is also opinionated, and some opinions will be wrong for a given household; editability is the answer. Changing a category's bucket retroactively changes historical Need/Want reports, which is correct behaviour but should be surfaced when it happens.
