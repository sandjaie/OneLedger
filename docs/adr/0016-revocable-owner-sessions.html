ADR-0016 — Revocable owner sessions and narrow auth bootstrap

Status: Accepted · Date: 2026-09-06 · Refines: ADR-0013 for route exceptions and security-and-privacy.html for session lifetime

Context

ADR-0013 correctly makes the Python service the authorization boundary, but current prose states that every route requires an owner. An OIDC login and callback cannot require the session they exist to create. The security specification also promised short access tokens with rotating refresh while the Phase 0 plan specified one signed 12-hour cookie. A signed cookie alone cannot be revoked before its expiry.

The application remains single-owner. Google authentication proves an external identity; it does not authorize that identity to read this ledger. The local seeded app_user UUID remains the application subject.

Decision

Delivery status. V5 and the strict session issuance/verification core land first. Logout/CSRF and household HTTP routes follow in the next sequential change; OIDC bootstrap follows after that. Routes described below are policy once present, not a claim that deferred routes exist.

The public API surface is limited to GET /health, GET /auth/login, and GET /auth/callback. The two auth routes are narrow bootstrap exceptions and expose no financial data. Login and callback arrive with the Google protocol implementation; until then only health is public. Every other route, including POST /auth/logout and GET /household, requires require_owner().

The service issues an HS256 session containing the local app_user.id as sub, normalized email, iat, exp, cryptographically random jti, and explicit issuer and audience. It lasts 12 hours. There is no refresh token and no silent refresh: expiry requires sign-in again.

Each jti is stored in app_session with its owner and expiry. Every authenticated request requires both valid signed claims and the exact unexpired, unrevoked server record. The joined user must have role = 'owner' and the configured email. Logout revokes that record before clearing the cookie, so replay fails. Cookie-authenticated mutations require an exact Origin match with WEB_ORIGIN; CORS is not treated as CSRF enforcement.

app_user.google_subject is nullable until the first verified login and unique once bound. The Google callback will bind the immutable Google subject without replacing the existing local UUID. That protocol and binding flow are deliberately outside this persistence slice.

Consequences

Good. A stolen or copied cookie can be invalidated immediately. Legacy JWTs without expiry, issuer, audience, local UUID subject, random session ID, or active record fail closed. A future member row cannot establish the owner boundary. Household configuration comes from the authenticated owner's database row and cannot be selected with a browser-supplied household identifier.

Costs. Every authenticated request performs a small indexed database lookup. Sessions require periodic cleanup after expiry, and rotating SESSION_SECRET invalidates every remaining cookie. The owner signs in again every 12 hours rather than receiving a refresh token.

Alternatives considered

Stateless signed cookies. Rejected because logout could only delete one browser's copy; a captured cookie would remain valid until expiry.

Rotating refresh tokens. Rejected for Phase 0 because they add another credential, rotation, reuse detection, and recovery paths to a single-owner application. A bounded 12-hour sign-in-again policy is explicit and testable.

Require owner authorization on the OIDC bootstrap routes. Impossible by construction: those routes create the first local session. Their narrow exception is recorded here rather than hidden in an allowlist.
