ADR-0002 — Freeze both reporting-currency amounts on every transaction

Status: Accepted · Date: 2026-09-04

Context

A household spread across two countries moves money between two currencies constantly, and the rate changes daily. The question that prompted this: "a two-month-old transaction will show a different rate today — which is correct?"

Both, for different questions. Flows must be frozen at the transaction-date rate; balances must translate at the as-of-date rate. If historical flows are re-translated live, last March's spending changes every day and every trend chart becomes partly a chart of the exchange rate.

Given that flows must be frozen, the question becomes: frozen in what?

Decision

Every household configures a reporting pair — household.base_currency and household.secondary_currency. Which two they are is configuration; that there are exactly two is the decision. Store on every transaction:

amount, currency                       immutable original
fx_rate_to_base, fx_rate_to_secondary  frozen at booked_date
amount_base, amount_secondary          frozen, derived once

Both reporting currencies are stored. The currency toggle swaps a column.

No currency code appears in a column name, an enum or a constraint. AED and INR are what the first household happened to choose; a household running EUR and CHF gets the same schema, the same queries and the same toggle, and changes two rows of configuration to get it.

Balances and net worth translate at the as-of date, computed live from fx_rate. The difference between the two treatments is FX translation gain/loss, surfaced as its own line in net-worth attribution rather than absorbed into a residual.

Alternatives considered

Convert on read. Store only the original; translate in every query. Rejected: it makes accidental re-translation of history the default behaviour rather than a bug, and it puts a per-row rate join into every report.

Freeze the base amount only, derive the secondary on read. Half the columns. Rejected because the secondary view would be a second-class derived view of a derived view, and because deriving it from a frozen base value reintroduces exactly the re-translation problem for the secondary toggle.

Pivot currency (freeze one amount in a fixed pivot such as USD, translate from there). Elegant and extends to any number of reporting currencies. Rejected for now: every report becomes a two-hop conversion with a rate join, for a system that has exactly two reporting currencies. The complexity is real and the benefit is hypothetical.

Name the columns after the currencies (amount_inr, amount_aed). Simpler to read in the first household and impossible to reuse in the second. Rejected: it puts a deployment's configuration into the schema, where changing it costs a migration instead of an UPDATE.

Consequences

Good

  • Historical figures are literally immutable. No query can accidentally re-translate.
  • Reporting is a plain SUM() on an indexed column.
  • The toggle is instant, and neither currency is second-class.
  • The FX translation line in attribution reconciles exactly, because the flow and stock treatments are cleanly separated.

Costs

  • Two extra NUMERIC(20,4) and two NUMERIC(20,10) columns per row. Negligible at ~20,000 rows.
  • Adding a third reporting currency requires a backfill migration — add a third column, populate from fx_rate history. A planned one-off, not a surprise. If a third currency ever becomes routine, revisit the pivot-currency alternative in a new ADR.
  • Changing the pair after import is a backfill, not a settings change. The frozen columns are already populated, so switching base currency re-derives every row from fx_rate history. Choose the pair at setup; the UI states this where it is chosen.
  • The importer must compute translations correctly at staging time. Enforced by a Pydantic validator that rejects an inconsistent amount_base.

Correction path. The only circumstance in which frozen values change is a corrected transaction date. That path re-fetches the rate for the corrected date and writes audit_log. Every other write path is blocked by trigger.
