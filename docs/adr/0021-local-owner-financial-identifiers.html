OneLedger architecture decisions

ADR-0021 — Local owner financial identifiers

Status: Accepted — owner direction, 11 September 2026 · Refines: ADR-0012, ADR-0019 · Replaces: the full-identifier prohibition in the security and account-design documents

Context

OneLedger is the owner's private financial application. Its purpose includes showing the owner which institutions, bank accounts and credit cards make up the ledger. The existing policy allowed only masks and matching hashes, so the application deliberately discarded a full account number even when the source statement supplied it. It also made a database-local layout link, rather than the uploaded PDF, the source of institution identity. Those choices prevent the product from presenting and resolving the owner's own accounts as requested.

The policy that must remain absolute is different: real financial data, identifiers, credentials, statement text and documents never enter source control, fixtures, screenshots or published evidence. Application data may live in the owner's database and document store. For this owner-controlled local deployment, application-level encryption creates a more important risk: loss of a separate key could make the owner's own financial history unreadable.

Decision

A complete source identifier is private application data stored as plaintext in the owner's local PostgreSQL database. When a supported PDF states a complete bank-account, IBAN or card identifier, the service retains its source spelling and stores a kind-normalized value for exact matching. OneLedger introduces no application encryption key, key rotation workflow or key-dependent startup. Losing an environment file must never make the ledger unreadable.

The ordinary account representation remains masked. An explicit eye action in the existing owner session returns one stored full value with no-store cache controls; it needs no second password and the browser keeps it only in the active view. The database and its backups can therefore contain readable identifiers. Operating-system disk and backup encryption remain an optional infrastructure choice rather than an application requirement.

A PDF that prints only a mask produces only a mask. The application never invents missing digits and the reveal control explains that the complete value was not supplied. A mask may resolve an existing account automatically only when institution, account type and visible digits identify exactly one household account. Ambiguity stops and asks.

Institution and account identity

Institution and account UUIDs remain the canonical identifiers. A layout captures public issuer branding from the PDF, and household/public alias data resolves that evidence to an institution row. The filename is never evidence. A new account at a known institution is a new account UUID under the existing institution UUID; the institution is not duplicated.

An exact household owner-confirmed alias takes precedence over generic catalogue names and shared aliases for that household. This makes an explicit choice durable without deleting shared evidence; multiple matches within the winning precedence tier remain ambiguous and stop for confirmation.

For a complete identifier, its kind-normalized stored value is the primary account-resolution signal. For a source mask, the unique composite above is a weaker but sufficient signal. A new or conflicting institution/account is shown as one statement-derived confirmation before any record is created or enriched. Editable institution, type, currency and country fields let the owner correct interpretation; the source identifier itself is corrected through the layout rather than replaced with unrelated browser text.

Existing imported documents already identify their account, layout and source through ledger provenance. A guarded application operation may re-read those documents to backfill issuer and complete identity, or correct a legacy source mask, onto the same account while previewing conflicts before any write. A corrected source mask remains unrevealable and never acquires invented digits. It must not infer identity from a filename, narration, balance or transaction description, and direct SQL is not an acceptance path.

Format scope

This decision does not add universal PDF understanding or an embedded AI parser. It applies to the four statement formats OneLedger currently supports. Each layout carries synthetic regression evidence for the public institution capture and account-identity shape. A future bank or a changed PDF format stops as unsupported and receives its own focused layout PR at that time. Once that layout is supported, the same institution, matching and reveal boundary applies without a schema redesign.

The detailed implementation boundary is the local statement identities specification.

Consequences and rejected alternatives

The account schema gains a separately scoped identifier store and institution aliases. The security, data-model, ingestion, API, schema and environment documents must be updated with the implementation; the earlier slice 1.8 mask-only contract is superseded where it conflicts with this decision. Logs, ordinary payloads, URLs, analytics and browser persistence remain identifier-free. Synthetic tests include formatted and Unicode digit variants.

Application-level encryption. Rejected because it adds key generation, storage, rotation, recovery and deployment failure modes to a single-owner local application; losing the key could destroy practical access to the ledger. Re-read the source PDF for every reveal. Rejected because reveal would depend on a retained document, its password and the continued availability of an old layout. Keep mask and hash only. Rejected because it prevents the owner from viewing source data the application exists to manage.
