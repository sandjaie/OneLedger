ADR-0010 — Signed balances; net worth is one SUM

Status: Accepted · Date: 2026-09-04

Context

Assets and liabilities both need balances, and every report has to combine them. Two conventions are available:

  • Signed: assets positive, liabilities negative. net_worth = SUM(balance).
  • Absolute with a class flag: everything positive; subtract liabilities by class. net_worth = SUM(assets) − SUM(liabilities).

Sign confusion in liability handling is, empirically, the most common source of wrong numbers in personal finance software — largely because a sign error is internally consistent and therefore invisible.

Decision

Signed, from the household's perspective, everywhere in the database.

balance > 0    you own it
balance < 0    you owe it

amount > 0     money entered the account
amount < 0     money left the account

This holds for liability accounts without special-casing. A card purchase is −310 (you owe more); a card payment is +3,900 (you owe less).

The display layer flips signs for liability screens — "You owe AED 4,500". The database never does.

Rationale

It makes the two core formulas trivial and universal:

balance   = opening_balance + SUM(amount)     -- every account type, no CASE
net_worth = SUM(balance_in_base)              -- one aggregate, no subtraction

The absolute convention needs a CASE on account_class in every balance query and a subtraction in every net-worth query. Each of those is a place to get the sign wrong, and a wrong sign there produces a plausible-looking number rather than an error.

It makes attribution work without special cases. Loan principal reduction is a positive change in a negative balance. In the signed convention it just adds. In the absolute convention it is a decrease in a subtracted quantity — correct, but requiring a sign flip in exactly the place where sign flips get miscounted.

It matches how transactions naturally read. Money in is positive; money out is negative. The card case, which feels inverted at first, is the same rule applied consistently: a purchase takes value out of your position.

Alternatives considered

Absolute values with a class flag. More intuitive on inspection — a SELECT on a loan table shows 4,000,000 rather than -4,000,000. Rejected: intuition at the row level is worth less than correctness at the aggregate level, and every aggregate would carry a conditional.

Signed in the database, signed in the UI. Fewer moving parts. Rejected: "Home loan: −₹40,00,000" alongside "You owe" reads as a double negative. The flip belongs in presentation, which is where every other formatting decision lives.

Consequences

Good. Net worth is one SUM over one indexed column. Balance computation is identical for every account type. Attribution needs no sign special-cases. The invariant is directly testable (Invariant I2, tested in testing-and-data-quality.html §1).

Costs. A liability row in the database reads as a negative number, which looks alarming before the convention is internalised. Every parser must get card sign handling right — card statements present a purchase as a positive debit, and the ledger stores it negative. This is tested per-parser precisely because the failure is internally consistent and would otherwise be invisible.

Enforcement. account_class is set by trigger from account_type, never by hand. The liability display flip lives in one formatting helper, not scattered across components.
