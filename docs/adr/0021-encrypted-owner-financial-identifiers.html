OneLedger architecture decisions

ADR-0021 — Encrypted owner financial identifiers

Status: Accepted — owner direction, 11 September 2026 · Refines: ADR-0012, ADR-0019 · Replaces: the full-identifier prohibition in the security and account-design documents

Context

OneLedger is the owner's private financial application. Its purpose includes showing the owner which institutions, bank accounts and credit cards make up the ledger. The existing policy allowed only masks and matching hashes, so the application deliberately discarded a full account number even when the source statement supplied it. It also made a database-local layout link, rather than the uploaded PDF, the source of institution identity. Those choices prevent the product from presenting and resolving the owner's own accounts as requested.

The policy that must remain absolute is different: real financial data, identifiers, credentials, statement text and documents never enter source control, fixtures, screenshots or published evidence. Application data may live in the owner's database and document store. Local-first deployment does not justify plaintext backups or broad API disclosure, so a revealable identifier still needs a deliberate storage and access boundary.

Decision

A source identifier is private application data, encrypted at rest and revealable to the authenticated owner. When a supported PDF states a complete bank-account, IBAN or card identifier, the service normalises it, stores an authenticated-encryption envelope and derives a separate keyed fingerprint for exact matching. The ordinary account representation remains masked. An explicit owner-only reveal operation returns the decrypted value with no-store cache controls; the browser keeps it only in the active view.

Encryption and matching use independent keys from the private environment. Development reads them from .env; the isolated local-production stack reads them from .env.production and generates independent values on initialization. Empty placeholders and setup instructions may be committed; key values may not. Envelopes carry a key version so rotation can be planned without changing account identity. Authenticated encryption binds the ciphertext to its household, account, identifier and kind so an envelope cannot be transplanted to another row. It protects a database dump without its environment; it cannot protect a machine compromised while the application and its keys are running.

A PDF that prints only a mask produces only a mask. The application never invents missing digits and the reveal control explains that the complete value was not supplied. A mask may resolve an existing account automatically only when institution, account type and visible digits identify exactly one household account. Ambiguity stops and asks.

Institution and account identity

Institution and account UUIDs remain the canonical identifiers. A layout captures public issuer branding from the PDF, and household/public alias data resolves that evidence to an institution row. The filename is never evidence. A new account at a known institution is a new account UUID under the existing institution UUID; the institution is not duplicated.

For a complete identifier, its keyed fingerprint is the primary account-resolution signal. For a source mask, the unique composite above is a weaker but sufficient signal. A new or conflicting institution/account is shown as one statement-derived confirmation before any record is created or enriched. Editable institution, type, currency and country fields let the owner correct interpretation; the source identifier itself is corrected through the layout rather than replaced with unrelated browser text.

Existing imported documents already identify their account, layout and source through ledger provenance. A guarded application operation may re-read those documents to backfill issuer and encrypted identity onto the same account, previewing conflicts before any write. It must not infer identity from a filename, narration, balance or transaction description, and direct SQL is not an acceptance path.

Format scope

This decision does not add universal PDF understanding or an embedded AI parser. It applies to the four statement formats OneLedger currently supports. Each layout carries synthetic regression evidence for the public institution capture and account-identity shape. A future bank or a changed PDF format stops as unsupported and receives its own focused layout PR at that time. Once that layout is supported, the same institution, matching and reveal boundary applies without a schema redesign.

The detailed implementation boundary is the encrypted statement identities specification.

Consequences and rejected alternatives

The account schema gains a separately scoped identifier store and institution aliases. The security, data-model, ingestion, API, schema and environment documents must be updated with the implementation; the earlier slice 1.8 mask-only contract is superseded where it conflicts with this decision. Logs, ordinary payloads, URLs, analytics and browser persistence remain identifier-free. Synthetic tests include formatted and Unicode digit variants.

Store plaintext identifiers. Rejected because every database dump or accidental broad query would expose immediately usable numbers. Re-read the source PDF for every reveal. Rejected because reveal would depend on a retained document, its password and the continued availability of an old layout. Keep mask and hash only. Rejected because it prevents the owner from viewing source data the application exists to manage.
