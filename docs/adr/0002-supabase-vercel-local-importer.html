ADR-0002 — Supabase + Vercel + local Python importer

Status: Superseded by ADR-0018 · Date: 2026-09-04

Context

Hard constraint: zero infrastructure spend. Free tiers only, localhost first, cloud eventually.

The original sketch was a conventional three-tier system: Next.js → hosted FastAPI → PostgreSQL. The interesting question is where the statement parsing runs, because parsing is by far the heaviest thing the system does — large PDFs, table extraction, unbounded runtime — while everything else is light.

There is also a secondary goal: this should be a real Python learning project, not a thin wrapper.

Decision

Three components:

  1. Next.js on Vercel — the app, reading Supabase directly from Server Components.
  2. Supabase — Postgres, Auth (Google), and Storage. The single source of truth.
  3. A local Python importer — a CLI on your own machine that parses statements and writes staged rows.

No hosted API server.

Alternatives considered

Hosted FastAPI on a free tier (Render, Koyeb, Fly). Truest to the original sketch, and accessible from anywhere. Rejected because free tiers sleep after inactivity — a 30–60 second cold start on the first request of the morning, on the screen meant to be glanced at — and because ~512 MB of RAM makes large PDF parsing genuinely fragile. It also puts every bank statement through a third-party host for no benefit, and has a clear path to eventually costing money.

All TypeScript, no Python. One language, one deploy, simplest operationally. Rejected because it abandons the Python learning goal and because pdfplumber and pandas have no real equivalent in the JavaScript ecosystem. Statement parsing is exactly the domain where Python's libraries are meaningfully better.

Local-only desktop app. Maximum privacy, no hosting at all. Rejected because the daily dashboard should be reachable from a phone, and a desktop app makes that a sync problem.

Consequences

Good

  • No cold starts. The dashboard is a static-rendered page over a fast database.
  • No execution ceiling on parsing. A 200-page CAS is fine.
  • Statements are parsed entirely on your own machine — a real privacy gain, not a theoretical one.
  • Debugging a parser is a breakpoint, not a deploy-and-read-logs cycle.
  • Free permanently, with no upgrade cliff.
  • The importer is where the substantial Python lives: Pydantic models, a parser registry, a rules engine, a matching algorithm, XIRR. More interesting than a CRUD API.

Costs, stated honestly

  • Imports require the machine with the importer installed. For a monthly batch operation this is close to free, but it is a real constraint.
  • Two deployment stories: git push for the web app, uv sync for the importer.
  • The service-role key lives on a laptop, making full-disk encryption a requirement rather than a suggestion.

Reversibility. The importer is a library behind a CLI. Putting an HTTP handler in front of it later — when hosting is affordable — is a small addition, not a rewrite. That is the test this architecture is designed to pass: the same architecture, smaller, rather than a different one that must be replaced.
