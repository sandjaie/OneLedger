ADR-0015 — Flyway for schema migrations

Status: Accepted · Date: 2026-09-05 · Revises: architecture.html §4 (its "plain SQL, forward-only" row)

Context

The specification settled on plain, numbered, forward-only SQL and rejected "ORM migration magic over a schema this deliberate". That judgement was about ORMs — about a tool that generates DDL from model classes and hides what it is doing. It was not an argument against a migration runner, and the difference matters, because the plan quietly assumed a runner existed: Task 1 lists scripts/migrate.sh among the files to create, and no step in the document ever says what goes in it.

So the real question was never "tool or no tool". It was "write the runner, or take one".

A runner has to do four things: apply pending files in order, record what it applied, refuse to apply a file that changed after it ran, and be safe to run twice. The fourth is easy. The third is the one people get wrong when they write it themselves, and it is the one that catches a migration edited in a pull request after it had already run on someone's machine.

Decision

Flyway runs the migrations. Pinned to flyway/flyway:13.5.0-alpine, as a service in the same compose file that already carries db, api and web (ADR-0014). Migrations keep living in db/migrations/ and stay plain SQL; only the naming changes to Flyway's convention.

db/migrations/V1__extensions_and_reference.sql
db/migrations/V2__identity_and_rls.sql
db/migrations/V3__accounts.sql
db/migrations/V4__fx_rates.sql

db/tests/0001_reference.sql        assertions, not migrations — deliberately not V-named

The invariant tests keep their numeric names. That is not an inconsistency: a file Flyway would run and a file that asserts what Flyway produced should not be one typo apart, and the naming difference makes them impossible to confuse.

Rationale

Checksums are the feature. Flyway records a hash of every applied migration and refuses to proceed when one changes underneath it. For a forward-only schema this is the guardrail that matters most — editing an already-applied migration is exactly the mistake that produces two databases with the same version number and different shapes, and it is invisible until something breaks in production.

It is one container, not a dependency. Nothing is added to the Python service, no library enters pyproject.toml, and the migrations remain readable SQL that a DBA could apply by hand if Flyway vanished tomorrow. The coupling is a file-naming convention.

The alternative was writing it. scripts/migrate.sh would have been perhaps forty lines that apply files in order and record them in a table — and then, over time, the forty lines that handle a partially-applied file, and detect a checksum change, and support a dry run, and print what is pending. That is a migration runner, badly, maintained by someone who wanted a ledger.

Cost is zero. Flyway OSS Edition covers versioned migrations against PostgreSQL, which is the whole of what this needs. No licence, no account, consistent with ADR-0014's spending constraint.

Alternatives considered

A hand-written scripts/migrate.sh. Fewest moving parts on day one, and it is what the plan implied. Rejected on the checksum argument above: the version of this script that is actually safe is not small, and nothing about this project makes writing it interesting.

Alembic. Already in the Python ecosystem and familiar. Rejected: its value is autogenerating migrations from SQLAlchemy models, and this schema has no ORM models to generate from (data-model.html is the source of truth, by hand). Taking Alembic would mean carrying a dependency for the one feature deliberately not wanted.

Liquibase. Comparable capability. Rejected: its native idiom is XML/YAML changelogs, and the plain-SQL path is the less-travelled one. Flyway's native idiom is a directory of .sql files, which is what already exists.

sqitch. Genuinely good, and its dependency graph beats linear versioning for large teams. Rejected as solving a coordination problem a single-author repository does not have, at the cost of a Perl toolchain in the stack.

Consequences

Good. An applied migration cannot be silently edited. flyway info answers "what state is this database in" without anyone inventing a convention for it. A fresh clone reaches a working schema with one command, and CI does the same thing the laptop does.

Costs. A JVM container in the stack — pulled once, run on demand, absent at runtime. And a naming convention that must be respected: V5__… comes after V4__…, and renaming an applied file breaks its checksum exactly as editing it does.

Verify before implementing. Flyway 13.5.0 was confirmed on 2026-09-05 to connect to Postgres 18.4 and read its schema. A migration was not observed applying end to end — the probe could not mount its SQL directory — so Phase 0 PR 1 must prove flyway migrate works against Postgres 18 before anything is built on it, and treat a failure there as a reason to revisit this decision rather than to work around it.
