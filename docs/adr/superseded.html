Decisions we changed before building

Nothing on this page is part of the system. These four decisions were made and then replaced, all of it before a line of application code existed. They are summarised here rather than kept as four separate documents, because a repository where half the decision pages describe an architecture that was abandoned is a repository that misleads on sight.

They are kept at all because a decision with no visible history looks arbitrary, and an arbitrary decision gets re-litigated. If someone asks "why not just use Supabase", the answer should be findable. What follows, for each: what was decided, what replaced it, and the part of the reasoning that is still worth having.

Once implementation starts, this stops being the right shape. A decision reversed after code depends on it needs its own record, with its own migration story — the way the ADRs in force are written.

Supabase + Vercel + a local Python importer

Decided 04 September 2026. Replaced by ADR-0013 and ADR-0014.

Three components: Next.js on Vercel reading Supabase directly from Server Components, Supabase for Postgres, Auth and Storage, and a local Python CLI that parsed statements on the user's own machine.

What drove it: a hard requirement of zero infrastructure spend. Free tiers only. Every component was chosen because it had one, and the shape of the system followed from that.

Why it went: the free-tier constraint turned out to cost more than it saved. It bought a Supabase project that pauses when idle, a storage ceiling, a keepalive cron to work around the pause, and vendor coupling to Auth, Storage and auth.uid() that would have to be unpicked the first time anything moved. ADR-0014 priced the alternative at roughly $5–12 a month for one VPS running the whole stack from one compose file, and the entire class of problem disappeared.

What survived: the privacy property. Statements are parsed by software running on a machine you control and reach no third party — that was its real argument for a local importer, and it holds today for a different reason (the machine is yours because the whole stack is).

24 months of history

Decided 04 September 2026. Replaced by ADR-0011.

Import the current year plus the prior year, with manually entered opening balances anchoring the window.

The reasoning, which mostly survived: 24 months is where trends become real — year-on-year comparison for every month, a seasonal cycle twice over, a net-worth curve with a shape. Parser effort rises sharply further back, because banks revise layouts every few years and five years can mean three layout versions per institution. Manual opening balances are honest and cheap: about fifteen numbers, entered once.

Why it went: the horizon moved to 36 months anchored at 01 January 2024, which is a calendar boundary rather than a rolling window. The parser-effort argument was weighed again and found acceptable for one more year. Everything else about the decision is unchanged, which is why ADR-0011 reads as an amendment rather than a reversal.

Classification and transfer matching in Postgres

Decided 05 September 2026. Replaced by ADR-0013, the same day.

One implementation of each, as Postgres functions — match_classification_rules(txn) and score_transfer_candidates(txn) — called over RPC by the importer and by the web app.

The problem it was solving is real and still is: the classification cascade and the transfer matcher were otherwise specified to exist twice, once in the importer and once in the app. What gets duplicated is the hardest semantics in the product — priority ordering, "every non-null condition must match", the FX-aware amount tolerance — and those are exactly what gets subtly mis-copied.

Why it went: the duplication existed because there were two clients. When ADR-0013 made the Python service the only thing that touches the database, there was one implementation again by construction, and it could live in the language with tests, a debugger and types. The requirement — one implementation — is unchanged; only its address moved.

Parse statements in the browser

Decided 05 September 2026. Replaced by ADR-0013, the same day.

Parse PDFs with pdf.js in a Web Worker, and retire the Python importer entirely. Its case: the browser is the local machine, so the privacy property that decision was protecting is preserved exactly — arguably strengthened, since the bytes never leave the page context and no local process holds decrypted content on disk.

Why it went: the same day, the objection that importing should be part of the web UI was met a different way. ADR-0013 put a Python service behind the UI, which keeps importing in the browser as an experience while parsing happens in a language with a real debugger. Parsing returned to pdfplumber.

The measurement worth keeping

The browser-parsing ADR originally presented the cost of choosing pdf.js as the loss of what pdfplumber gives "for free". Tested against the actual statements, that was overstated. On the encrypted, space-less layout — the hardest of the four — pdfplumber recovers no more than pdf.js does:

extract_text()  → PageNo.:1 Statementofaccount
extract_words() → ['PageNo.:1', 'Statementofaccount', 'AccountBranch', ':',
                   'PERUMBAKKAMNOOKAMPALAYAMROAD', 'HDFCBANKLTD,FIRSTFLOOR,MALLES']

The producer emits no space characters and the glyph runs are contiguous, so there are no gaps to split on in any language. What actually resolves all four layouts is column banding by x-position, which is language-neutral and is what ADR-0012 specifies.

This matters beyond the decision it was written for: it is the reason ADR-0013 does not claim pdfplumber as a parsing-capability win. The honest advantages of Python here are spreadsheet parsing, OCR and extract_table() for ruled tables — none of which this product needs.
