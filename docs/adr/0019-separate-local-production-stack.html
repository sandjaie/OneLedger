OneLedger architecture decisions

ADR-0019 — Separate local production stack

Status: Accepted · Date: 2026-09-10 · Refines: ADR-0014

Context

The default Compose project is the development and acceptance environment. Its ledger holds working data and must remain available while production-built images are exercised locally. Reusing that database, its ports or its volumes would make a clean start destructive or leave production behavior dependent on test and imported data.

Decision

A second file, docker-compose.production.yml, always runs as project oneledger-production. It binds web, API and database to loopback ports 3100, 8100 and 55432. It owns the exact external volumes oneledger-production_pgdata and oneledger-production_documents; the default and test stacks never name them.

scripts/production-stack.sh is the lifecycle boundary. Its first initialization creates a mode-600, git-ignored .env.production with independent generated secrets. Startup builds application images, migrates the database, idempotently creates exactly the configured owner, then waits for healthy API and web services. It seeds no financial, import or mock data.

Ordinary down preserves both external volumes. Destructive reset requires the exact argument --confirm oneledger-production, brings down only that project and removes only the two literal production volume names. No wildcard, inferred Compose volume or development name participates.

This stack uses the loopback-only local session mode from ADR-0018. It is a local production-build rehearsal, not the hosted topology. Public deployment remains a separate planned change that adds TLS and selects Google authentication explicitly.

Alternatives considered

Use Compose profiles in the default file. Rejected: shared defaults and implicit project-derived volume names make it too easy for an operator command to address the working ledger.

Use an ephemeral clean database. Rejected: local production is meant for normal use before cloud deployment, so its ledger and original documents must survive teardown and machine restarts.

Copy the development environment file. Rejected: shared database, session, hash and backup secrets couple two security boundaries and make later rotation ambiguous.

Consequences

Both stacks can run concurrently and be recognized by their fixed ports and project names. The local-production ledger starts empty but persists intentionally. A reset is more verbose by design. Cloud deployment cannot happen by exposing this file unchanged; its authentication, origin and TLS decisions must be made explicitly.
