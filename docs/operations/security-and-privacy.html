09 — Security and Privacy

This database contains an entire financial life: every transaction, every balance, every institution, net worth, salary. Security is a product requirement, specified before auth is wired — not hardened later.

The strongest control available is also the simplest: the system never holds credentials that can authorise a financial action, and real financial data never enters source control or published evidence.

1. The storage boundary

The distinction is between credentials that can control an asset and private application data the owner expects OneLedger to manage. The first list is absolute. The second is permitted in the owner's local database under ADR-0021.

✗  Bank passwords or PINs
✗  Internet banking credentials
✗  Card CVV                            — never, in any form
✗  UPI PINs
✗  OTPs
✗  Full PAN / Emirates ID / passport   — last 4 only, for reference
✗  Statement PDF passwords in database — private environment/request only

Local private application data when a source supplies it:
✓  Bank account number                 — masked by default; owner-revealable
✓  IBAN                                — masked by default; owner-revealable
✓  Credit card number                  — only the digits the source actually provides

No account/card identifier, statement text, transaction, amount, credential or real financial example enters source control, a fixture, screenshot or published report. Complete identifiers are stored as plaintext in local PostgreSQL so they remain readable without a separate application key. The database and its backups must therefore be treated as private financial data.

Historical identity backfill previews are owner-only and read-only. They select stored PDFs only through completed import provenance, reject an original that fails its local path, symlink or SHA-256 check, and hold an optional PDF password in the request frame only. Their ordinary response contains safe UUIDs, fixed reason codes, counts and a stale-state digest; it contains no filename, storage path, statement capture, narration, amount, institution name or complete identifier. Apply takes the household lock, reproduces that exact preview from the stored sources and refuses stale or disagreeing evidence before writing. It stores a complete identifier only through the shared statement-provenance writer; no backup or encryption-key check gates the owner's local data.

Even a full application compromise must not provide a password, PIN, CVV or OTP capable of moving an asset. Read exposure is still serious, which is why ordinary views remain masked and reveal is an explicit owner-only operation.

2. Threat model

Honest about what a personal single-user system faces.

The two highest real-world risks are laptop theft and data loss — not exotic attacks. Both are addressed by unglamorous measures that are easy to skip and shouldn't be.

3. Authentication

One authorization boundary, with local and Google login modes. No application password, ever. ADR-0018 adds a loopback-only local bootstrap while retaining Google OIDC for a public deployment.

  • No signup flow. No public registration. No invitation system. No password reset.
  • The allowed account is pinned by email in configuration; any other Google account authenticating is rejected by the service even though Google authenticated it successfully.
  • MFA is inherited from the Google account, where it should live.

In AUTH_MODE=local, which is accepted only with an HTTP loopback WEB_ORIGIN, GET /auth/login resolves exactly one configured owner and issues the same persisted, revocable session described below. It does not bypass require_owner, RLS, household scoping or the exact-origin mutation check. Application code defaults to AUTH_MODE=google, so a copied public configuration fails closed.

Login uses authorization code flow with random state, nonce and PKCE S256. The signed flow cookie is HttpOnly, SameSite=Lax, valid for ten minutes and Secure when COOKIE_SECURE=1. Callback checks that cookie and state before any token exchange, then verifies the ID token's RSA signature with Google's JWKS, documented issuer, configured audience, expiry, nonce, nonempty subject and boolean verified-email claim. The authorization request fixes prompt=select_account so retrying after a denied account offers the chooser instead of silently reusing that Google session. Google discovery and JWKS are not fetched at startup.

The verified normalized email must match exactly one seeded owner. A single conditional update binds the Google subject only if its stored value is null or already equal, so ambiguous rows and competing different subjects fail closed. The seeded local UUID remains the application session subject.

# Every authenticated route, in the service
def require_owner(session: str = Cookie(default="")) -> OwnerSession:
    claims = verify_signed_claims(session)    # 401 if absent; 403 if forged or expired
    owner = lookup_active_owner_session(claims["sub"], claims["jti"], claims["email"])
    if owner is None:
        raise HTTPException(403)
    return owner

Where authorization actually happens

Google will authenticate any Google account. Authentication is not authorization, and a redirect to /unauthorized is a page-level control, not a wall.

The API service is the authorization boundary (ADR-0013). Sign-in verifies Google's id_token against Google's JWKS and checks the address against ALLOWED_USER_EMAIL; the service then issues its own signed, HttpOnly session cookie. Every request resolves that session to an unexpired, unrevoked app_session row joined to the owner app_user, and rejects with 403 if there is none. Every query it issues is scoped to that household explicitly.

This is a weaker guarantee than what it replaces, and the change is deliberate. Under browser parsing a forgotten WHERE clause returned nothing, because RLS was the boundary. Now it would return another household's rows — in a system that has one household and is permanently single-tenant, but the property is genuinely lost, not merely relocated.

What still holds:

Surface What stops an unpermitted authenticated caller
Household-scoped tables RLS stays enabled as defence in depth. The service connects with the service-role key and so bypasses it — but the policies remain correct, and any future client connecting as a user is protected by them
Every API request Session cookie verified; it must resolve to an active, unexpired and unrevoked app_session row joined to an owner app_user, and the normalized address must match the pinned one. A stranger who signs in with Google gets 403 from every route
Cookie-authenticated mutations In addition to the owner session, every POST, PUT, PATCH and DELETE carrying a session cookie must send an exact Origin header matching WEB_ORIGIN. CORS is not treated as CSRF protection
Reference tables (fx_rate, currency, price_snapshot) RLS enabled with a SELECT-only policy. No write policy exists, so writes are denied to every role
SECURITY DEFINER functions Each calls assert_is_owner() first, which raises 42501 unless app.user_id resolves to a row in app_user
The documents volume Not web-served. Originals are streamed by a route that checks the session first, so no URL works without one

current_household_id() is deliberately exempt from assert_is_owner(): returning NULL for an unknown caller is the correct behaviour, and it is what every policy depends on.

The test that proves this is not "sign in as the wrong account and check the redirect". It is: obtain a JWT for a second Google account and call every API route directly with it, asserting 403 on all of them — including the ones that only read. That is a Phase 0 exit item, and it matters more now than it did under RLS, because the service is the only thing in the way.

Why no signup is a security control, not a shortcut: registration, invitation and password reset flows are where a large share of authentication vulnerabilities live. Not building them removes the class entirely. This is the single biggest advantage a single-user system has, and it would be careless not to take it.

Session: a signed 12-hour JWT in a secure, httpOnly, sameSite=lax cookie, backed by an unexpired and unrevoked app_session row. There is no refresh token or silent refresh; expiry requires sign-in again. Sign-out revokes the exact server record before clearing the cookie, so replay of the old cookie fails. Cookie-authenticated mutations require an exact Origin match with WEB_ORIGIN. See ADR-0016.

Callback errors clear the transient cookie and redirect only to the configured web origin. Identity denial uses the unauthorized page; recoverable failures use one generic login reason. Codes, tokens and raw exceptions are absent from responses. The shipped API command disables raw Uvicorn access logs because callback request targets contain authorization codes. Use uv run uvicorn oneledger.main:app --reload --port 8000 --no-access-log locally as well.

4. Account number handling

Statements must be matched to accounts and the owner must be able to inspect the source identity. Under ADR-0021, a complete identifier retains its source value and a normalized exact-match value in the local database. A mask remains the ordinary display value.

api/oneledger/identifiers.py is the sole value boundary. It validates each identifier kind, retains the trimmed source spelling when complete, converts Unicode decimal digits to ASCII, removes permitted visual separators, uppercases ASCII letters for matching, and derives only the safe mask and visible suffix from explicitly declared mask-only evidence. Capture completeness is not guessed from letters such as X, because those are also legal identifier characters. General serialization of a complete value exposes only its safe presentation; its value object, representation and validation errors do not render the complete identifier. The module performs no database I/O and reads no environment state.

No identifier encryption key exists. Ordinary account payloads return only the mask; the explicit owner-authenticated POST /accounts/{accountId}/identifiers/{identifierId}/reveal route may return one complete stored source identifier. Its successful responses carry Cache-Control: no-store and Pragma: no-cache. A source that printed only a mask returns source_mask_only; OneLedger never manufactures its missing characters.

The same treatment applies to PAN, Emirates ID and passport numbers — last four for human recognition, nothing more.

5. Data protection

Layer Control
In transit TLS everywhere. HSTS. No plaintext HTTP anywhere in the stack
At rest — database Owner-selected host controls; volume encryption is recommended but not required by OneLedger
At rest — storage Documents on a Docker volume, served only through the service — never by a static path
At rest — local Owner-controlled machine; FileVault / LUKS / BitLocker is recommended but is not an application gate
Access RLS on every household-scoped table
Document access Served by the service, per request, after authorization. No public path exists
Backups Treated as private financial data; encryption is recommended but remains the owner's choice

Row Level Security

Enabled on every household-scoped table from Phase 0, even with one user:

ALTER TABLE transaction ENABLE ROW LEVEL SECURITY;

CREATE POLICY household_isolation ON transaction
  USING (household_id = current_household_id());

Three reasons this is not premature:

  1. A forgotten WHERE clause returns nothing instead of everything — for any connection that is not the service's own.
  2. It is a second wall behind the service's authorization, at a cost of one USING clause per table. Since ADR-0013 the service connects privileged and bypasses these policies, so they are depth, not the boundary.
  3. The policy is already correct on the day a second person is added, rather than being retrofitted across forty tables.

Verified by a test that queries every table as an unauthenticated role and asserts zero rows.

6. Secrets

Secret Location Rotation
NEXT_PUBLIC_API_URL Public by design — the browser has to know where the API is. The only NEXT_PUBLIC_ variable, and it holds a URL With the deployment
SESSION_SECRET The service's mode-600 environment file. Local production generates a separate .env.production. It signs the session cookie — anyone holding it can mint a valid session Immediately if exposed; this invalidates every session
DATABASE_URL · POSTGRES_PASSWORD The service's environment file; local production generates its own credentials. This is the application's own connection, and it is privileged enough to bypass RLS Immediately if exposed
Google OAuth client secret The service's .env, mode 600 If exposed
ACCOUNT_HASH_SALT The service's .env, with a copy in a password manager — losing it is unrecoverable Never — rotation invalidates all hashes
PDF passwords Typed into the import form; held in memory for the parse only Never stored, so never rotated
Optional backup encryption key Owner-selected storage when backup encryption is enabled According to the owner's backup policy

Controls

  • .env and .env.production are git-ignored; .env.example and .env.production.example document variables with placeholder values. The production lifecycle script creates the real file with mode 600 and independent generated secrets.
  • The local-production project publishes only to loopback, uses exact external volume names, and can erase them only after reset --confirm oneledger-production. Normal down preserves them (ADR-0019).
  • Pre-commit hook (gitleaks or equivalent) scans staged changes for key-shaped strings.
  • CI fails on a detected secret.
  • No secret is ever prefixed NEXT_PUBLIC_. A lint rule enforces this — the prefix is what would silently ship one to the browser.

7. Audit log

Append-only, capturing everything that changes financial data.

Logged:  create · update · delete on transaction, account, transfer, loan, holding,
         valuation_snapshot
         import batches and their outcomes
         rule creation and bulk applications
         sign-in and sign-out
         document upload, download, deletion

Stored:  actor · action · entity · before (JSONB) · after (JSONB) · timestamp

The application role has INSERT only — no UPDATE, no DELETE. Written by trigger, so it cannot be bypassed by forgetting to call a logging function.

It answers "why is this transaction categorised this way and who changed it" six months later, which matters more in practice than intrusion detection does for a system of this size.

8. Privacy

No financial data leaves your infrastructure in Phase 1 or Phase 2.

  • No analytics. No telemetry. No error-reporting service receiving payloads.
  • No third-party scripts on any page rendering financial data.
  • No CDN-hosted fonts that would leak page visits — fonts are self-hosted.
  • The only outbound network call is the FX rate fetch, which sends nothing but a date range.

Logs never contain amounts, balances, account numbers or descriptions. Importer logs reference row numbers and hashes, not content — so a log file pasted into a bug report leaks nothing.

V2 changes this, which is exactly why AI is deferred rather than half-built. Any LLM integration requires an explicit decision recorded in an ADR, covering: what is sent, what is redacted, what is retained by the provider, and whether it can be turned off per-import. That decision is not made in this document, and not made implicitly by shipping a feature.

Planning records and owner exports

Goals, insurance coverage, expected receipts, nominee-review metadata and actions are financial data and use the same owner authorization and log-redaction rules as the ledger. Store only metadata allowed by the storage boundary; a policy register does not justify a financial-action credential. A complete source financial identifier is stored only when the product needs to match or show it, through ADR-0021's household-scoped identifier relation rather than an arbitrary text field.

Owner exports are delivered through authorized routes, contain only selected records and documents, and omit secrets. Temporary archives must not be publicly served and must be removed after a bounded retrieval period. Record the export event without logging financial contents. A downloaded archive requires the same local protection as statements.

Emergency handover remains a separate unapproved access feature. No trusted-person login, shared link, advisor delivery or outbound reminder containing financial data is introduced by the product review.

9. Backups

Restated here because data loss is the most likely serious failure and the least exciting to prepare for.

Daily     pg_dump → encrypted → local disk               30 days retained
Weekly    documents volume → local disk                  4 weeks retained
Monthly   Both → second physical location                12 months retained
Quarterly RESTORE TEST → scratch database                verified, not assumed

The daily row is taken by the compose backup service, not by anyone remembering, and Settings › Data Quality says when it has not been (architecture.html §10). Retention never drops below the thirty newest, so after a reset the last good backups survive at least thirty further dumps of an emptied database — a month of daily ones — not indefinitely.

The quarterly restore test is a checklist item in testing-and-data-quality.html. A backup that has never been restored is a hypothesis.

Keep ~/statements/ outside the repository as a second copy of the source data: the ledger is reconstructible from originals if it ever comes to that. That is a further argument for keeping parsers deterministic and versioned.

10. Incident response

Small system, short plan — but written down, because the moment to work it out is not during.

Database credentials exposed

  1. Rotate the database password and the session secret immediately.
  2. Update the .env on the box and restart the stack.
  3. Review audit_log for unfamiliar activity.
  4. Rotate the account-hash salt only if the database itself was accessed (this requires re-hashing every account number).

Laptop lost or stolen

  1. Invalidate all sessions by rotating SESSION_SECRET.
  2. Rotate the database password.
  3. If full-disk encryption is enabled, follow the operating system's recovery process.
  4. Change the Google account password and review its active sessions.

Repository accidentally made public

  1. Make private; assume anything committed is compromised.
  2. Rotate every secret regardless of whether one appears in the history.
  3. Verify no real statement or fixture containing real data was ever committed — a history scan, not a glance at HEAD.

Data corruption discovered

  1. Stop importing.
  2. Identify the batch via import_batch and audit_log.
  3. Restore to a scratch database, compare, and correct forward with an adjusting entry rather than editing history.
