12 — Testing and Data Quality

A financial tool fails differently from most software. It rarely crashes — it produces a number that is quietly wrong, and you believe it.

So the tests that matter are the ones that assert the invariants (prd.html §4), not the ones that assert a button renders.

1. The invariant test suite

Eight tests. If any fails, the ledger cannot be trusted, and no feature work proceeds until it passes.

InvariantWhat the test must prove
I1 originals immutableUPDATE of amount or currency raises.
I2 signed balancesA savings account at +100,000, a card at −4,500 and a home loan at −4,000,000 sum to −3,904,500 with no CASE and no subtraction.
I3 transfers excludedConfirming a remittance drops spending by exactly the source amount; rejecting it restores the figure. Proves the exclusion is live, not assumed.
I4 card payment not double-countedA −310 purchase and a +3,900 payment yield spending of exactly 310.
I5 historical flows frozenMove the rate table by a large step after import; the March figure is byte-identical.
I6 provenanceNo row with source = 'statement_import' has a null source_document_id.
I7 derived values labelledA Sunday import carries fx_rate_is_carried = true and an fx_rate_date earlier than its booked_date.
I8 reconciliation blocksA statement with one row dropped raises ImportBlocked and stages zero rows.

Test source: test-suite.md.

2. Static checks

Some invariants are better enforced by refusing to compile than by testing at runtime.

Three checks are enforced by refusing to build rather than by testing at runtime: no reporting function may read the base transaction table instead of v_transaction_reportable (I3); no query may multiply amount by a rate rather than reading a frozen column (I5); and no money value may pass through parseFloat or Number(), which is the likeliest way precision is silently lost. All three are rules in scripts/check-identifiers.py, run by the commit hook. The first two read SQL where it lives — inside string literals — and guard product code, not tests. Each says what it allows as well as what it refuses: a handful of files read the base table on purpose (the ledger listing, import, classification, transfer matching, account balances), each named in the script with its reason; and a balance times today's rate is allowed everywhere, because a balance is a position translated as of now and only a flow is frozen (ADR-0002).

Check source: test-suite.md.

Lint rules

Rule Enforces
No NEXT_PUBLIC_ on any secret-shaped variable No secret ships to the browser
No parseFloat / Number() on a money field No float money anywhere
No string-interpolated SQL Injection surface
mypy --strict on the service Contract integrity
Parsers may not import from lib/queries Parsing stays pure and unit-testable without a database

3. Parser tests

Parsers are the most fragile component — they depend on a third party's layout choices.

Golden fixtures

api/tests/fixtures/
├── uae-card/
│   ├── skywards_2026_01.pdf               redacted
│   ├── skywards_2026_01.expected.json
│   └── README.md                          what real statement this reproduces
├── uae-current/
├── axis/
└── hdfc/                                  encrypted fixture + its test password

The HDFC fixture is redacted and re-encrypted with a throwaway password committed beside it. The real password never enters the repository.

Each fixture asserts row count, every date and amount, opening and closing balance, and successful reconciliation. A layout change breaks the test loudly, which is the point.

Fixtures are redacted. Real statements never enter the repository — not in main, not in a branch, not in history. Redaction keeps layout, column positions and formatting; it replaces amounts, dates, account numbers and merchant names. The README.md in each directory records provenance so a future layout change can be diagnosed.

Property-based tests

hypothesis generates the awkward cases — zero amounts, extreme values, boundary dates — more reliably than hand-written examples. Two properties hold for any generated input: a parsed statement's opening balance plus the sum of its rows equals its declared closing balance, and a normalized transaction's amount_base equals its amount times its stated rate, to four decimal places.

4. Financial calculation tests

Verified against independent implementations, not against the code's own output.

Calculation Verified against Tolerance
XIRR Spreadsheet XIRR() on the same cash flows 0.01%
Amortisation The lender's own schedule 1 currency unit
FX spread cost Hand computation Exact
Net worth attribution Components + residual = actual delta Exact
Acquisition position Hand-derived units × accepted non-future price, against frozen contributions Exact to the stored money scale
Investment net worth Ledger, holdings and snapshot mode fixtures before and after a dated transition Exactly one source in both reporting currencies
Month-end positions Stored ledger balance against assert_account_reconciles' own figure (including a row booked on the opening date); a closed account keeps the months it was open; a holding valued with the month-end price and rate, fully sold to zero; a snapshot carried forward and translated at each month's own rate; a refresh replayed twice is identical, and a failure partway through leaves the previous rows intact (Phase 2.2 Task 1) Exact to the stored money scale; a late failure changes nothing
Savings rate Hand-tallied month Exact
Utilisation The card statement Exact

XIRR is verified against an independent computation, not against its own output. For 24 monthly outflows of 10,000 from 2024-09-01 and a 268,400 terminal inflow on 2026-09-01, the answer is 0.111228 — NPV at that rate is 0.00, and at 0.1428 it is −6,328.45. A second case uses irregular flows with interleaved redemptions, on which Newton–Raphson alone diverges, to prove the bisection fallback engages: a silent null there would render as a blank XIRR that reads as missing data rather than a failed solve.

The irregular-flow case is included specifically because Newton–Raphson diverges on some real SIP series with interleaved redemptions. A silent None there would show a blank XIRR that looks like missing data rather than a failed solve.

Three properties make this useful rather than noise:

  1. It names the probable cause. A residual and a missing statement are shown as connected.
  2. It distinguishes expected from wrong. 218 carried-forward weekend rates is ℹ, not ⚠.
  3. It runs automatically after every import, so problems surface while the context is fresh.

The COVERAGE block above is GET /doctor's Coverage section (api-contracts.html §2, Phase 2.1 Task 1): one warning per row with a missing or partial month, naming the account or Payslips and its earliest gap month, or one ok finding when every row is reconciled or acknowledged.

6. Test pyramid

Level Count Runtime Scope
Invariants 8 < 5 s The eight product invariants. Block everything on failure
Unit ~200 < 30 s Extraction, normalization, dedupe hashing, FX freeze, XIRR
Parser golden 4+ < 20 s One fixture per layout, exact output
Property ~15 < 60 s Reconciliation, FX consistency, sign handling
Database ~40 < 45 s RLS, constraints, triggers, views, and the two matching functions
Integration ~30 < 2 min Full pipeline against local Postgres
E2E ~10 < 3 min Import → review → commit → dashboard, Playwright

Database tests cover constraints, triggers, views and RLS. ADR-0013 moved the rules engine and the transfer matcher into Python, so their tests are ordinary unit tests — which was one of the reasons for that decision.

Target: the full suite under five minutes, so it is actually run.

Delivery gates: commit and push hooks run fast static checks only. Application tests, migrations-from-empty and SQL invariants run during implementation and the required local /verify gate. The full CI workflow remains available as an owner-triggered remote mirror. Migrations are verified by applying all of them to a fresh database and diffing the result against the schema snapshot — a migration that drifts from the documented schema fails.

7. Manual verification

Some things are only provable against reality.

Per milestone

  • Import a real statement. Reconcile. Compare a handful of rows against the PDF by eye.
  • Compare a computed balance against the bank's app.

Monthly

  • Compare monthly spending against a hand tally for one category.
  • Confirm net worth against a manual sum of account balances.
  • Clear Settings › Data Quality warnings, or record why one is acceptable.
  • Run scripts/restore-drill.sh against the isolated test server and confirm it passes. A backup that has never been restored is a hypothesis.

Quarterly

  • Work the security checklist (security-and-privacy.html §11).
  • Review rule health: unused rules, frequently-overridden rules, shadowed rules.

Product outcomes and scenario gates

The P01–P12 scenarios supplement the eight ledger invariants. They are planned acceptance gates, not claims that tests already exist in Phase 0.

  • Phase 1.3 / Phase 1.4: external support reduces retained income; internal transfers do not; verified dates and in-transit gaps remain visible. One complete recent month provides an early usability checkpoint.
  • Phase 1.6 / Phase 2.2: investment funding and principal repayments cancel cash legs; income, distributions and market/FX effects are counted once; platform transfers preserve acquisition history. The V33 SQL suite proves exact full-leaf cash allocation, report exclusion and unlink restoration, event/lot capacity and temporal eligibility, split-leaf behavior and split-parent refusal, owner authorization and household isolation. A separate rollback-scoped rehearsal applies the real V33 file to populated V32 state and proves the legacy guard fails before any V33 surface persists. The Task 7 API suite additionally proves proposals are read-only, confirmation detects stale state, one-to-many and many-to-one allocations remain atomic, transfer legs are ineligible while the final debit is eligible, and unlink restores one selected leaf without changing income or net worth. The V34 SQL and API cases prove corrected originals cannot receive funding, funded events cannot be corrected, active replacements remain eligible, and a real concurrent correction/confirmation race commits one side while the obsolete confirmation returns a stale conflict.
  • Phase 3.1 / Phase 3.2: account-level shortfalls remain visible; purchases and card settlements have distinct spending/cash timing; actual payments clear future commitments; actions resolve without duplicates.
  • Phase 3.3 / Phase 3.4: resources cannot be reserved twice; emergency coverage uses a visible baseline; partial claims settle without creating duplicate income; renewals and maturities surface actions.
  • Phase 1.8: the owner can interpret exported records independently and unauthorized sessions cannot retrieve them.
  • Phase 1.7 Task 1: a payslip is stored only when its lines reconcile exactly to the stated gross, deductions and net pay, entered or imported; re-importing a multi-month file creates nothing twice; a correction supersedes without editing the original; and net pay links to exactly one eligible ledger credit, unlinking with income, spending and net worth unchanged. The V42 SQL suite proves owner/member/foreign/anonymous isolation on both tables, a totals mismatch refused at constraint time with nothing stored, and immutability of every field but the deposit link. The live API suite proves exact round trips, idempotent replay and conflicting-key refusal, a multi-month import committing only reconciling months in one request, a manually entered month reporting already_recorded on a later import, deposit-candidate window edges, and a linked credit reading eligible: false once it becomes a transfer leg.
  • Phase 1.7 Task 2: a commitment moves its account's 30/60/90-day forecast balances exactly and GET /forecast changes no row, balance or dashboard figure — proved by re-running GET /dashboard and counting commitment rows before and after. The unit suite proves occurrence-date month-end and 29 February clamping, an inclusive end date, the exclusive-balance-date/inclusive-day-90 window and exact four-place Decimal sums. The V43 SQL suite proves owner/member/foreign/anonymous isolation and a cross-household account reference refused by its composite foreign key. The live API suite proves create/replay/conflict, an archived commitment refusing further edits, excess precision refused with no row, and every forecast exclusion reason: not_ledger_valued, no_balance_date, balance_after_as_of for accounts and account_closed, account_excluded, currency_mismatch for commitments.
  • Phase 2.3: GET /rules/analytics and GET /rules/suggestions change no transaction row. The live suite proves coverage counts and percentages over the anchor window, per-rule hits, last-hit date and disagreements for a synthetic rule, a suggestion appearing only from three or more owner corrections (never from two, never duplicating an active rule's exact pattern and outcome) with affected/unclassified equal to what POST /rules/preview reports for the same rule body, and owner/household isolation. The Python proposed_pattern twin and the web's proposedPattern are proven identical on one shared vectors file consumed by both a pytest and a vitest suite. GET /classification-review/groups?sort=impact is proven to order groups by total absolute amount_base then occurrence count, distinct from the default severity/date order.
  • Phase 3.1 Task 1: a monthly commitment settled by linking its posting advances to next month and its forecast occurrence disappears exactly once; a part payment leaves the exact remainder projected; dismissing an occurrence records the reason and the next occurrence still appears. GET /forecast, the payment-candidates read and GET /commitments change no row. The V48 SQL suite proves isolation on commitment_resolution, the resolution shape, closing and transaction uniqueness, every commitment_payment_is_eligible refusal (wrong account, currency, sign, excluded, opening balance, a payslip pair posting, a split parent) and a transfer leg accepted, and immutability once inserted; a separate upgrade rehearsal migrates to V47, inserts a once, a month-end monthly, a 29 February annual and an ended commitment on accounts with past balance dates, applies V48 and asserts each backfilled nextDueDate. The unit suite proves is_occurrence/next_occurrence across the same month-end and 29 February clamps and inclusive end dates as occurrence_dates. The live API suite proves full and part payment, completed and dismissed closes, a once commitment finishing, replay returning 200, every 409/422 refusal (stale due date, archived, finished, already resolved, a reused posting, every ineligible sign/account/currency/excluded posting), undo of a part payment and of the latest closing row with refusal of an older one or one whose next occurrence already has a payment (undoable agreeing each time), an overpayment leaving remainingNext "0.0000", and payment-candidate window edges.
  • Phase 3.1 Task 2: a card statement due appears as an action; Plan payment turns it into one commitment item and removes the card item; settling that commitment (linking the bank-side transfer leg) clears both. Snoozed items return after their date; a follow-up completes and reopens; the overview count matches the list. The V49 SQL suite proves isolation on action_item and action_mark, the cross-household account/card-statement references refused, the card-source check and the one-open-plan index (an archived plan frees the statement for a new one), and the title/reason/mark shape checks. The live API suite proves commitment items in and out of the seven-day window with overdue-first ordering; card-item membership (paid in full, zero balance, an older cycle superseded by a newer statement, due more than seven days past, planned, dismissed all absent; an archived plan present again; action_list(apply_marks=False) listing snoozed and dismissed items); a snooze moving an item to snoozed and back after its date, 404 on a foreign or stale key, 422 before any database access on a malformed key, a bad date or a reason on a non-card key; follow-up create/replay/conflict/complete/dismiss/reopen and their 409 transitions; every card-source refusal on POST/PUT /commitments and the 409 second plan; GET /actions, GET /forecast and payment-candidates changing no row; household isolation of GET /actions against real foreign rows; and member 403 and foreign-household 404 on every write.
  • Phase 3.2 Task 1: a card-statement commitment moves the paying account down and its card up by the same amount on the same date, the currency total unchanged by it, and linking the payment removes both; a card account whose own balance date is on or after the payment gets no mirror, and an excluded or currency-mismatched card account still applies the paying side while listing the commitment as card_settlement_not_projected. A 1,000 balance with a 1,500 outflow before a salary commitment shows an exact 500 shortfall, naming a second same-currency account with enough as fundingAccounts and leaving it unchanged, never an illiquid or other-currency one. Confirmed-only points and lowest balances are exact per account and per currency, with a currency's pre-asOf occurrences folded into its asOf-dated start; a foreign household's accounts and card dues never appear. Archived commitments and dismissed occurrences contribute nothing; unapplied occurrences (on or after nextDueDate, on or before the balance date) are capped at 12 per commitment; balanceAgeDays, coverageGapMonths, currency membership, excludedAccountIds and staleAccountIds are exact; unplannedCardDues lists a due regardless of snooze or dismissal marks and excludes one past asOf + 90. GET /forecast changes no row.
  • Phase 3.2 Task 2: V50 SQL proves the first-day check and owner/member/foreign/anonymous isolation. Against a synthetic month with one coverage gap, one transfer candidate pair, one unclassified reportable row and two complete stored month totals, GET /monthly-review returns the exact gapCells/rowsWithGaps, candidateCount, unclassifiedCount and a changeBase matching the two totals' own difference; a month with an incomplete or absent stored total gives a null changeBase and null totalBase. PUT .../completion is 201 the first time and 200 with the same completedAt on a replay; DELETE .../completion is 204 and idempotent; a month after the current one is 422 on GET and PUT .../completion; a foreign household's real transfer pair, unclassified row, stored totals, commitments, follow-up and completions never enter another household's steps, completion state or previousMonthReview; GET /monthly-review changes no row, including an existing completedAt. GET /actions's previousMonthReview reflects a completion and a reopen. Member 403 on the three new routes is covered by the repo-wide owner-dependency inventory test, not a dedicated case.

Run the scenario checks as each feature lands. Every included native balance reconciles to its source; real-data coverage and valuation uncertainty are reported separately from unexplained errors. A blanket 1% net-worth tolerance does not waive reconciliation. Complete synthetic attribution cases have zero residual, including internal movements and dated FX effects.

Measure import plus ledger-review time against the twenty-minute target; measure the added planning review separately. Validate that the user can identify the verified position, next obligations, uncommitted resources and unresolved actions. Daily opening frequency alone is not success.

8. Definition of done

A milestone is complete when all of the following hold. Partial completion is tracked as incomplete — a milestone that is "done except for tests" is a milestone whose numbers cannot be trusted, which defeats the purpose.

☐  Feature works against real data, not only fixtures
☐  Unit tests cover the calculation logic
☐  Any invariant the milestone touches has a test
☐  Settings › Data Quality reports no new warnings
☐  Migrations apply cleanly from an empty database
☐  Types regenerated; schema parity test passes
☐  Docs updated where behaviour changed
☐  Manual verification performed against a real statement or a bank app
☐  No secrets, no real financial data in the diff
