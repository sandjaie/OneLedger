What is generic, and what isn't

The product is institution-agnostic by construction. Accounts, institutions, categories, merchants, rules, securities and statement layouts are all rows — added, edited and deleted by the user. Opening a bank account next year, or importing a statement from an account closed years ago, requires no code change and no deploy.

Bank and merchant names appear throughout these documents as examples — a remittance is easier to follow as "ENBD Current → HDFC NRO" than as "account A → account B". That is prose, not structure. The rule the code follows is narrower and absolute:

No institution, card, or fund name appears as a code identifier, module name, enum value, or required seed row.

Seed data — the starter institution list and the ~120 merchant classification rules — exists only to make the first import useful rather than a wall of uncategorised rows. Every row is deletable, and nothing depends on any of them.

Decisions already locked

Settled in discussion. Reopening any of these means revisiting documents, so they are recorded here in one place:

Decision Choice ADR
Hosting One VPS, one docker compose stack — web, api, db, caddy. Localhost first; hosted later 0014
Auth Google OIDC implemented in the service. No password, no signup, one pinned account 0004
Backend shape React UI · Python (FastAPI) backend · Postgres. All containers; local through Phase 1 0013
Users Single user now; household_id / owner_person_id carried from day one 0004
Reporting currency A configured base and secondary. Both frozen per transaction 0002
FX model Two rates: transaction-date for flows, as-of-date for balances 0002

Rules & matching Classification cascade and transfer scoring live in the Python service — one implementation, one caller 0013
Reporting year Calendar year for everything; tax-year views in V2 Q20

Opaque assets Manual valuation snapshots with staleness indicator 0006
Investments Transaction-level: units, NAV, lots, XIRR 0005
Transfers Auto-detect with confidence score, confirmed in review queue 0007

How to change these documents

The specs are version-controlled prose, and they are expected to change — but deliberately.

  • A change that contradicts a locked decision needs a new ADR superseding the old one. Do not silently edit the old ADR; mark it Superseded by ADR-XXXX.
  • A change to the schema updates data-model.html and ships a migration in the same commit.
  • A change that moves work between phases updates roadmap.html and records its scope tradeoff.
  • All new implementation plans go in docs/superpowers/plans/, and all new specifications go in docs/superpowers/specs/. Existing Phase 0 plans and references live directly in docs/superpowers/.
