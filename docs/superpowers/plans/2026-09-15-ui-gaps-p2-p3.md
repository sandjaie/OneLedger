gaps its re-check found in the delivered UI completion work, so every delivered outcome is usable
and understandable from the web application.

Phase 1.8 payslips and Phase 2.2 wealth history specifications; ADR-0002, ADR-0010, ADR-0013.

## Task 3b — pending classification knowledge, knowledge list and recent runs

**Workspace/branch/base/target:** `/Users/sandjaieravi/dev/OneLedger` /
`feature/ui-classification-knowledge` / `develop` / `develop`.
**Depends:** 3a.
**Files:** create `db/migrations/V47__pending_classification_knowledge.sql`,
`web/app/settings/merchant-knowledge.tsx` and test; update
`api/oneledger/routes/merchant_knowledge.py`, `api/oneledger/routes/classification_decisions.py`,
`api/oneledger/ingest/knowledge.py` only if it reads knowledge without the active filter, their live
tests, `web/app/review/classification-review-screen.tsx` and test, `web/app/workspace.tsx`;
`docs/superpowers/schema.md`; generated types; API contracts; progress.
**Contract:**

- **Pending knowledge.** V47 extends `classification_evidence_state_is_known` to
  `active`, `pending`, `revoked`, and `classification_evidence_revocation_agrees` so a pending version
  has `revoked_at IS NULL`. Every consumer (imports, `/classify`, suggestions, the knowledge list and
  any view) already reads or must read only `state = 'active'`; the implementer lists every read of
  `classification_knowledge_version` and of the alias or merchant rows knowledge creation writes, and
  proves none of them lets a pending version or its alias classify a transaction. If an alias row
  alone would classify, the alias is created at activation instead.
- `POST /merchant-knowledge` accepts `pending: bool = false`; pending creates the version in
  `pending` state. `POST /classification-runs/preview` accepts an active or pending version of this
  household. `POST /classification-runs/{runId}/apply` activates the run's pending version in the
  same transaction as a successful apply (refusing with the existing 409 if another active version of
  that knowledge now exists), and leaves it pending on conflict or expiry. A pending version older than
  one day is revoked by the next knowledge write (no scheduler). A one-row answer creates pending
  knowledge and never activates it.
- The classification review card creates pending knowledge at Preview; nothing it previews changes
  future classification until Apply succeeds.
- `GET /classification-runs?limit&offset` lists this household's applied and undone runs newest first:
  `runId`, `appliedAt`, `reason`, `changed`, `state`, `sourceRunId`, knowledge display name. The
  Classify screen shows **Recent changes** with **Undo** (existing `POST /{runId}/undo` with a reason
  and one idempotency key per attempt) and shows the server's refusal text.
- Settings gains **Merchant knowledge**: list active (optionally inactive) knowledge, edit through
  `PATCH /merchant-knowledge/{aliasId}` sending the full `KnowledgeBody` built from the row plus the
  owner's edits, and deactivate through `DELETE`. It says edits affect future classification only.

**Tests:** live: pending knowledge never classifies an import row, a `/classify` pass or a suggestion;
apply activates it atomically; conflict and expiry leave it pending; stale pending is revoked; runs
list is household-scoped and paged; member and foreign refusals for the new route and flag. Web:
preview creates pending knowledge; recent changes undo; knowledge edit sends the full body; deactivate.
**Commands:** `(cd api && uv run pytest -q tests/test_classification_decisions_live.py
tests/test_merchant_knowledge_live.py)` (adjust to the files covering these routes); migration
tests; shared types command; `(cd web && npx vitest run && npm run typecheck && npm run lint)`;
`scripts/verify.sh`.
**Acceptance:** a previewed but unapplied suggestion changes nothing; an applied run can be undone
after a reload; remembered merchants can be reviewed, edited and removed.

## Task 3c — lot allocation, investment review queue and event paging

**Workspace/branch/base/target:** `/Users/sandjaieravi/dev/OneLedger` /
`feature/ui-investment-lots-reviews` / `develop` / `develop`.
**Depends:** 3b.
**Files:** `api/oneledger/investments/portfolio.py`, `api/oneledger/routes/portfolio.py`, a new
`api/oneledger/routes/investment_reviews.py` registered in `main.py`, their live tests; create
`web/app/investments/lot-allocation-panel.tsx`, `web/app/investments/review-queue.tsx` and tests;
update `holding-screen.tsx`, `portfolio-screen.tsx`, `web/app/settings/data-quality.tsx`; generated
types; API contracts; progress.
**Contract:**

- `GET /portfolio/holdings/{holdingId}/lots` lists the holding's acquisition lots oldest first:
  `lotId`, `acquisitionEventId`, `acquiredOn`, `originalUnits`, `remainingUnits`, `costNative` as
  strings; household-filtered; foreign holding 404.
- A disposal event with an open `incomplete_lot_allocation` review shows **Allocate lots** on the
  holding page. The panel lists open lots, takes allocated units per lot as exact strings, posts the
  existing proposal route to get `expectedState`, shows the proposed allocations, then confirms
  through `POST /investment-funding/lot-allocations` with `expectedState` and one idempotency key
  per draft (reused on an unchanged retry). It shows the returned realised cost, gain and remaining
  basis as server strings and reloads the holding. No TypeScript arithmetic: remaining-units checks
  are the server's.
- `GET /investment-reviews?status=open&limit&offset` lists open `investment_review_item` rows:
  `id`, `reason`, `isBlocking`, `holdingId`, `securityName`, `accountName`, `importId`,
  `investmentTransactionId`, `createdAt`; household-filtered. The portfolio page shows **Reviews**
  with a link per row to its holding (lot allocation) or import; Data Quality links to it.
- `GET /portfolio/holdings/{holdingId}` accepts `eventsOffset` and `eventsLimit` (default and maximum
  200). The holding page offers **Load more events**, and funding and correction work on every loaded
  event.

**Tests:** live lots read with remaining units after an allocation; foreign 404; review queue scoped,
paged and reasons exact; events paging offset. Web: allocate lots proposal then confirmation with exact
strings and key reuse; queue links; load more.
**Commands:** `(cd api && uv run pytest -q tests/test_holding_detail_live.py
tests/test_investment_funding_live.py)` plus the new live test files; shared types command;
`(cd web && npx vitest run && npm run typecheck && npm run lint)`; `scripts/verify.sh`.
**Acceptance:** a sale recorded in the application can have its lots allocated so realised gain is
stated; every open investment review is reachable.

**Contract:**

- `GET /wealth-history` adds per complete month `chartRatio`: that month's base total divided by the

  from the server value, no arithmetic) with incomplete months labelled blank.

  120-second timeout; the server refuses ranges over 400 days (422) in addition to its existing
  checks; the card shows `written`.
- Rule packs ship inside the API package (moved from `db/seeds/rules/`, keeping one source of truth).
  `GET /rules/packs` lists pack names and rule counts; `POST /rules/packs/{name}` loads one with the
  existing seed-rule semantics (409 once loaded). Rules shows **Load starter rules** when none are
  loaded.

**Tests:** chart ratio exact for mixed-sign synthetic months and null for incomplete; backfill range
refusal; packs list and load, 409 on repeat, unknown pack 404. Web: bars render from server ratios;
backfill posts dates; starter rules load.
**Commands:** `(cd api && uv run pytest -q tests/test_wealth_history_live.py tests/test_rules_live.py
tests/test_fx_backfill.py)` (adjust to the files covering these routes); shared types command;
