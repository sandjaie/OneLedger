# UI gaps P2 and P3 implementation plan

> Execute in the active checkout. Track completion only in `../progress.md`.

**Goal:** Close the remaining P2 and P3 gaps from the 15 September 2026 UI coverage audit, and the
gaps its re-check found in the delivered UI completion work, so every delivered outcome is usable
and understandable from the web application.

**Architecture:** Branch 3a is web-only wording, navigation, timeouts and existing-route screens.
Branch 3b keeps classification knowledge pending until a preview is applied and adds knowledge and
recent-run management. Branch 3c adds lot reads, lot allocation, an investment review queue and
holding event paging. Branch 3d adds a server-scaled wealth chart and two maintenance cards.

**Stack:** Existing Python/FastAPI, PostgreSQL/Flyway and Next.js/React. One forward-only migration
(3b). No new dependency. Authority: the Phase 1.5 classification decisions, Phase 1.6 investments,
Phase 1.8 payslips and Phase 2.2 wealth history specifications; ADR-0002, ADR-0010, ADR-0013.
This group is planned together and reviewed once.

## Task 3b — pending classification knowledge, knowledge list and recent runs

**Workspace/branch/base/target:** `/Users/sandjaieravi/dev/OneLedger` /
`feature/ui-classification-knowledge` / `develop` / `develop`.
**Depends:** 3a.
**Files:** create `db/migrations/V47__pending_classification_knowledge.sql`,
`web/app/settings/merchant-knowledge.tsx` and test; update
`api/oneledger/routes/merchant_knowledge.py`, `api/oneledger/routes/classification_decisions.py`,
`api/oneledger/ingest/knowledge.py` only if it reads knowledge without the active filter, their live
tests, `web/app/review/classification-review-screen.tsx` and test, `web/app/workspace.tsx`;
`db/tests/0020_classification_decisions.sql` and a new db test; `docs/design/data-model.html`
(knowledge lifecycle), `docs/superpowers/specs/2026-09-10-classification-knowledge.md` (lifecycle
line), `docs/superpowers/schema.md`; generated types; API contracts; progress.
**Contract:**

- **Pending knowledge.** V47 extends `classification_evidence_state_is_known` to `active`, `pending`,
  `revoked`; `classification_evidence_revocation_agrees` so a pending version has `revoked_at IS NULL`;
  and `CREATE OR REPLACE`s `assert_classification_knowledge_version_immutable()` to allow exactly
  active→revoked, pending→active (`revoked_at` stays NULL) and pending→revoked. Every classifier reads
  knowledge through `load_knowledge()` (`ingest/knowledge.py`), which already filters
  `v.state = 'active'`, and no view reads aliases or versions, so aliases are still created at
  POST; the implementer confirms this with one live test rather than new filters.
- `POST /merchant-knowledge?pending=true` (query parameter, not a `KnowledgeBody` field, because
  `PATCH` reuses that model) creates the version in `pending` state. `GET /merchant-knowledge` never
  lists pending versions, even with `includeInactive`. `DELETE` revokes an active or pending version.
- `POST /classification-runs/preview` accepts a version in `active` or `pending` state; the apply
  evidence check accepts either. `ApplyBody` gains `activateKnowledge: bool = true`. After a
  conflict-free apply, when `activateKnowledge`, the same transaction runs
  `UPDATE … SET state = 'active' WHERE id = … AND state = 'pending'`; conflict and expiry leave it
  pending (the household lock serialises applies). The "knowledge version is no longer active" conflict
  now fires only for a revoked version. Pending versions that are never applied are simply ignored.
- The classification review card creates pending knowledge at Preview and applies with the default;
  the one-row answer creates pending knowledge, applies with `activateKnowledge: false`, and keeps its
  `DELETE` (pending→revoked). Nothing previewed changes future classification until Apply succeeds.
- `GET /classification-runs?limit&offset` lists this household's `state = 'applied'` runs newest first,
  excluding review-reset bridge runs (`reason = _REVIEW_RESET_REASON`): `runId`, `appliedAt`
  (`resolved_at`), `reason`, `changed`, `sourceRunId` (from `result->>'sourceRunId'`), `undone` (an
  applied run exists whose `result->>'sourceRunId'` is this run), and the knowledge display name
  (`counterparty_alias.knowledge_version_id` → `counterparty.display_name`). The Classify screen shows
  **Recent changes** with **Undo** on runs that are neither undone nor undo runs (existing
  `POST /{runId}/undo` with a reason and one idempotency key per attempt), shows the server's refusal
  text, and says undo leaves the remembered merchant active with a link to Settings › Merchant knowledge.
- Settings gains **Merchant knowledge**: list active (optionally inactive) knowledge, edit through
  `PATCH /merchant-knowledge/{aliasId}` sending the full `KnowledgeBody` built from the row plus the
  owner's edits (`merchantId` with `merchantName: null`, since `coherent` refuses both), and deactivate
  through `DELETE`. It says edits affect future classification only.

**Tests:** db test: allowed and refused state transitions. Live: a pending version does not
classify an import row, a `/classify` pass or a suggestion; apply activates it atomically;
`activateKnowledge: false` and conflict leave it pending; pending is not listed; runs list is
household-scoped, paged, excludes bridge runs and marks undone; member and foreign refusals for the
new route and flag. Web: preview creates pending knowledge; one-row answer does not activate;
recent changes undo; knowledge edit sends the full body; deactivate.
**Commands:** `(cd api && uv run pytest -q tests/test_classification_decisions_live.py
tests/test_merchant_knowledge_live.py)` (adjust to the files covering these routes); migration
tests; shared types command; `(cd web && npx vitest run && npm run typecheck && npm run lint)`;
`scripts/verify.sh`.
**Acceptance:** a previewed but unapplied suggestion changes nothing; an applied run can be undone
after a reload; remembered merchants can be reviewed, edited and removed.

## Task 3c — lot allocation, investment review queue and event paging

**Workspace/branch/base/target:** `/Users/sandjaieravi/dev/OneLedger` /
`feature/ui-investment-lots-reviews` / `develop` / `develop`.
**Depends:** 3b.
**Files:** `api/oneledger/investments/portfolio.py`, `api/oneledger/routes/portfolio.py`, a new
`api/oneledger/routes/investment_reviews.py` registered in `main.py`, their live tests; create
`web/app/investments/lot-allocation-panel.tsx`, `web/app/investments/review-queue.tsx` and tests;
update `holding-screen.tsx`, `portfolio-screen.tsx`, `web/app/settings/data-quality.tsx`; generated
types; API contracts; progress.
**Contract:**

- `GET /portfolio/holdings/{holdingId}/lots` lists the holding's acquisition lots oldest first:
  `lotId`, `acquisitionEventId` (`origin_transaction_id`), `acquiredOn` (`acquisition_date`),
  `acquiredUnits`, `remainingUnits`, `costBasisNative` as strings and `eligible` (false for a lot whose
  origin event is corrected or that has an active successor); household-filtered; foreign holding 404.
  Remaining units come from the same lot-state query the proposal uses (`_load_lot_state()` in
  `investments/funding.py`), moved into one shared helper so the list and the proposal cannot disagree.
- `HoldingEventRow` gains `lotAllocationOpen: bool` (an open `incomplete_lot_allocation` review exists
  for that event). Such a disposal shows **Allocate lots** on the holding page. The panel lists eligible
  lots dated on or before the disposal, takes allocated units per lot as exact strings, posts
  `POST /investment-funding/lot-allocation-proposals` to get `expectedState`, shows the proposed
  allocations, then confirms through `POST /investment-funding/lot-allocations` with
  `expectedState` and one UUID idempotency key per draft (reused on an unchanged retry). It shows
  the returned realised cost, gain and remaining basis (each nullable) as server strings and
  reloads the holding. No TypeScript arithmetic: remaining-units checks are the server's.
- `GET /investment-reviews?limit&offset` lists open `investment_review_item` rows:
  `id`, `reason`, `isBlocking`, `holdingId`, `securityName`, `accountName`, `importId`,
  `investmentTransactionId`, `createdAt` (holding, security and account left-joined, since import
  reviews may have none); household-filtered. The portfolio page shows **Reviews**
  with a link per row to its holding (lot allocation) or import; Data Quality links to it.
- `GET /portfolio/holdings/{holdingId}` accepts `eventsOffset` and `eventsLimit` (default and maximum
  200). The holding page offers **Load more events**, and funding and correction work on every loaded
  event.

**Tests:** live lots read with remaining units after an allocation; foreign 404; review queue scoped,
paged and reasons exact; events paging offset. Web: allocate lots proposal then confirmation with exact
strings and key reuse; queue links; load more.
**Commands:** `(cd api && uv run pytest -q tests/test_holding_detail_live.py
tests/test_investment_funding_live.py)` plus the new live test files; shared types command;
`(cd web && npx vitest run && npm run typecheck && npm run lint)`; `scripts/verify.sh`.
**Acceptance:** a sale recorded in the application can have its lots allocated so realised gain is
stated; every open investment review is reachable.

**Files:** `api/oneledger/routes/wealth_history.py`, `api/oneledger/routes/rules.py`,

**Contract:**

- `GET /wealth-history` adds per complete month `chartRatio`: that month's base total divided by the
  largest absolute complete-month base total, as a `Decimal` string with 4 places (half-even) in
  `[-1, 1]`; `"0.0000"` for every complete month when that largest total is zero; null for incomplete
  months. Wealth renders bars from a zero baseline by setting the server string as a `--ratio` CSS custom
  property with `transform: scaleY(var(--ratio))` (negative values flip below the baseline; no
  arithmetic), with incomplete months labelled blank.
- Settings › Exchange rates (the card in `web/app/workspace.tsx`) gains **Backfill rates** calling
  `POST /fx/backfill?start&end` (`api/oneledger/routes/fx.py`) with a 120-second timeout; the server
  refuses ranges over 400 days (422) in addition to its existing checks; the card shows `written`.
- Rule packs ship inside the API package (moved from `db/seeds/rules/`, keeping one source of truth;
  update `test_seeded_rules.py`, `test_rules_live.py`, `db/seeds/README.md` and `rules.py` docstrings).
  `GET /rules/packs` lists packs by file stem with rule counts; `POST /rules/packs/{name}` loads one
  with the existing seed-rule semantics (409 once that household has seed rules; unknown name 404) and
  replaces `POST /rules/pack`. Rules shows **Load starter rules** when none are loaded.

**Tests:** chart ratio exact for mixed-sign synthetic months and null for incomplete; backfill range
refusal; packs list and load, 409 on repeat, unknown pack 404. Web: bars render from server ratios;
backfill posts dates; starter rules load.
**Commands:** `(cd api && uv run pytest -q tests/test_wealth_history_live.py tests/test_rules_live.py
tests/test_seeded_rules.py tests/test_fx_range_live.py)` (adjust to the files covering these
routes); shared types command; `(cd web && npx vitest run && npm run typecheck && npm run lint)`; `scripts/verify.sh`.
**Acceptance:** wealth over time is visible as a chart; exchange rates and starter rules can be
maintained from Settings.
