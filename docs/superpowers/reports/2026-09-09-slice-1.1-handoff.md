## 3. Field intelligence — do not rediscover this

Gathered by running the current engine against the real statements in `pdf-statements/`
(git-ignored; **never commit any of it, never `git add -f` that directory**).

**38 card statements confirmed** (`E-STATEMENT_*.pdf`), matching slice 1.1's acceptance count.
71 files total across all four layouts.

### The card profile that works

**`db/seeds/card-layout.json` is the answer, and `db/seeds/README.md` explains it.** Read those
two rather than this section — they ship with the branch and cannot drift from what the tests
prove. What follows is only the context they do not carry.

Header row is `Transaction Date | Posting Date | Description | Amount`, and the column bands in
the seed were read off its word coordinates on page 1.

### Four things that will bite

1. **The balance anchors cannot be regexes over a label.** The producer emits no space
   characters between cells, so the six summary figures extract as a single run with nothing
   between them, and the labels are a separate physical line above (two lines on one of the two
   card variants). Anchoring on the label and counting figures after it does not work — the
   seed anchors on the figures line itself, requires exactly six, and captures the first and
   the **fifth**. The fifth is the total payment due; the sixth is a current balance that also
   carries any remaining installment principal and reconciles against nothing. Anchoring on
   the figures rather than the labels is also what lets **one profile cover both variants**.

2. **The period must be DERIVED, never captured.** The installment block prints each plan's
   *original purchase date*, so the statement legitimately carries rows dated outside its own
   period — and those instalment charges are part of the declared purchase total the anchors
   reconcile against. Capturing the period would fail those rows and break the identity.
   `dateFormat` carries a four-digit year, so deriving is permitted. (Separately: the printed
   period uses a two-digit year, which `normalize._period_bounds` refuses anyway — it requires
   both bounds under one four-digit-year format.)

3. **`continuation:no_date_and_no_amount` runs past the end of the transaction table**,
   appending pages of legal furniture to the last row's `description_raw` — 2,232 characters of
   it against 46 with the rule off. The seed therefore sets **no continuation rule and no skip
   patterns**: this card writes each transaction on one physical line, so nothing is lost that
   the row needed, and the dropped lines are counted in `lines_unparsed` and reported in the
   parse summary (Invariant 7). A layout whose narration genuinely wraps sets the rule on.

4. **The amount word sits ~2pt below its own row.** Line grouping must tolerate that;
   `words.py` infers tolerance from modal character height, which is why it currently works.
   Do not hard-code a tighter tolerance.

### The arithmetic that proves the frame

The rows sum positive in the ledger's frame (a payment credit outweighing the month's
purchases), while the statement declares its previous balance and its total payment due bare —
both money owed. The identity closes only once both anchors are negative; read in the issuer's
frame the computed closing overshoots the declared one by twice the opening balance, which is
what blocked all 38 files.

The worked example, with invented figures, is `api/tests/test_ingest_card_frame.py`. **No
figure, date or per-file count from a real statement appears in this repository** — those files
are git-ignored, and the committed evidence is that suite.

## 5. Process that binds every remaining branch

- Cycle: **plan → implement (TDD) → `/verify` → `/oneledger-code-review` (one round) → fix
  blocking → `/verify` → first push → PR → merge → delete branch.** Codex/external review is
  disabled — never wait for it.
- Nothing reaches `origin` unreviewed. `--no-verify` is not an option.
- Diff budget 800 / 1,600 soft, 1,200 / 2,400 hard; `ONELEDGER_SIZE_OVERRIDE="reason"` past the
  hard stop, with the same reason in the PR's Notes.
- `docs/superpowers/progress.md` is updated **on the task branch, in the head that gets
  merged**. No parallel trackers.
- Money: `Decimal` / `NUMERIC(20,4)` / string on the wire. No institution, currency or country
  name as an identifier. `require_owner()` is the boundary. Reports read
  `v_transaction_reportable`. Migrations forward-only via Flyway; never edit an applied one.
- Deviations from the plan go in the PR and `progress.md`, never by editing the plan after
  dispatch.
- UI branches: build to `docs/product/mockups/` (`OneLedger.dc.html`, `Review.dc.html`,
  `NetWorth.dc.html`, `LayoutMapping.dc.html`) — the owner's instruction is that these are
  exactly how the UI should look.
