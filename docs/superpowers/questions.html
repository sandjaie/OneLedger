Open Questions

Status: 17 of 24 answered (2026-09-05). The seven still open — Q8, Q17, Q18, Q19, Q21, Q23, Q24 — are downstream of milestones that are not yet scheduled. None blocks Phase 0, M1 or M2.

Answers below are the record of decisions actually made. Where an answer changed a locked decision, it cites the ADR that supersedes it.

These are one deployment's answers, not the product's requirements. They are kept because the specifications are only readable alongside the constraints that produced them — a different household answers differently and gets a different, equally valid configuration. Nothing here is a supported list; every name in it is a row in a table.

Write answers directly under each **Answer:** line and commit. Order is by when it's needed, so answering top-down means answering the urgent ones first.

⚠ Do not put account numbers, balances, passwords, PANs or Emirates ID numbers in this file. It's committed to git. Institution names and account types are fine — that's all I need. See security-and-privacy.html §1.

Needed before Phase 0 (foundations)

Q1 · Which Google account signs in?

Pinned as ALLOWED_USER_EMAIL; every other Google account is rejected even if Google authenticates it (ADR-0004).

Default if unanswered: the address on the session that set the project up.

Answer: one address, set in .env as ALLOWED_USER_EMAIL. It is deployment configuration and is never written into a committed document.

Q2 · Supabase project region?

Affects latency and where your financial data physically sits. Options roughly: Mumbai (ap-south-1), Singapore, Frankfurt, or a US region. Mumbai is closest to India, Frankfurt is often the lowest-latency free-tier option from the UAE.

There's no UAE region on the free tier, so this is a genuine choice rather than an obvious one.

Default if unanswered: Mumbai — nearest to the larger share of the data, and keeps Indian financial data in India, which is the more likely future regulatory concern of the two.

Answer: Mumbai (ap-south-1) — default accepted.

Moot since ADR-0014. There is no Supabase project to place. Postgres runs in a container on a machine you choose, so the question becomes where that VPS is, and the reasoning above still answers it: put the data nearest the jurisdiction most likely to care about it.

Q3 · What OS is the importer machine?

Determines the keychain integration for secrets, the full-disk-encryption instructions, and the ~/statements/ cloud-sync exclusion guidance.

Default if unanswered: macOS.

Answer: macOS. Since parsing moved out of a local CLI into the browser, there is no keychain integration and no secret held on the machine at all. What remains OS-specific: ~/statements/ must sit on the FileVault volume, outside the repository, and be excluded from iCloud Drive sync.

Q5 · Any joint or spouse-held accounts?

The schema carries owner_person_id and an optional joint_owner_person_id already (ADR-0004), so tagging is free. I just need to know whether to seed a second person row.

Default if unanswered: one person, everything solely held.

Answer: One person, everything solely held. Spouse deferred entirely to Phase 2 — owner_person_id and joint_owner_person_id exist in the schema from day one and stay unused in Phase 1, so adding her later needs no migration.

Q6 · What's the history window start date?

We settled on ~24 months (later 36). This is the exact date opening balances get anchored to — probably 01 Jan 2025 or 01 Apr 2025 (aligning to the Indian financial year).

Default if unanswered: 01 Apr 2025, so the window aligns to Indian FY boundaries and makes tax reporting cleaner later.

Answer: 01 Jan 2024 — ~36 months. Supersedes the earlier 24-month horizon; recorded as ADR-0011.

Q8 · Can you download statements in bulk, or one month at a time?

Purely practical — 24 months × 6 institutions is 144 downloads if it's one at a time. Some banks offer a date-range export. Worth knowing before you sit down to do it.

Default if unanswered: assume one at a time; I'll make the importer take a whole directory so it's one command regardless.

Answer: Not yet answered. 71 files covering Jan 2025 – Sep 2026 are gathered. Calendar 2024 still needs collecting to reach the ADR-0011 anchor.

Needed before M3 (PDF parsers)

Q9 · Which statements are password-protected, and what's the password scheme?

Scheme, not the password. e.g. "HDFC = customer ID + DDMMYYYY of birth", "ICICI = PAN in lowercase + DOB". I need the shape so the importer can prompt correctly; the password itself goes in your OS keychain and never touches the repo or database (statement-ingestion.html §2).

Default if unanswered: importer prompts interactively for a password on any encrypted PDF.

Answer: The question is moot — no scheme is modelled.

Both HDFC files are encrypted; the other three layouts are not. A password supplied by the user opens both HDFC files. That is the whole of what is known, and it is all the product needs.

The UI prompts for a password on any file that fails to open, and that is the entire design. Nothing is derived from a scheme, nothing is pre-filled, nothing is remembered between imports, and nothing is stored — not in the database, not in a config file, not in the OS keychain (09 §1). pdfplumber takes it directly via pdfplumber.open(path, password=…).

Correction (2026-09-05). An earlier version of this answer read "HDFC = customer ID. Confirmed against both HDFC files." That was wrong on both counts: the scheme was inferred from a masked value in a diagnostic dump, not confirmed, and no scheme needs to be known at all.

Needed before M5 (transfers)

Q11 · Which channels do you use to send money to India?

Bank wire, exchange house (LuLu, Al Ansari, UAE Exchange), Wise, something else? The provider-level cost comparison in transfers-and-reconciliation.html §5 only becomes interesting if there's more than one to compare.

Answer: Bank wire / TT, Wise, and Careem Pay — the last appears in the UAE statements as CAREEM PAY. The receiving side is visible in the HDFC and Axis statements.

Careem Pay needs a dedicated seed rule at a priority above the existing CAREEM → Transport → Taxi rule (06 §2), otherwise every remittance lands in Transport and monthly spending is overstated by the full amount sent.

Q12 · Do your remittance statements itemise the fee separately?

If the fee is a separate line, explicit_fee_amount is populated and the spread is computed on top. If it's baked into the rate, everything shows as spread. Both work; the reporting reads differently.

Default if unanswered: handle both — populate the fee when a matching charge is found within the same transfer, otherwise attribute the whole cost to spread.

Answer: Default: handle both. The UAE current-account narration embeds the destination INR amount and the achieved rate directly, so implied_rate is read from the statement rather than derived from two legs, and any separately itemised fee is matched on top.

Needed before M7 (investments — the largest milestone)

Q14 · Can you get a consolidated CAS for Indian mutual funds?

CAMS or KFintech both issue one covering every AMC in a single document. If yes, one parser gets most of the portfolio and M7 shrinks considerably. If not, it's per-AMC statements or manual entry.

CAS is usually requested by email from camsonline.com or kfintech.com and arrives as a password-protected PDF.

Default if unanswered: assume no CAS; build manual entry plus broker-statement import first.

Answer: Yes — CAMS/KFintech consolidated CAS.

Investments are currently made through ETMoney; Kuvera was used previously. A CAS is keyed on PAN and folio, not on the platform used to transact, so a single consolidated CAS covers ETMoney purchases, historic Kuvera purchases and anything bought direct — in one document.

That makes the CAS the primary M7 source and ETMoney's own PDFs a cross-check rather than a second parser. Request one covering 01 Jan 2024 onward.

Q15 · Which broker/investment platforms?

Zerodha, Groww, Kuvera, INDmoney, IBKR, Vested, employer RSU platform, something else?

Answer: ETMoney (current), Kuvera (historic). Both covered by the CAS above. ETMoney SIP debits already appear in the Axis narration as ACH-DR-ETMONEY-…, which gives the investment-funding transfer its rule hint.

Q16 · Any international/US holdings, and where?

Affects whether USD pricing and a third currency in reporting matter sooner than planned. Note that adding USD as a reporting currency means a backfill migration (ADR-0002) — holding USD assets does not, and works today.

Default if unanswered: USD assets supported, USD reporting not built.

Answer: Yes — US equities and ETFs. Held and valued in USD, translated at the as-of rate like any other foreign-currency asset. This works with no schema change. USD is not added as a reporting currency — that would need the backfill migration in ADR-0002, and it is not being done.

Q17 · Do you have PPF, EPF or NPS?

These get manual valuation snapshots rather than lot tracking (ADR-0006) — no XIRR, but they count toward net worth and allocation.

Answer: Not yet answered. If any exist they take manual valuation snapshots (ADR-0006) — no XIRR, but they count toward net worth and allocation. Needed before M7 completes, not before it starts.

Needed before M9 (net worth + dashboard)

Q20 · Which tax year drives "this year" on the dashboard?

India runs Apr–Mar; the UAE runs the calendar year. This affects every annual figure — YoY comparison, annual spending, annual remittance cost.

Options: Indian FY (Apr–Mar) · calendar year (Jan–Dec) · calendar year for cash flow, Indian FY for anything tax-related.

Default if unanswered: calendar year for everything, with tax-year views added in V2 when tax reporting arrives. Simpler now, and "this month" and "this year" read as most people expect.

Answer: Calendar year for everything. Tax-year views arrive in V2 with tax reporting.

Q21 · How should the property be valued?

Purchase price held flat, or a periodic manual estimate? Held flat is more conservative and produces a boring, honest line. Manual estimates are more accurate when updated and quietly misleading when they aren't.

Default if unanswered: purchase price as the initial snapshot; you update it when you have a real number. Staleness is displayed either way (Invariant I7).

Answer: Not yet answered — no property appears in the statements. If one exists, the default is purchase price as the initial snapshot, updated manually, with staleness always displayed (Invariant I7).

Q22 · What counts as "liquid" for you?

Liquid net worth drives one of the four dashboard tiles. My default excludes property, PPF/EPF/NPS, and anything with a lock-in — so it's cash, plus mutual funds and equities that could realistically be sold within a month.

Do FDs count? They're breakable with a penalty, so it's a genuine judgement call.

Default if unanswered: FDs count as liquid; property and retirement accounts do not.

Answer: Everything counts by default, with a per-account toggle to opt out.

No schema change needed — account.is_liquid already exists (03 §5). It defaults to true; the Accounts screen exposes it as a checkbox, and the Liquid Net Worth tile sums whatever is ticked.

Product review follow-up — 6 September 2026

The finance OS requirements are accepted as the later-phase product direction. Phase 0 remains in progress with GitHub PRs #3–#7 merged; the new master plan starts from that baseline.

Configure actual essential-spend assumptions, emergency resources, goal targets/currencies, commitments and protection records when those features are used. These are user choices, not invented defaults or blockers for Phase 0. Do not enter balances, identities or passwords in this file.

Emergency handover remains an explicit scope/privacy decision for a later discussion; it is not permission to add another login or sharing. Existing Q22 liquid-account preferences remain valid; emergency coverage is a separate measure. The original question record retains its 17-of-24 answered count; these planning preferences are separate.

Anything else

Things I haven't asked about, constraints I've missed, or parts of the spec you disagree with. Disagreement is the most useful thing you can put here — the whole point of writing this down before coding was to have the argument now rather than at M7.

Answer: Raised during the review of this spec set, and acted on:

  1. The rule engine and transfer matcher were specified to exist twice — once in Python, once in Postgres for retroactive apply and manual linking. Resolved by ADR-0013: one implementation, in the service.
  2. Circular foreign keys break migration order. transaction references transfer, card_statement, investment_transaction, loan and recurring_series, all created in later migrations, and transfer references transaction back. Migration 0006 cannot apply as written. Fixed by adding those FKs via ALTER TABLE once both sides exist.
  3. M2 assumed a clean CSV export exists. None does (Q7). M2 is re-planned around the UAE card layout — the cleanest of the four, and the one covering the most files.
  4. 71 real statements were sitting untracked inside the git working tree, with full card numbers in the filenames. .gitignore now excludes pdf-statements/, *.pdf and .env. Nothing was ever committed — history was checked and is clean.
