05 — Statement Ingestion

The hardest subsystem, and the one that determines whether the product is usable at all. If importing a month of statements is painful, the ledger goes stale and everything built on top of it becomes decoration.

Target: six institutions, one month, under 20 minutes including review.

1. Pipeline

   Upload
     │  SHA-256 · reject if already imported
     ▼
   Identify institution
     │  text fingerprint → filename hint → ask
     ▼
   Extract                        parser-specific, versioned
     │  raw rows, verbatim
     ▼
   Normalize                      dates, signs, currency, description
     │
     ▼
   Detect duplicates              against staged and committed rows
     │
     ▼
   Reconcile                      opening + Σ rows = declared closing?   ← blocks
     │
     ▼
   Enrich FX                      fetch rates, freeze amount_base / amount_secondary
     │
     ▼
   Classify                       deterministic cascade
     │
     ▼
   Match transfers                scored candidates
     │
     ▼
   Stage                          write document, import_batch, staged_transaction
     │
     ▼
   Review                         web app: confirm, correct, exclude
     │
     ▼
   Import                         one database transaction; balances recomputed

Reconciliation runs before FX enrichment, not after it. The check is local, exact and blocking: it needs only the parsed rows and the statement's own declared balances, so running it first means a batch that cannot reconcile costs no network round trip and no stored rate rows. The verdict recorded on import_batch is identical in either order — the identity is evaluated on native signed ledger amounts, which FX enrichment does not touch. The earlier ordering, with reconciliation after transfer matching, was written before the importer had a blocking verdict to compute.

Every stage runs in the Python service on localhost (ADR-0013). The web app posts the file and renders the result; it performs no parsing and no arithmetic. Statements are processed on your own machine and reach no third-party host — only the original blob is uploaded to Storage at staging.

2. Stage 1 — Upload and checksum

Every file is hashed before anything else happens.

sha256 = hashlib.sha256(file_bytes).hexdigest()

document.sha256 is uniquely indexed per household. An identical file is rejected immediately — before parsing, before any cost is incurred — with a message naming when it was first imported.

This is the cheapest of the three duplicate defences and catches the most common case: the same statement downloaded twice.

Password-protected PDFs. Some statements are encrypted — two of the seven accounts in the set gathered so far. The product models no password scheme and derives nothing. When a file fails to open, the import screen shows a password field for that file and the user types it in. pdfplumber accepts it directly:

with pdfplumber.open(path, password=password) as pdf:
    ...

The import form prompts for it and posts it alongside the file, over localhost or the TLS connection Caddy terminates. The service holds it in a local variable for the duration of the parse. It is never written to disk, a keychain, a config file, the database or a log, and it is not remembered between imports. What is stored in the documents volume is the original encrypted file.

The import screen prompts per file, and only for files that actually fail to open. It does not guess, pre-fill, or offer to save.

3. Stage 2 — Institution identification

Three strategies, in order:

1. Content fingerprint. Each saved layout profile carries a signature — distinctive strings from the statement header. Profiles are rows in statement_layout, created through the mapping UI (ADR-0012); no bank name appears in application code.

// a row in statement_layout — created by the mapping UI, not shipped in the codebase
{
  "name": "UAE card",                    // whatever the user calls it
  "version": 1,
  "fingerprints": ["Credit Card Statement", "Card Type:"],
  "header_row_pattern": "Transaction Date\\s+Posting Date\\s+Description\\s+Amount",
  "columns": [
    { "field": "booked_date",  "x_min": 40,  "x_max": 110 },
    { "field": "value_date",   "x_min": 110, "x_max": 175 },
    { "field": "description",  "x_min": 175, "x_max": 430 },
    { "field": "amount",       "x_min": 430, "x_max": 560 }
  ],
  "date_format": "dd/MM/yyyy",
  "sign_convention": "cr_suffix",
  "inverts_sign": true,
  "quirks": ["filter_script:arabic"]
}

2. Filename hint. Users name files predictably (ENBD_Sep2026.pdf). Used as a tiebreaker only, never on its own — a filename is a claim, not evidence.

3. Ask, and offer to map. If no saved profile matches, the import screen offers the existing profiles and a Map a new layout action. Mapping auto-proposes column bands from the header row and shows the parsed result live; the user confirms or drags. The saved profile matches automatically from then on — including for statements from an account that has since been closed.

This is the path for every future bank. No code change, no deploy.

Account resolution. Once the institution is known, the account is resolved by hashing the account number found in the statement and matching account.account_number_hash. If no account matches, the import screen stops and asks — it never guesses which account a statement belongs to, because a wrong guess corrupts two accounts at once.

4. Stage 3 — Extraction

The extraction engine

One engine, driven by a profile. There is no per-bank class, and no bank name appears in the codebase (ADR-0012).

class ExtractionEngine(Protocol):
    def matches(self, profile: StatementLayout, text: str, filename: str) -> float: ...
    def extract(self, profile: StatementLayout, pages: list[Page]) -> ExtractionResult: ...
    def propose(self, pages: list[Page]) -> StatementLayoutDraft: ...

RawRow is deliberately unopinionated — whatever the parser saw, with its position:

export interface RawRow {
  pageNumber: number;
  rowNumber: number;
  rawText: string;                        // the whole line, kept for debugging
  fields: Record<string, string>;         // parser's best column split
}

Words and coordinates

pdfplumber returns words with bounding boxes directly, so the engine consumes page.extract_words() rather than grouping glyph runs itself.

One caveat, measured rather than assumed: on a producer that emits no space characters, extract_words() returns run-together tokens like Statementofaccount — one of the four layouts in hand does exactly this. Word grouping does not rescue that case in any language. What does is column banding by x-position, which the layout profile specifies and which works identically whatever the spacing.

Layouts are versioned

Banks change statement layouts without notice. statement_layout_id and layout_version are recorded on every transaction, so when a September import behaves oddly, the question "which layout produced these rows?" is answered by a foreign key — and the profile itself can be opened and inspected, which a parser name could not offer.

When a bank does change format, reconciliation fails (§8), the user re-maps in the same UI, and the profile's version increments. Rows already imported keep pointing at the version that produced them.

A layout change is caught by reconciliation (§8) as a hard failure, not as silently wrong data. That is the entire reason reconciliation is non-optional.

Format handling

Format Approach
PDF, text-based pdfplumber via api/oneledger/parse/words.py. Columns identified by x-position, never by regex over a flattened line. Mandatory for any layout whose text extracts without spaces — one of the four in hand does
PDF, scanned Out of scope for Phase 1. Detected (a page with no text items) and reported, not silently mis-parsed
PDF, encrypted pdfplumber.open(path, password=…). The import screen prompts per file; no scheme is modelled
CSV / Excel Not built. No institution in use provides either (Q7). Added if one ever does

Multi-line descriptions are the most common PDF parsing failure. A transaction's narration often wraps across two or three physical lines, with only the first carrying a date and amount. The rule: a line without a parseable date and without a parseable amount is a continuation of the previous row. Each parser declares its own row-start predicate.

5. Stage 4 — Normalization

Turning what the bank wrote into the ledger's shape. This is where most correctness lives.

Dates

Ambiguity is the trap: 03/09/2026 is 3 September in both the UAE and India, but 09/03/2026 appears in some formats. Rules:

  1. Each parser declares its date format explicitly. No inference.
  2. Parsed dates must fall inside the statement period, which is itself extracted. A date outside it fails the row.
  3. Two-digit years are windowed against the statement period, not against a fixed pivot.

Signs (Invariant I2)

Statements express direction in at least four ways:

Format Example Handling
Separate columns Debit: 310.00 / Credit: — Debit → negative, credit → positive
Signed amount -310.00 Used as-is
Dr/Cr suffix 310.00 Dr Dr → negative, Cr → positive
Balance delta balance fell from 5,000 to 4,690 Derived from consecutive balances

A balance is not an amount. The Dr/Cr suffix above means one thing on an amount only under the cr_suffix convention, but a balance is a position rather than a movement, so on a balance it always reads the same way: Dr negative, Cr positive. A balance that carries one has stated its own direction, and inverts_sign is then withheld from it — reading the suffix and inverting as well reverses the statement instead of reframing it. This governs a row's running balance, the balances balance_delta derives amounts from, and reconciliation's declared anchors alike, and each balance is framed before any subtraction: a difference taken between two frames belongs to neither.

For credit cards, the convention inverts relative to the statement's presentation. A card statement shows a purchase as a positive "debit" because it increases what you owe. In the ledger a purchase is negative (Invariant I2). Each card parser declares inverts_sign = True and this is asserted in tests, because getting it wrong makes every card balance wrong in a way that still looks internally consistent.

Description cleanup

description_raw is never modified — it is the audit record. description_clean is derived for matching and display:

POS 4821 STARBUCKS DUBAI MALL      AE  030926 REF 887262819
    ↓
STARBUCKS DUBAI MALL

Removals: terminal and reference numbers, trailing dates, POS/ATM prefixes, repeated whitespace, trailing country and currency codes. Uppercase preserved — banks are inconsistent and case carries no meaning.

Cleanup is rule-driven and inspectable, not clever. A user can see exactly what was stripped.

Currency

The account's currency, unless the statement states a foreign amount. A foreign transaction on an AED card:

amount            −310.00    AED     ← what left the account; the ledger's truth
original_amount     −75.00    USD    ← reference
original_currency     USD

The bank's conversion is authoritative because it is what actually happened. The ledger does not second-guess it with a market rate.

6. Stage 5 — Duplicate detection

Three layers, in increasing cost.

Layer 1 — document checksum (§2). Same file. Free.

Layer 2 — transaction fingerprint. Statements overlap; a July–August statement followed by an August–September one shares August.

dedupe_hash = sha256("|".join([
    str(account_id),
    booked_date.isoformat(),
    f"{amount:.4f}",
    normalise_for_hash(description_raw),   # uppercase, collapse whitespace, strip punctuation
    reference_raw or "",
]))

Uniquely indexed on (household_id, account_id, dedupe_hash). Any row whose hash already exists is marked duplicate and excluded from import by default.

Reference number is included deliberately. Two genuinely distinct identical-looking transactions — two AED 31 coffees at the same shop on the same day — will differ in their bank reference, and the hash separates them.

Where a bank provides no reference, the disambiguator must be stable across documents. The obvious choice — the row's ordinal position within the statement — is wrong, and wrong in a way that silently corrupts balances:

Jul–Aug statement    …  row 50: 12 Aug  AED 31.00  STARBUCKS
Aug–Sep statement    …  row 12: 12 Aug  AED 31.00  STARBUCKS     ← same transaction

Different ordinal, different hash, so Layer 2 does not recognise the overlap and imports the August rows a second time. Layer 3 only warns. Spending and balances double for the overlapping month, which is exactly the failure the three layers exist to prevent.

The disambiguator is therefore the occurrence index within the day, not within the document:

# nth identical (date, amount, normalised description) on this account, counting from 0
occurrence_index = prior_identical_rows_on_same_date

Any statement covering 12 August contains the same set of transactions for that date, so the second coffee is occurrence 1 in both documents and hashes identically in both. Two distinct same-day identical transactions still get distinct hashes, which is the property the ordinal was reaching for.

The index is computed within the current document only — among this statement's own rows for that date, in statement order. Counting committed rows into the index would shift an overlapping row past its committed copy (the copy holds 0, the incoming would take 1), defeating the very recognition the example above establishes. The cost is the rare day whose identical pair is split across a statement boundary: its second occurrence collides with the committed first and stages as a visible duplicate the owner can accept in review — a surfaced judgement call, not a silently doubled month.

Layer 3 — near-duplicate warning. Same account, same amount, date within ±3 days, description similarity above 0.85 (token-set ratio). Warned, not blocked — this catches a genuinely double-charged subscription as well as a re-import, and only the user can tell those apart.

7. Stages 6–7 — FX and classification

FX enrichment. For each row, look up the rate for booked_date, carrying forward across non-publication days. Missing rates trigger a fetch. An import never proceeds against a missing rate and never falls back to 1.0 or to today's rate. Detail: multi-currency-and-fx.html §3.

Classification. The deterministic cascade, run locally so the review queue arrives pre-populated. Detail: classification.html.

Transfer matching. Candidates proposed and scored; nothing linked without confirmation. Detail: transfers-and-reconciliation.html.

8. Stage 8 — Reconciliation (Invariant I8)

The single highest-value check in the pipeline.

Most statements declare an opening and a closing balance. If the extracted rows are complete and correctly signed:

opening_balance + Σ(amounts) == closing_balance

If they do not balance, something is wrong — a dropped row, a missed continuation line, a sign error, a misread amount. Any of these would otherwise enter the ledger silently and be discovered months later, if ever.

const result = reconcile(extraction);
switch (result.status) {
  case "matched":
    return proceed();
  case "mismatched":
    throw new ImportBlocked(
      `Reconciliation failed: declared closing ${result.declaredClosing}, ` +
      `computed ${result.computedClosing}, delta ${result.delta}. ` +
      `Likely a dropped or misparsed row. Import blocked.`,
    );
  case "running_balance_break":
    // An account declaring no opening or closing balance, only a running column. A break
    // localises the fault to one row rather than the whole batch.
    throw new ImportBlocked(
      `Running balance breaks at row ${result.firstDivergentRow}: ` +
      `${result.previousBalance} plus ${result.amount} ` +
      `should be ${result.computedClosing}, statement says ${result.declaredClosing}.`,
    );
  case "unavailable":
    // The configured evidence did not extract. Blocks like the other two.
    throw new ImportBlocked(`Reconciliation evidence unavailable: ${result.message}`);
}

A mismatch blocks the import. Not a warning — a block. Wrong financial data is worse than absent financial data, because absent data announces itself and wrong data does not.

When it blocks, the diagnostics panel shows the computed running balance beside each row so the divergence point is visible immediately. In practice this turns a parser bug from an afternoon of confusion into a two-minute fix.

unavailable blocks too. The has_a_balance_anchor CHECK means every saved layout declares a closing balance pattern or a running-balance column, so the verdict never means "this statement has no balances". It means the configured evidence did not extract — a shifted band, a changed label or a parse regression — and the message points at remapping the layout rather than at the rows. Letting it through would import rows that bypassed reconciliation entirely, which is the one thing this stage exists to prevent. A genuinely anchorless source, if one ever exists, is an explicit case for the milestone that meets it, not this value. (The draft preview in the layout mapper is the one place the verdict renders without blocking anything: an auto-proposed draft has no anchors yet, and nothing is being staged.)

9. Stage 9 — Staging

CREATE TABLE staged_transaction (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  import_batch_id      UUID NOT NULL REFERENCES import_batch(id) ON DELETE CASCADE,
  household_id         UUID NOT NULL REFERENCES household(id),

  -- normalized, same shape as transaction

  description_raw      TEXT NOT NULL,

  fx_rate_is_carried   BOOLEAN NOT NULL DEFAULT false,

  -- proposals, all overridable in review

  proposed_merchant_id    UUID REFERENCES merchant(id),
  proposed_payment_method payment_method,
  proposed_country        CHAR(2),
  classified_by           classified_by NOT NULL DEFAULT 'unclassified',
  classification_rule_id  UUID REFERENCES classification_rule(id),

  -- transfer candidacy
  proposed_transfer_peer_staged_id UUID REFERENCES staged_transaction(id),
  proposed_transfer_peer_txn_id    UUID REFERENCES transaction(id),
  transfer_match_confidence        NUMERIC(4,3),
  proposed_transfer_kind           transfer_kind,

  -- dedupe
  dedupe_hash              TEXT NOT NULL,
  duplicate_of_transaction_id UUID REFERENCES transaction(id),
  near_duplicate_of_id     UUID REFERENCES transaction(id),

);

CREATE INDEX idx_staged_batch ON staged_transaction (import_batch_id, status);

raw_row retains the parser's original view of the data. When a classification looks wrong six months later, the question "what did the statement actually say?" is answerable without reopening the PDF.

10. Stage 10 — Review

The screen where a month's import is confirmed. It should be fast enough to be pleasant, because it is the recurring cost of using the product.

Grouping, most-attention-needed first:

⚠  Blocked            reconciliation failed — resolve before importing
🔁 Transfers          4 candidate pairs, high confidence pre-ticked
❓ Unclassified       11 rows with no category
⚡ Low confidence     6 rows classified below threshold
✓  Ready             183 rows, classified with high confidence   [collapsed]
⊘  Duplicates         27 rows already present                     [collapsed]

Interactions

  • Keyboard-first. j/k to move, c to categorize, t to toggle transfer, x to exclude, Enter to accept, ⌘Enter to import all. Reviewing 200 rows with a mouse is why people abandon these tools.
  • Bulk apply — select several rows, categorize together.
  • Rule creation inline — categorizing offers "always categorize TALABAT* as Food & Dining → Delivery", with a live count of how many past and future rows it affects.
  • Original visible — each row shows description_raw and links to the source document at the right page.
  • Running totals update live so the shape of the month is visible before committing.

Nothing imports without a click in Phase 1. Confidence pre-sorts and pre-ticks; it never decides.

11. Stage 11 — Commit

BEGIN;
  INSERT INTO transaction (...) SELECT ... FROM staged_transaction
    WHERE import_batch_id = $1 AND status = 'accepted';

  INSERT INTO transfer (...)      -- confirmed pairs
  UPDATE transaction SET transfer_id = ... , txn_type = 'transfer_in'|'transfer_out';

  INSERT INTO card_statement (...)  -- if the document was a card statement

  UPDATE account SET current_balance = ..., current_balance_as_of = now()
    WHERE id = $account;

  -- verify against the statement one final time
  -- raises and rolls back the whole batch on mismatch
  PERFORM assert_account_reconciles($account, $declared_closing);

  UPDATE import_batch SET status='completed', rows_imported=..., completed_at=now();
COMMIT;

All or nothing. A partial import leaves the ledger in a state that reconciles against nothing and is worse than no import at all.

Post-commit, asynchronously: net-worth snapshot, holdings, XIRR, recurring-series detection.

12. The import screen

There is no CLI (ADR-0013). Everything a CLI would have done is a screen.

Was going to be Is
oneledger import ~/statements/2026-09/ /import — drop a folder's worth of files into the picker; each is fingerprinted, parsed and reconciled independently, with per-file status
oneledger import --dry-run The same screen. Nothing is written until Stage batch is pressed; the parse, reconciliation and classification summary are all visible first
oneledger parse --show-rows --show-running-balance Diagnostics panel on the import screen — the extracted rows beside the computed running balance, with the divergent row highlighted. The first thing to open when a bank changes layout
oneledger fx backfill / fx check Settings › FX — a date range and a Backfill button; a rate inspector showing source and carry-forward status
oneledger doctor Settings › Data Quality — already specified there in 12 §5
oneledger recompute balances|networth|xirr|holdings Settings › Maintenance — buttons calling the corresponding Postgres functions
oneledger stats classification Settings › Rules — coverage, hit counts, override counts, top unclassified descriptions

Multi-file import is the common case. Selecting twelve months of one account, or one month of seven accounts, is a single drop. Each file gets its own import_batch and its own reconciliation verdict, so one bad statement blocks only itself.

13. Institution notes

Parser-specific quirks, recorded as they are discovered. Populated during M2–M3; the structure matters more than the current contents.

Observed directly from the 71 statements gathered (Jan 2025 – Sep 2026). Every institution is PDF-only; no CSV or Excel export exists from any of them — which is why M2 is planned around the easiest PDF rather than a CSV.

These are field notes, not a supported-institutions list. Layouts are rows created through the mapping UI (ADR-0012); nothing below is compiled into the product. It is recorded because it is what the engine and the quirk vocabulary were designed against, and because a future layout change is easier to diagnose with a note of what the format looked like before.

Layout Files Encrypted Reconciliation anchor Known quirks
UAE card (Skywards + noon One) 38 No Header block: credit limit, statement date, due date, minimum due One issuer, one layout for both cards. Bilingual AR/EN — Arabic text interleaves in extraction order, so filter by script or use x-position. Credits carry a CR suffix; debits are bare. inverts_sign = True
Axis (2 accounts) 6 No Declares OPENING BALANCE and a running balance column Tran Date · Chq No · Particulars · Debit · Credit · Balance · Init.Br. Multi-line particulars. Trailing legend page of abbreviation definitions must not be parsed as rows. (cid:9) artefacts in that legend
UAE current account 20 No Running balance column only — no declared opening/closing Reverse-chronological. Two physical lines per transaction. Balance carries a Cr suffix. Remittance narration embeds destination INR amount and achieved rate
HDFC (2 accounts) 6 Yes ClosingBalance column per row Encrypted — the user is prompted per file. Text extracts with no spaces (Statementofaccount) — flattened-text regex is impossible here; word coordinates are mandatory. Date · Narration · Chq./Ref.No. · ValueDt · WithdrawalAmt. · DepositAmt. · ClosingBalance

Where no opening/closing balance is declared — the UAE current account — reconciliation uses the running balance column instead, asserting balanceₙ = balanceₙ₋₁ + amountₙ for every consecutive pair. That is a stronger check than the opening/closing bridge, because it localises a divergence to a specific row rather than reporting a batch-level delta.

Test fixtures are redacted. Real statements never enter the repository. Fixtures keep layout and structure with substituted amounts, dates and account numbers, and each carries a README.md recording which real statement's structure it reproduces.

14. Acceptance criteria

  1. A real statement from each of the six institutions imports with zero manual correction of dates or amounts.
  2. Reconciliation passes for every one of them.
  3. Re-importing an identical file imports zero rows and names the original import.
  4. An overlapping statement imports only the non-overlapping rows.
  5. A deliberately corrupted amount fails reconciliation and blocks the batch.
  6. Two identical-amount same-day transactions both import (the reference/ordinal disambiguates).
  7. A password-protected PDF imports without the password touching disk or database.
  8. 200 rows are reviewable in under 10 minutes.
  9. Every imported row traces to document, page and row number.
