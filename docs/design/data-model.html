03 — Data Model

PostgreSQL 18. Every monetary value is NUMERIC — never float, real or double precision. Every table carries household_id for row-level security and future household support.

Read multi-currency-and-fx.html first. The frozen-amount columns below only make sense with that model in hand.

1. Conventions

Sign convention (Invariant I2)

Every balance and every amount is signed from the household's perspective.

Positive Negative
Balance You own it You owe it
Transaction amount Money entered the account Money left the account

This holds for liability accounts without special-casing:

Event Account Amount Effect on balance
Salary credited Savings +18,000 −→ more positive
Rent paid Savings −5,000 −→ less positive
Card purchase Credit card −310 −→ more negative (owe more)
Card payment Credit card +3,900 −→ less negative (owe less)
Home loan EMI Home loan +42,000 principal portion −→ less negative

Consequences that make this worth the discipline:

balance    = opening_balance + SUM(amount)        -- works for every account type
net_worth  = SUM(balance_in_base)                 -- one aggregate, no CASE, no subtraction

The display layer flips signs for liability screens ("You owe AED 4,500"). The database never does. Sign confusion in liability handling is the single most common source of wrong numbers in personal finance software, and it is designed out here rather than tested for.

Naming and types

Concept Type Note
Money NUMERIC(20,4) 4 dp handles fils/paise and rate-derived precision
Units (securities) NUMERIC(28,8) Mutual fund units go to 3–4 dp; 8 is safe
Price / NAV NUMERIC(20,6)
FX rate NUMERIC(20,10)
Percentage NUMERIC(9,4) Stored as 15.2500 for 15.25%, never as 0.1525
Currency CHAR(3) ISO 4217
Country CHAR(2) ISO 3166-1 alpha-2
Identifier UUID gen_random_uuid()
Timestamp TIMESTAMPTZ Always UTC
Business date DATE Never a timestamp — a transaction happens on a date, not an instant

Every table has created_at TIMESTAMPTZ NOT NULL DEFAULT now(); mutable tables also have updated_at maintained by trigger.

3. Identity and tenancy

Single user now, household-capable from day one (ADR-0004). The columns exist and RLS uses them; no multi-user behaviour is built.

TableWhat it holds
householdName and the reporting pair: base_currency (the default) and secondary_currency (the toggle).
personDisplay name, is_self, tax residency, and last four only of a tax ID and a national ID (PAN and Emirates ID, in the first deployment). Full numbers are never stored.
app_userThe stable local UUID, owner role and normalized email; nullable unique google_subject binds the verified Google identity on first login.
app_sessionA random session id, local owner, expiry and optional revocation time. Every cookie must match an active row.

Full DDL: schema.md 0002 and V5.

Since ADR-0013, RLS is defence in depth rather than the primary boundary. The Python service connects with the service-role key and therefore bypasses these policies; it enforces authorization itself, scoping every query to the household resolved from the request's signed claims and active session record. The policies below are kept because they cost nothing to maintain, they remain correct, and they protect any future client that connects as a user rather than as the service.

What is genuinely lost is the property that a forgotten WHERE clause returned nothing. It would now return another household's rows — in a system that has one household and is permanently single-tenant, but the guarantee is gone, not relocated. This is recorded in security-and-privacy.html §3 as a deliberate trade.

RLS pattern. The household lookup goes through a SECURITY DEFINER function, never an inline subquery:

-- SECURITY DEFINER is load-bearing. An inline `SELECT household_id FROM app_user ...` inside
-- app_user's own policy re-enters that policy and Postgres raises infinite recursion — which,
-- because every other policy depends on the same lookup, fails reads across the application.
-- Running as the function owner (who bypasses RLS) breaks the cycle.
CREATE FUNCTION current_household_id() RETURNS UUID
  LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public
AS $$
  SELECT household_id FROM app_user
  WHERE id = NULLIF(current_setting('app.user_id', true), '')::UUID AND role = 'owner'
$$;

ADR-0014 removed Supabase, and with it auth.uid(). Identity now comes from a session variable the service sets on the connection after it has authorized the request:

SET LOCAL app.user_id = '<uuid>';   -- per transaction, by the service

current_setting(..., true) returns NULL rather than raising when the variable is unset, so a connection that never scopes itself sees nothing rather than everything. Everything downstream of current_household_id() is unchanged.

Applied to every household-scoped table:

ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;

CREATE POLICY household_isolation ON <table>
  USING (household_id = current_household_id());

Tables that carry system seed rows need a wider read policy. institution, category, merchant and security use a nullable household_id, where NULL means "shipped with the product". NULL = <uuid> evaluates to NULL, not true, so the policy above would hide every seeded institution and the entire seed taxonomy — breaking M1 and M4 outright:

-- read: own rows plus the shared seed set
CREATE POLICY household_read ON <seeded_table> FOR SELECT
  USING (household_id IS NULL OR household_id = current_household_id());

-- write: own rows only. The seed set is not user-modifiable in place; a user who wants a
-- different Groceries category edits a copy scoped to their household.
CREATE POLICY household_write ON <seeded_table> FOR ALL
  USING (household_id = current_household_id())
  WITH CHECK (household_id = current_household_id());

Even with one user, RLS is enabled everywhere. A missing WHERE clause in application code then returns nothing rather than everything, and the policy is already correct on the day a second person is added. See security-and-privacy.html.

Authenticated is not the same as permitted

Google will authenticate any Google account. A valid sign-in proves identity and nothing more. Authorization is the service's job (ADR-0013): it checks the address against ALLOWED_USER_EMAIL, resolves the session to an active, unexpired and unrevoked app_session row joined to an owner app_user whose normalized address matches the pinned address, and only then scopes the database connection with SET LOCAL app.user_id.

An unscoped connection therefore reads nothing, because every policy predicate is NULL. The remaining hole is SECURITY DEFINER functions, which bypass RLS by design:

-- Called first by every SECURITY DEFINER function. Authentication is not authorization.
CREATE FUNCTION assert_is_owner() RETURNS VOID
  LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = public
AS $$
BEGIN
  IF current_household_id() IS NULL THEN
    RAISE EXCEPTION 'not authorized' USING ERRCODE = '42501';
  END IF;
END $$;

current_household_id() is the one exception, and safely so: it returns NULL rather than data for an unknown caller, which is precisely the behaviour the policies rely on.

V7 seeds one neutral household and person so an owner row can exist before the first sign-in. No currency code is written in the migration: the reporting pair is the first two seeded currencies by code, and the owner chooses the real pair in Settings before the first import. reporting_pair_is_locked() answers whether any household-scoped table already holds a frozen amount_base. update_household_configuration(...) is the single owner-guarded write: it locks the household row, refuses an identical pair, and refuses a pair change once amounts are frozen (ADR-0002).

FX rates

Global, not household-scoped — rates are public data. That does not mean unprotected.

If the service ever connects as a role other than the owner, RLS is what gates it. A table with RLS enabled and no matching policy denies everything; a table with RLS disabled falls back to those grants — so leaving RLS off here would let any authenticated Google account UPDATE the entire historical rate table directly, corrupting every balance conversion and every future import.

Reference tables therefore enable RLS with a read-only policy, and all writes go through a SECURITY DEFINER function that calls assert_is_owner() first:

ALTER TABLE fx_rate  ENABLE ROW LEVEL SECURITY;
ALTER TABLE currency ENABLE ROW LEVEL SECURITY;
ALTER TABLE price_snapshot ENABLE ROW LEVEL SECURITY;

-- Readable by anyone signed in. No INSERT/UPDATE/DELETE policy exists, so writes are denied
-- to every role except through the vetted functions.
CREATE POLICY reference_read ON fx_rate        FOR SELECT TO authenticated USING (true);
CREATE POLICY reference_read ON currency       FOR SELECT TO authenticated USING (true);
CREATE POLICY reference_read ON price_snapshot FOR SELECT TO authenticated USING (true);

Keyed on (rate_date, base_currency, quote_currency), with the rate as NUMERIC(20,10). Every row records its provenance: source is ecb, derived_peg, manual or actual_transfer, and a carried-forward rate must name the date it came from — a CHECK enforces that, so a derived value can never masquerade as an observed one (Invariant I7).

6. Categories and merchants

Two enums carry the meaning: category_kind (income/expense/transfer/investment/debt) and category_bucket (need/want/investment/debt_service/income/ignore). category is a two-level tree; the depth limit is a trigger, not a CHECK, because a subquery in a CHECK is not valid PostgreSQL. The seeded tree is versioned shared data: a household's bucket or activity choice on a seed row is a category_override row (V11) merged over it on read, never an edit of the seed itself, so seed updates stay recognisable and one household's choice is never another's default.

Full DDL: schema.md 0006.

The two-level CHECK above is illustrative — a subquery in a CHECK is not valid PostgreSQL. It is implemented as a BEFORE INSERT OR UPDATE trigger. Noted explicitly so it is not copied verbatim into a migration.

The bucket column is what makes Needs/Wants/Investments/Debt free. One classification pass yields both the detailed category tree and the coarse view, without asking for the same judgement twice (ADR-0008). Seed taxonomy is listed in classification.html §3.

One merchant, many merchant_alias rows — because the same coffee shop appears as STARBUCKS DUBAI MALL, STARBUCKS #4471 DXB and SBUX DUBAI across three statements. Each alias carries a pattern_kind (exact, prefix, contains, regex) and a priority, and counts how often it has matched.

Splits: the container-versus-posting rule

Splitting one ₹8,000 supermarket bill into ₹6,500 groceries and ₹1,500 household creates child rows via parent_transaction_id. Both the parent and its children then exist in transaction, so a naive opening_balance + SUM(amount) counts the movement twice.

The parent's amount cannot simply be zeroed — it is the bank's figure and is immutable (I1).

Rule: a row with children is a container, not a posting. Only leaf rows count.

-- A row is a posting unless something points at it as a parent.
CREATE VIEW v_transaction_posting WITH (security_invoker = true) AS
SELECT t.* FROM transaction t
WHERE NOT EXISTS (SELECT 1 FROM transaction c WHERE c.parent_transaction_id = t.id);

Balances, cash flow and every category report read leaf rows. The parent keeps its immutable amount, its description_raw and its document provenance (I6); the children inherit account_id, booked_date, source_document_id and the frozen FX columns from it, and differ only in amount, category_id and notes.

A constraint trigger asserts children sum exactly to the parent, so a split can never change an account's balance:

-- SUM(child.amount) = parent.amount, enforced at statement end
CREATE CONSTRAINT TRIGGER trg_split_sums_to_parent
  AFTER INSERT OR UPDATE OR DELETE ON transaction
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION assert_split_sums_to_parent();

Splits are one level deep. A child cannot itself be split — the trigger rejects it — because nothing in the product needs it and the leaf rule stays trivially correct.

The reporting guard view (Invariant I3)

The exclusion of transfers is enforced in the database, not in application code, so no future query can forget it.

-- security_invoker is load-bearing, not a stylistic choice. A PostgreSQL view evaluates its
-- base-table access as the view *owner* by default, and the owner bypasses RLS — so without
-- this, any authenticated caller reads every household's transactions through the view that
-- exists to make reporting safe. Requires PG15+; the stated target is 18.
CREATE VIEW v_transaction_reportable WITH (security_invoker = true) AS
SELECT *
FROM   v_transaction_posting           -- split parents excluded; only leaf rows post
WHERE  transfer_id IS NULL             -- a transfer leg is never income or expense
  AND  is_excluded = false
  AND  txn_type NOT IN ('opening_balance','adjustment',
                        'transfer_in','transfer_out',
                        'investment_buy','investment_sell','investment_income',
                        'loan_disbursement','loan_repayment');

This view is built on transaction, and the leaf rule above applies to it too: a split parent is excluded because its children carry the categories. v_transaction_reportable therefore selects from v_transaction_posting, not from transaction directly.

Every cash-flow, budget, spending and savings-rate query reads this view, never the base table. A static check enforces it (testing-and-data-quality.html).

Investment and loan flows are excluded here because they are balance-sheet movements, not consumption. They have their own views:

CREATE VIEW v_investment_flow WITH (security_invoker = true) AS
  SELECT * FROM transaction
  WHERE txn_type IN ('investment_buy','investment_sell','investment_income')
    AND is_excluded = false;

CREATE VIEW v_debt_service_flow WITH (security_invoker = true) AS
  SELECT * FROM transaction
  WHERE txn_type = 'loan_repayment' AND is_excluded = false;

8. Transfers

A transfer links two legs and records what the movement actually cost. Beyond the two account and two transaction references it holds source_amount/destination_amount with their currencies, and the FX truth: implied_rate (what you got), market_rate (what it was worth), fx_spread_pct, fx_spread_cost_source, explicit_fee_amount and total_cost_source. Plus transfer_kind, provider, match_confidence and status (candidate/confirmed/rejected).

Full DDL: schema.md 0010.

The partial unique indexes stop one transfer from claiming the same transaction twice in the same role. They do not stop one transaction from being the source of transfer A and the destination of transfer B — each index is satisfied independently, while transaction.transfer_id can only point at one of them, leaving the other silently inconsistent.

The matcher will not produce that pairing (it scores only debit→credit, so a row is a plausible source or destination, never both), but manual linking (§6 of 07) can. The invariant is therefore enforced rather than assumed:

-- On confirmation, neither leg may already belong to a different confirmed transfer.
CREATE CONSTRAINT TRIGGER trg_one_transfer_per_leg
  AFTER INSERT OR UPDATE ON transfer
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW WHEN (NEW.status = 'confirmed')
  EXECUTE FUNCTION assert_legs_unclaimed();

assert_legs_unclaimed() raises if either leg's transaction.transfer_id is non-null and differs from NEW.id. Candidates may still overlap freely while the matching engine proposes alternatives; confirmation is what resolves to one.

This is test 8 of 07 §8, which the partial indexes alone would not have satisfied.

9. Credit card statements

One row per statement cycle: period and statement dates, payment due date, opening and closing balance (signed), statement_balance (positive — what was due), minimum due, total debits and credits, credit and cash limits, finance charges, late fees, reward points opening/earned/redeemed/closing, and whether it was is_paid_in_full with the payment transaction that settled it.

The sign is refused rather than trusted: statement_balance is never negative, and a cycle with a positive closing balance — a card in credit — has nothing due, so the amount due stored as the closing balance is a row the table will not hold (owed_is_negative, ADR-0010).

Utilisation is computed, not stored — ABS(closing_balance) / credit_limit. Storing it would be a second source of truth for the same fact.

XIRR

Computed from the holding's signed cash flows plus current value as a terminal inflow, solving:

Σ  CFᵢ / (1 + r)^(dᵢ − d₀)/365  =  0

by Newton–Raphson with bisection fallback (Newton alone diverges on irregular SIP series). Recomputed on any new investment transaction or price refresh, stored on holding, and stamped with xirr_computed_at so a stale figure is visible as stale.

Manual valuations

For property, physical gold, EPF, PPF — anything with no importable statement (ADR-0006).

“As of date X, this is worth Y.” Targets either an account or a holding — a CHECK enforces exactly one — and freezes the FX rates at as_of_date alongside the native value. Carries a method and a confidence, both displayed, never hidden.

Full DDL: schema.md 0014.

Carried forward flat, never extrapolated. The valuation in effect on any date is the most recent snapshot at or before it. A trend line between two snapshots is drawn as a step, not a slope, because a smooth line would imply knowledge that does not exist (Invariant I7).

Schedules are versioned rather than mutated. A rate change or prepayment generates schedule_version + 1; the prior version is retained. This preserves what was expected at the time, which is what makes "interest saved by prepaying" a computable number rather than a remembered one.

12. Documents and import

Every document carries its institution, type, period, currency, storage location, byte size, page count, and a SHA-256 checksum uniquely indexed per household, so a file has one row however often it is uploaded. What refuses a duplicate import is the checksum check (statement ingestion §2), run before the parse and again inside the staging transaction under the household lock. A batch that was cancelled does not count: re-importing its file reuses and refreshes the row. Parse status, the layout that produced it, and any parse error are recorded alongside.

Full DDL: schema.md V12 (applied).

At most one batch per document that is not cancelled; any number of cancelled attempts may name the same document, each keeping its own account, layout and period. Tracks status through the pipeline, row counts (extracted, new, duplicate, needs-review, imported, rejected), and the reconciliation verdict: declared opening and closing balance, computed closing, reconciliation_status and the delta. That last group is Invariant I8 made durable — the verdict is recorded for the batches that stage.

A blocked import records nothing at all: a reconciliation mismatch, a running-balance break, an unavailable verdict, an unidentified layout, an unresolved account, a missing rate or a parse failure leaves the database unchanged — no document, no batch, no staged row (I8's "stages zero rows"). It cannot be otherwise: document.sha256 is uniquely indexed per household, so a persisted blocked document would make its own checksum reject the retry after the owner re-maps the layout, which is the recovery path ADR-0012 exists to provide. The verdict travels in the POST /parse response body, where the diagnostics panel reads it.

Full DDL: schema.md V12 (applied).

Statement layouts

No bank name appears anywhere in application code (ADR-0012). A statement layout is a row, created through the mapping UI on first import of an unrecognised format. One generic extraction engine reads any profile.

No bank name appears anywhere in application code (ADR-0012). A layout is a row the user creates through the mapping UI, holding: detection fingerprints; the header-row pattern and column x-bands; date format, sign_convention, inverts_sign and chronological order; row-start and continuation rules; skip patterns for legend pages and footers; balance anchors; a small additive quirks vocabulary; and metadata patterns for card header blocks.

A CHECK requires either a closing-balance pattern or a running-balance column, so a layout that cannot be reconciled is rejected at creation rather than silently letting a mis-mapped column through.

Full DDL: schema.md V12 (applied).

has_a_balance_anchor is the constraint that keeps Invariant I8 enforceable: a layout must offer some way to verify the extracted rows, either a declared closing balance or a running balance column. A profile that offers neither cannot be reconciled, and would let a mis-mapped column through silently — so it is rejected at creation.

staged_transaction mirrors transaction's shape plus review metadata, and carries the parser's original view of each line in raw_row — so "what did the statement actually say?" stays answerable without reopening the PDF. The pipeline stage it serves is statement-ingestion.html §9.

source_row_number is NOT NULL (V16). Every writer types it and every reader requires one — reconciliation names its divergent row by it, and the review payload labels each row by it — so a null was a row nothing could produce and nothing could review. Its counterpart on transaction stays nullable: a manually entered transaction comes from no statement and has no row to name.

import_batch.period_is_derived (V17) records whether the batch's period came from the rows' own dates or from the statement's own words. The two are indistinguishable afterwards — a period derived from rows dated 1 and 2 March looks exactly like one stated as 1–2 March — so the review payload reads the recorded flag rather than inferring one, and a batch staged before the column says it recorded none (Invariant I7).

Full DDL: schema.md V13, V16 (applied).

13. Classification rules

A rule matches when every non-null condition matches; absent conditions are ignored. Matchers cover description pattern and kind, account, currency, amount range or exact, direction, country and reference pattern. Outcomes set category, merchant, txn type, payment method, country, tags, or flag the row as a transfer candidate with a counterparty account. priority ascends — user rules default to 100, seed rules to 500, so a user rule always wins without either needing to know about the other.

15. Audit log

Why every child table carries household_id

A foreign key to an RLS-protected parent gives a child no protection whatsoever. PostgREST exposes every table directly, so payslip_line, loan_schedule_entry, loan_event and budget_line are each independently queryable — and salary line items or a loan's amortisation are exactly as sensitive as their parents.

The parent's policy does not cascade, and a join-based policy costs a subquery on every row read. So the rule is flat and mechanical: every household-owned table carries household_id and the same policy, including child tables where the column is strictly redundant with the parent's. Redundancy is cheaper than a leak.

The exceptions, and the reason each is safe:

Table Why no household_id
currency, fx_rate Public reference data. Exchange rates are not private
price_snapshot Market prices for securities. Not private, and shared across households by design
household Scoped on its own id: USING (id = current_household_id())

Written by trigger on transaction, account, transfer, loan, holding and valuation_snapshot, so it cannot be bypassed by forgetting to call a logging function. The circular references

transaction references transfer, card_statement, investment_transaction, loan, loan_schedule_entry and recurring_series. Every one of those tables is created after transaction, and transfer references transaction back. V10 (schema.md section 0007) therefore cannot declare those columns as foreign keys — the targets do not exist yet.

The columns are created as bare UUID in V10, and each constraint lands with the migration that creates its target — not earlier, and not all together in a trailing migration. V12 already did this for the four whose targets it creates (source_document_id, receipt_document_id, import_batch_id, statement_layout_id); classification_rule_id gains its foreign key with M4's migration. The clauses below are the remaining eventual set (schema.md section 0018), each added by the migration that creates the table it points at:

ALTER TABLE transaction
  ADD CONSTRAINT fk_txn_transfer     FOREIGN KEY (transfer_id)       REFERENCES transfer(id),
  ADD CONSTRAINT fk_txn_card_stmt    FOREIGN KEY (card_statement_id) REFERENCES card_statement(id),
  ADD CONSTRAINT fk_txn_inv_txn      FOREIGN KEY (investment_transaction_id)
                                     REFERENCES investment_transaction(id),
  ADD CONSTRAINT fk_txn_loan         FOREIGN KEY (loan_id)           REFERENCES loan(id),
  ADD CONSTRAINT fk_txn_loan_entry   FOREIGN KEY (loan_schedule_entry_id)
                                     REFERENCES loan_schedule_entry(id),
  ADD CONSTRAINT fk_txn_recurring    FOREIGN KEY (recurring_series_id)
                                     REFERENCES recurring_series(id);

The schema listing in §7 shows the columns with their eventual REFERENCES for readability. The migration order is what is authoritative.

No down-migrations. For a single-user system, a mistake is corrected by a new forward migration against a restored backup — which is simpler and safer than maintaining reversibility that would be exercised roughly never.
