02 — Architecture

Constraint that shapes everything: near-zero infrastructure spend. Localhost first, one small VPS when it earns it — ADR-0014 settled this at roughly $5–12 a month with no usage pricing, replacing the free-tiers-only rule the earlier drafts were written under.

That constraint turns out to produce a better architecture than an unconstrained one would, for reasons set out in §2.

1. The shape

   ┌───────────────────────────────────────────────────────────┐
   │  React · Next.js · TypeScript · Tailwind                  │
   │  runs on localhost:3000                                   │
   │                                                            │
   │  UI only: review queue · dashboards · layout mapping      │
   │  No business logic. No parsing. No money arithmetic.       │
   └───────────────────────┬───────────────────────────────────┘
                           │  HTTP (localhost)
   ┌───────────────────────▼───────────────────────────────────┐
   │  FastAPI · Python 3.14                                    │
   │  runs on localhost:8000                                   │
   │                                                            │
   │  parse (pdfplumber) → normalize → dedupe → FX freeze      │
   │       → reconcile → stage                                  │
   │  classify · match transfers · XIRR · amortisation          │
   │                                                            │
   │  Statements are parsed on your machine and never           │
   │  transit a third-party host.                               │
   └───────────────────────┬───────────────────────────────────┘
                           │  service-role connection
   ┌───────────────────────▼───────────────────────────────────┐
   │  POSTGRES 18                                              │
   │  the single source of truth                                │
   │  constraints · triggers · reporting views                  │
   └───────────────────────────────────────────────────────────┘

   All four run as containers in one compose file, on your laptop
   now and on one small VPS later.          (ADR-0014)

Three pieces, each with one job: React renders, Python computes, Postgres guarantees.

The invariants live in Postgres, not in Python. A backend is a convenient place to put logic and a poor place to put guarantees — so the constraints, the triggers and the reporting views stay where no code path can route around them (ADR-0013).

2. Why a Python service

Two earlier designs put this logic elsewhere, and each recorded its own cost:

  • An earlier decision put classification and transfer matching in Postgres — "harder to unit-test than Python".
  • Another put parsing in the browser — "~200 lines of word grouping that pdfplumber gives free".

Both costs existed only because there was no backend. Matching went to SQL because two clients needed it; parsing went to the browser because the alternatives were a CLI (rejected as the wrong interface for a monthly task) or a hosted server (which would put statements on a third-party host). Adding a local service dissolves both rather than trading between them.

What is not the argument: that Python extracts PDFs better. That was measured and found false — on the hardest of the four layouts pdfplumber recovers no more than pdf.js does. The real arguments are that iterating a parser against 71 real files wants a REPL and a breakpoint, that one backend means one implementation of the trickiest semantics, and that OCR and spreadsheet support become additive rather than a new component.

Local, not hosted. The service runs on localhost. That preserves the privacy property the original sketch was protecting, without the CLI that made importing a terminal command — you drop files into the web app and it posts them to the service.

Which versions, and why

Newest stable at project start, because the support window is the constraint. Nothing here is deployed yet, so there is no upgrade to weigh against — the only cost of starting a major version behind is arriving at end-of-life sooner, for no benefit.

Postgres 18      security support to Nov 2030   (15 ends Nov 2027)
Python 3.14      security support to Oct 2030   (3.12 ends Oct 2028)
Node 24 LTS      maintenance to Apr 2028        (26 becomes LTS Oct 2026)

Node stays on 24 because it is the active LTS line today and 26 does not become one until October 2026. Everything else — FastAPI, Pydantic, Next.js, React — moves on its own release cadence and is pinned only by a floor in pyproject.toml and package.json.

Two version-specific notes, checked 2026-09-05:

  • security_invoker views require PG15 or newer. That floor is what data-model.html §6 depends on; 18 is simply where the target sits.
  • PG18 makes uuidv7() available, which would give time-ordered primary keys and better index locality than gen_random_uuid(). Not adopted. The benefit is real at millions of rows and invisible at twenty thousand, and a v7 UUID embeds its creation time in every id the UI puts in a URL. Revisit if the ledger ever gets large enough for insert locality to show up in a query plan.

Money crosses the wire as a string. A JSON number is an IEEE-754 float by the time it reaches React, and the precision is gone before anyone can check. Python holds Decimal, Postgres holds NUMERIC, and the wire holds "-310.0000". React formats it and performs no arithmetic on it — enforced by lint.

5. Data flow: an import

1.  You      open /import and drop 6 PDFs into the file picker
2.  Web      POST /parse  (multipart) → localhost:8000, one request per file
3.  API      SHA-256 each file → skip anything already in `document`
4.  API      detect layout by fingerprint against saved profiles
5.  API      prompt needed? return 409 with `password_required` for that file
6.  API      pdfplumber → words → apply the layout profile → raw rows
7.  API      normalize: dates, signs, currency, description cleanup
8.  API      compute dedupe_hash → mark duplicates against existing rows
9.  API      fetch missing FX rates → freeze amount_base / amount_secondary
10. API      classify through the deterministic cascade
11. API      propose transfer matches, scored
12. API      reconcile: opening + Σ rows = declared closing?   ← blocks on mismatch
13. API      write the original to the documents volume; write document, import_batch,
             staged_transaction — one database transaction
14. You      review: confirm categories, confirm transfers, fix anything wrong
15. Web      POST /import/{batch}/commit → staged rows become transaction rows
16. API      balances, net worth snapshot, holdings recomputed

Steps 3–13 are one HTTP call per file. The file bytes reach the service and the documents volume, and nowhere else.

Nothing is written until the batch reconciles. A failure at step 12 returns the divergent row and leaves the database untouched — no orphaned document row to clean up.

6. Data flow: a morning dashboard load

Browser → Next.js → GET /dashboard on the Python service
                  → 4 queries against pre-computed tables:
                       net_worth_snapshot        (latest row)
                       v_monthly_cashflow        (current month)
                       holding + price_snapshot  (portfolio value)
                       card_statement            (what is due)
                  → one JSON payload → render

Headline figures are indexed row reads against pre-computed snapshots, not aggregations over the whole ledger. No loading spinner ever appears where a number belongs.

The service is on the read path. That is the cost of a backend: if it is not running, the dashboard has no data. Acceptable while everything is local, and the first thing to reconsider when the cloud question is taken up (§11).

7. Environments

There is one environment definition. The compose file that runs on your laptop is the one that runs on the VPS (ADR-0014); only the .env and whether Caddy is enabled differ.

services:
  caddy    reverse proxy · automatic TLS        (hosted only)
  web      Next.js                              :3000
  api      FastAPI                              :8000
  db       Postgres 18                          :5432
volumes:
  pgdata      the ledger
  documents   original statements

docker compose up brings up the whole system with no network dependency beyond the FX rate fetch. Development works offline.

Promotion is git pull && docker compose up -d --build on the box. Migrations run forward against it. There is no staging environment — for a single-user personal system, one would cost more attention than it saves.

PDF passwordsPosted with the file, held in memory for the parseWritten to disk, a keychain, the database or a log

A privileged database connection is back, and that is a real loss. Parsing in the browser had removed it entirely by making the browser write as the signed-in user under RLS. A backend holds credentials, so they return to the threat model. They are confined to one process on one machine, never reach the browser, and security-and-privacy.html §3 records what now stands in for RLS as the authorization boundary.

9. Sizing

The free-tier arithmetic this section used to contain is obsolete (ADR-0014) — you size the box rather than fitting inside someone's allowance.

The workload is small. Thirty-six months of transactions is on the order of 30,000 rows; statements, payslips and receipts are roughly 100 MB of PDFs; one user generates a handful of page loads a day. The only burst is a monthly import, which is CPU-bound for seconds at a time.

ResourceNeeds
RAM1–2 GB. Postgres and two small application containers. Parsing a statement is measured in tens of megabytes
Disk10–25 GB. The ledger is a few hundred megabytes with indexes; documents grow by roughly 40 MB a year
CPUOne shared core. The monthly import is the only load that registers
BandwidthNegligible

That is the smallest instance every provider sells — roughly $5–12 a month at DigitalOcean, Hetzner or Railway. The bill does not grow with the ledger, which is the property that matters: no per-row, per-seat or per-request pricing to be surprised by.

Growth would be gradual and visible: documents are the only thing that accumulates, and at 40 MB a year the first disk resize is years away.

10. Backups

The one place where "personal project" is not an excuse. Hours of downtime are fine; losing the ledger is not.

Daily    pg_dump → gzip → local disk, 30 days retained     scripts/backup-db.sh
Weekly   documents volume → local disk                     scripts/backup-docs.sh
Monthly  copy of both to a second physical location

Restore is tested quarterly against a scratch database, and the test is a checklist item in testing-and-data-quality.html. A backup that has never been restored is a hypothesis, not a backup.

Keep ~/statements/ outside the repository as a second copy of the source data. The ledger can be rebuilt from the original files if it ever comes to that — which is a quiet argument for keeping the parsers deterministic and versioned.

11. Deployment

Nothing is deployed yet, and nothing needs to be until Phase 1 is done. This section records the target so the local build does not accumulate work that would have to be undone to reach it (ADR-0014).

One VPS. One compose file. Caddy terminates TLS and proxies to web; web talks to api; api talks to db. Only Caddy is exposed.

What hosting changes

ConcernLocalHosted
TLSNone neededCaddy, automatic
Google OAuth redirectlocalhostThe real hostname — both registered in the Google console
Secrets.env, git-ignoredSame file, on the box, mode 600
BackupsNightly to local diskNightly on the box, copied off it
AccessNothing exposedSSH keys only, no password auth, firewall to 22/80/443

What it does not change

The schema, the module boundaries, the data flow, and the fact that statements are parsed by software you run on a machine you control. That last point is why this arrangement is the first one that can put the whole system in the cloud without contradicting security-and-privacy.html §8.

What it costs you in attention

You administer a machine: unattended security upgrades, a firewall, an SSH key rather than a password, and a restore you have actually tested. That last one is not optional — one box is one point of failure, and the quarterly restore test in testing-and-data-quality.html §7 stops being belt-and-braces over a managed service and becomes the only thing standing between you and losing the ledger.
