06 — Classification

The Phase 1 and Phase 2 application makes no LLM calls. The cascade below is fully deterministic and inspectable — every classification can name the rule that produced it. A model fallback is a Phase 5.3 consideration only (ADR-0003).

ADR-0020 permits owner-delegated assistance now: the agent can research public provider identities, preview and save supported merchant rules, classify clear cases and ask grouped questions about uncertainty. Payment rails and personal names alone do not establish purchase categories. Existing overrides are preserved; embedded AI, automatic correction learning and unattended operation are not implied.

This is not a limitation being worked around. A rule engine that is genuinely good is faster, free, offline, reproducible and debuggable — and it sets the bar that any later model has to beat. Most personal spending is a few hundred recurring merchants; that is a pattern-matching problem, not a language problem.

1. The cascade

Evaluated in order. First match wins and evaluation stops.

1  Explicit user override on this transaction    →  classified_by = user_manual
2  User rule, by priority                        →  classified_by = user_rule
3  Private knowledge / merchant alias match      →  classified_by = merchant_alias
4  Recurring series match             [Phase 2]  →  classified_by = recurring_series
5  Prior classification, same account + text     →  classified_by = prior_match
6  Seed rule                                     →  classified_by = seed_rule
7  No match                                      →  classified_by = unclassified
                                                     → Transactions → Needs a category

Private knowledge is household-only and carries its evidence, economic role, direction and optional account scope. Within this step, lower priority wins; then exact beats prefix, prefix beats contains, and contains beats regex; then the longer, more specific service name wins. If equally strong matches propose different outcomes, the engine abstains as unclassified instead of depending on database order. This is what lets a provider's purchase service outrank its parent brand while keeping its wallet role separate.

Prior matches learn only from direct owner decisions and still-active user rules. An alias decision cannot prove its originating evidence is still active on an older transaction, so it is not promoted into a prior; nor is a prior or seed decision. No prior may propagate a report-excluding transfer, investment, loan, adjustment or opening-balance type. Priors match only within the same posting direction, and conflicting equally strong outcomes abstain. Those meanings require explicit knowledge or review.

classified_by and classification_rule_id are stored on every transaction, so the UI can always answer "why is this Food & Dining?" — which is what makes the engine trustworthy enough to rely on.

An unclassified row asks in the Transactions ledger, not while it is still staged. Choosing a category shows an editable, digit-free contains pattern and the rule's total and unclassified match counts before any write. The owner either creates the household-private rule and applies it only where the complete cascade decides with that rule, or changes just this row. An existing classification is never overwritten by this flow.

Where the cascade runs. In the Python service (ADR-0013) — classify.py, called at stage 10 of the import pipeline and again by the rules screen for retroactive application and affected counts. Both callers load the same rules, private knowledge and bounded trusted priors through one shared resolver, so the classification a row gets at import is by construction the one it gets from POST /classify. The resolver performs no network calls; a public evidence URL is provenance stored at write time, never an import-time fetch target.

This replaces an earlier decision that put the cascade in SQL because two clients needed it. With a backend there is one client, and the cost that ADR recorded — matching logic being harder to test in SQL than in Python — is simply not paid.

Confidence

Source Confidence Behaviour in review

User rule 0.980 Collapsed, pre-ticked

Threshold for automatic pre-ticking: 0.80. Below that, the row surfaces.

2. Rule evaluation

A rule matches when every non-null condition matches. Absent conditions are ignored — a rule with only a description pattern matches on description alone.

Matchers                          Outcomes
─────────────────────────────     ──────────────────────────────
description  contains/prefix/     category
             exact/regex          merchant
account                           txn_type
currency                          payment_method
amount       min / max / exact    country
direction    debit/credit/any     tags
country                           transfer candidacy + counterparty account
reference    pattern

Priority ascending; lower number evaluated first. User rules default to 100, seed rules to 500, so a user rule always beats a seed rule without either needing to know about the other.

Examples

- name: "Salary from employer"
  priority: 10
  match: { description_pattern: "SALARY", account: "ENBD Current", direction: credit }
  set:   { txn_type: income, category: "Income → Salary" }

- name: "Card payment is a transfer"          # Invariant I4
  priority: 20
  match: { description_pattern: "CREDIT CARD PAYMENT", account: "ENBD Current", direction: debit }
  set:   { transfer_candidate: true, counterparty_account: "ENBD Credit Card" }

- name: "DEWA utilities"
  priority: 100
  match: { description_pattern: "DEWA", direction: debit }
  set:   { category: "Bills → Utilities", merchant: "DEWA", country: AE }

- name: "SIP debit is investment funding"
  priority: 30
  match: { description_pattern: "ACH.*MUTUAL FUND|SIP", account: "HDFC Savings", direction: debit }
  set:   { transfer_candidate: true, txn_type: investment_buy }

- name: "Small Careem rides"
  priority: 90
  match: { description_pattern: "CAREEM", amount_max: 200, direction: debit }
  set:   { category: "Transport → Taxi", merchant: "Careem" }

The last shows why the amount matchers exist: CAREEM under AED 200 is a ride; a larger amount is more likely food delivery or a subscription, and should be reviewed rather than assumed.

Regex is available but discouraged. contains handles the overwhelming majority of cases and is comprehensible six months later. Regex rules are validated at creation and rejected if they can catastrophically backtrack.

Economic meaning before categories

Classification distinguishes internal transfers, external household support, earned/other income, refunds and receivable settlements. Category names alone do not settle that distinction. Refunds and purchase-linked cashback offset spending on their posting date; an identified reimbursement settles the corresponding receivable without creating income a second time. An uncertain expected reimbursement does not automatically become a recognised asset.

Family support may retain its “To family” label, but confirmed external support reduces retained income even when excluded from consumption. Investment funding, platform transfers and reinvestment remain distinguishable. The governing definitions are finance OS F01–F03; implement them with Phase 1.3 reporting requirements and preserve explicit user overrides.

Seed rules ship as packs

The category tree above is universal. The merchants that fill it are not, so rules are split into a pack that always loads and one pack per country. Which country packs load is not a setup question — it is SELECT DISTINCT country FROM account. 4. Learning from corrections

Explicit, never silent. Recategorizing a transaction opens a prompt:

  Recategorized:  TALABAT DUBAI  →  Food & Dining → Delivery

  ☐  Create a rule: descriptions containing "TALABAT"
     → Food & Dining → Delivery

     Affects 47 past transactions and all future ones.
     [ Preview the 47 ]

  ☐  Also apply to the 47 past transactions

  [ Just this one ]   [ Create rule ]

Three properties matter here:

  1. The count is shown before committing. A rule that would recategorize 300 transactions is a different decision from one that affects 4.
  2. The affected rows are previewable. No blind bulk edits.
  3. Retroactive application is opt-in. Sometimes a rule should only apply going forward.

The system never quietly changes past classifications. Financial data that reorganizes itself overnight is data you stop trusting.

Pattern suggestion

When offering a rule, the engine proposes the pattern by finding the longest common substring across transactions the user has classified the same way, then trimming volatile tokens (reference numbers, dates, terminal IDs, city suffixes).

TALABAT DUBAI 887262819       ┐
TALABAT ABU DHABI 887299201   ├→  suggested pattern:  "TALABAT"
TALABAT DUBAI 887301442       ┘

The suggestion is always editable. A suggestion that over-generalizes is worse than none, so the preview count is the safeguard.

Rule health

Rules accumulate and go stale. A settings screen surfaces:

  • Rules never applied in 6 months → candidates for deletion.
  • Rules whose classification the user has overridden more than 3 times → the rule is wrong.
  • Overlapping rules where a lower-priority rule can never fire → shadowed, flagged.

5. Merchant normalization

The same merchant appears many ways. One merchant row, many merchant_alias rows:

Starbucks
  ├ STARBUCKS
  ├ SBUX
  └ STARBUCKS COFFEE

Emirates NBD (as a counterparty, not the account)
  ├ EMIRATES NBD
  └ ENBD

Normalizing at the merchant level rather than per-rule means "how much did I spend on coffee last year" works across statement format changes and across countries. It is also what makes merchant spend trends possible.

Aliases are created implicitly: assigning a merchant during review offers to add the cleaned description as an alias.

6. Special classifications

Some rows are not spending, and misclassifying them corrupts every downstream figure.

Pattern Correct handling Why it matters
Credit card payment Transfer (I4) Otherwise every card purchase is counted twice
Remittance to India Transfer, remittance Otherwise a year's remittances register as spending
SIP / mutual fund debit investment_buy, linked to the investment transaction Investing is not consumption
Loan EMI loan_repayment, split into principal and interest Principal is balance-sheet; only interest is a cost
ATM withdrawal Transfer to a cash account The spending happens when the cash is spent, not withdrawn
Salary credit income, category Salary Anchors savings rate
Interest credited income → Investment income Small but compounds
Bank charge reversal refund, not income Otherwise reversals inflate income
Cheque bounced and represented Both rows kept, net effect zero Deleting either breaks reconciliation
Self-transfer between own accounts Transfer, internal Extremely common; the largest source of double counting

ATM withdrawals deserve emphasis. Treating a withdrawal as an expense means cash spending is recorded on the day it was withdrawn, in whatever category the withdrawal lands. Modelling it as a transfer into a cash account, with manual entries as the cash is spent, is more accurate — at the cost of manual entry. Phase 1 default: transfer to cash, with a periodic "reconcile cash" prompt that writes a single adjusting entry rather than demanding per-coffee bookkeeping.

7. Quality targets

Milestone Target
First import, seed rules only ≥ 70% auto-classified
After one month of corrections ≥ 90%
After three months ≥ 95%
Misclassification rate (wrong, not merely unclassified) < 2%

Unclassified is a much cheaper failure than misclassified: it surfaces itself. The engine is therefore tuned to abstain rather than guess — a rule that would fire at low confidence returns nothing instead.

Measurement: Settings › Rules reports coverage, rule hit counts, override counts and the top unclassified descriptions by frequency — which is also the best list of rules worth writing next.

Definitions (GET /rules/analytics, Phase 2.3): a hit is a row whose stored classified_by is user_rule or seed_rule and whose classification_rule_id names the rule. A disagreement is a row for which the rule is the first match by priority within its own origin group — the same _first_matching evaluation classify_row itself calls, over the household's user rules or seed rules exactly as the cascade separates them — whose stored category or transaction type differs from what the rule would set, and whose stored classification_rule_id names a different rule (or none). A rule silent on a field never disputes it: disagreement is judged only on the fields the rule actually decides. The four confidence bands are none (no stored confidence), below 0.5, 0.5 through 0.8 and above 0.8 — the same threshold PRE_TICK_THRESHOLD fixes. Repeated owner corrections that share a proposed pattern, direction, category and transaction type — at least three, and only where no active rule already produces that outcome — surface as a suggested rule (GET /rules/suggestions) the owner may create and, separately, apply to past rows.

8. What Phase 5.3 would add

Recorded so the boundary stays clear, not as a commitment.

An LLM fallback would sit at step 7, after everything deterministic has abstained — typically a handful of rows per import. It would propose, never decide, and its output would land in the review queue like any other suggestion.

Prerequisites before that is worth building:

  1. The rule engine is demonstrably above 90% — otherwise the model is compensating for a fixable gap rather than adding value.
  2. The privacy decision deferred in ADR-0003 is made explicitly.
  3. Redaction is specified: what exactly leaves the machine, and what never does.
  4. Cost per import is measured, not assumed.

Until all four hold, the fallback is the review queue, and the review queue is fine.
