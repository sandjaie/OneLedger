04 — Multi-Currency and FX

Read this before the data model. Currency handling determines several column choices that are painful to change later.

The problem, stated plainly: the AED/INR rate moves every day. A transaction from two months ago will show a different converted value today than it did then. Which value is correct?

The answer: both — for different questions. Conflating them is the defect that quietly ruins multi-currency personal finance tools.

1. Two rates, two purposes

Flows translate at the transaction-date rate, frozen forever

A coffee bought on 03 Sep 2026 for AED 31 cost ₹742 at that day's rate of 23.94.

That ₹742 must never change. If historical spending is re-translated at today's rate:

  • "March spending" is a different number every day.
  • Year-on-year comparisons compare rate movement, not behaviour.
  • A budget that was met can retroactively become a budget that was missed.
  • Any chart of spending over time is partly a chart of the exchange rate.

So: compute once at import, store the result, never recompute.

Balances translate at the as-of-date rate, computed live

An HDFC balance of ₹500,000 on 30 Sep is worth AED 20,876 at 30 September's rate. Not at the blended rate of every deposit that built it, and not at each deposit's own rate.

A balance is a snapshot of value held now. Snapshots use spot.

The two are different, and the difference is real

Sum every INR-converted transaction into an AED account and you will not get the AED balance converted at today's rate. The gap is FX translation gain or loss, and it is not an error to be reconciled away — it is a genuine change in wealth.

If you hold AED and the AED strengthens against the INR, your net worth in INR rises without you earning, spending or investing anything. That belongs on the balance sheet as its own line:

+ ₹12.0 L   investment contributions
+ ₹ 8.0 L   market appreciation
+ ₹15.0 L   loan principal reduction
+ ₹ 1.4 L   FX translation gain          ← this line
− ₹ 2.0 L   asset depreciation

Most tools hide this in a rounding residual. Showing it is one of the more informative things this product can do for a two-currency life.

2. What is stored on a transaction

amount                1000.0000       ← immutable, as the bank stated it
currency              AED             ← immutable

fx_rate_date          2026-09-03      ← the date the rate is quoted for
fx_rate_is_carried    false           ← true if carried from an earlier date
fx_rate_to_base         23.9400000000 ← frozen
fx_rate_to_secondary     1.0000000000 ← frozen
amount_base          23940.0000       ← frozen, derived once
amount_secondary      1000.0000       ← frozen, derived once

Base and secondary are whatever household was configured with — INR and AED here.

Why store both converted amounts rather than converting on read?

  1. Historical figures become literally immutable, not just conventionally so. No query can accidentally re-translate history.
  2. Reporting is a plain SUM() — no per-row rate join across millions of row-reads.
  3. The currency toggle is a column swap, so neither currency is second-class.

The cost is a backfill migration if a third reporting currency is ever added. That is an acceptable one-off, and it is recorded in ADR-0002 along with the pivot-currency alternative that was considered and rejected.

Rounding: amounts are NUMERIC(20,4), rates NUMERIC(20,10). Never floating point. Round half-up at the point of storage; never round intermediates.

3. Where rates come from

A peg is a row, not a constant

A currency held at a fixed rate against another needs no feed of its own. currency.pegged_to and currency.peg_rate record the anchor and the rate, and everything derived through them is stored with source = 'derived_peg', so abandoning a peg is one identifiable set of rows.

The first deployment pegs one currency — AED to the US dollar at 3.6725 AED = 1 USD, held since 1997 — which leaves exactly one volatile rate to track:

USD/INR   ← the only rate that actually moves
AED/INR = (USD/INR) ÷ 3.6725

A deployment with no pegged currency seeds no peg row and fetches both sides. Fewer fetches is a consequence of the configuration, never an assumption in the code.

Source

Primary: ECB daily reference rates (via the Frankfurter API — no key, no rate limit, no account). The ECB quotes ~30 currencies against the euro, so any pair is one division:

quote per base = (EUR/quote) ÷ (EUR/base)

USD/INR = (EUR/INR) ÷ (EUR/USD)          both published
AED/INR = (EUR/INR) ÷ (EUR/USD × 3.6725) AED reached through its peg

The ECB does not publish AED, which is exactly why the peg derivation exists. A currency that is neither published nor pegged raises rather than guesses — see units_per_eur in phase-0-foundations.md Task 7.

Verify before implementing. Free API availability and terms change. The rate source is behind an interface (FxRateSource) with the ECB path as the default implementation, so swapping providers is a single class. Alternatives to evaluate: exchangerate.host, open.er-api.com, or a manual CSV import as the always-available fallback.

Every stored rate records its provenance

fx_rate (
  rate_date, base_currency, quote_currency, rate,
  source              -- 'ecb' | 'derived_peg' | 'manual' | 'actual_transfer'
  is_carried_forward, carried_from, fetched_at
)

source = 'derived_peg' for anything computed through the 3.6725 constant. If the peg is ever abandoned, every affected row is identifiable by that one field.

Weekends, holidays and gaps

The ECB publishes on TARGET business days only. Roughly 30% of calendar dates have no published rate, and transactions occur on all of them.

Rule: carry forward the last published rate. Never interpolate, never invent.

Fri 04 Sep   USD/INR 88.42   published
Sat 05 Sep   USD/INR 88.42   carried_forward, carried_from = 2026-09-04
Sun 06 Sep   USD/INR 88.42   carried_forward, carried_from = 2026-09-04
Mon 07 Sep   USD/INR 88.61   published

Carried rates are flagged on the transaction (fx_rate_is_carried) and shown in the UI on hover. Invariant I7: nothing derived is presented as if observed.

Forward-filling is correct here; interpolating between Friday and Monday would fabricate a Saturday rate that never existed and would make a Saturday transaction's INR value depend on what happened on Monday.

Backfill and schedule

  • Backfill on setup: 24 months of daily rates (~730 rows per pair) — one API call for the full range.
  • Daily thereafter: fetch the latest, derive any pegged pair, carry forward any gap.
  • On import: if a statement contains a date with no rate, the import path fetches that date's range before proceeding. An import never proceeds against a missing rate.

4. The reporting-base decision

household.base_currency is the base; household.secondary_currency is the toggle. Both are chosen at setup and neither is baked into the schema (ADR-0002).

How to choose. Denominate the base where the wealth will eventually be spent, not where it is currently earned — the net-worth curve is the primary long-term metric, and it should be measured in the currency the money is destined for. Put day-to-day spending in the secondary, where it reads naturally. For the first household that is INR base, AED toggle: wealth accumulates in INR terms, daily life is priced in AED.

Because both values are frozen per row (§2), which of the two is shown is a display default, not a data asymmetry: swapping it changes one config value and no data. Changing which two currencies the pair contains is a different thing — the frozen columns are already populated, so it is a backfill from fx_rate history.

Display rule: the original currency is always visible. Never show only the converted figure.

STARBUCKS DUBAI MALL
−AED 31.00          ₹742  @ 23.94 on 03 Sep 2026

Formatting follows currency.number_format, not a hardcoded locale: INR renders in the Indian numbering system (₹1,02,34,567, with lakh and crore abbreviations), AED in international grouping (AED 1,234,567.89). A currency added later declares its own grouping in that column.

5. Actual rates beat reference rates

This is where the model produces something no bank statement shows.

When AED 5,000 is remitted and ₹111,000 arrives, the rate actually achieved was 22.20. The mid-market rate that day may have been 22.55. The 0.35 gap is a real cost, and it is almost always larger than the fee that was disclosed.

For every confirmed transfer:

source_amount        AED 5,000.00
destination_amount   ₹111,000.00
implied_rate         22.2000        = destination ÷ source
market_rate          22.5500        = mid-market on transfer_date
fx_spread_pct         1.5521 %      = (market − implied) ÷ market
fx_spread_cost       AED 77.60      = source_amount × spread_pct
explicit_fee         AED 26.25      = as itemised by the provider
total_cost           AED 103.85
effective_cost_pct    2.077 %

Aggregated over a year, per provider:

2026 remittances to India

Provider        Sent (AED)   Fees     Spread    Total    Effective
─────────────────────────────────────────────────────────────────
Bank wire          80,000     420     1,690     2,110      2.64 %
Exchange house     70,000     315       910     1,225      1.75 %
Wise               30,000     198        95       293      0.98 %
─────────────────────────────────────────────────────────────────
                  180,000     933     2,695     3,628      2.02 %

Which answers a question worth real money: which channel should be used, and what is the current one costing?

The spread is computed only where both legs are known — that is, a confirmed transfer (see transfers-and-reconciliation.html). An unmatched leg produces no cost figure rather than a guessed one.

The UAE narration already carries the achieved rate

Observed in the gathered statements: an outbound remittance on the UAE current account posts a narration of the form

RMA REF: EPHCOR…       −4,271.00
BENEFICIARY NAME INR100000@.04271

The destination INR amount and the achieved rate are in the narration of the source leg. That is materially better than deriving implied_rate from two matched legs:

  • Cross-currency matching becomes near-exact rather than a ±5% FX tolerance (07 §3), so false positives all but disappear.
  • implied_rate is read rather than derived, so it is exact rather than rounded through two amounts.
  • A one-sided transfer still yields the full cost analysis. Where the Indian leg has not been imported, the spread and total cost are still computable, which is the case §5 otherwise cannot serve at all.

The parser extracts remit_amount and remit_rate into raw_row; the matcher uses them as a strong direct signal. Where the narration does not carry them, the two-leg derivation above stands unchanged as the fallback.

6. Balance and net worth translation

A balance is translated at the rate for the date being viewed:

-- Net worth on any date, in any base currency
SELECT SUM(b.balance_native * fx.rate) AS net_worth
FROM   account_balance_on(as_of_date) b
JOIN   fx_rate fx
  ON   fx.rate_date       = as_of_date
 AND   fx.base_currency   = b.currency
 AND   fx.quote_currency  = :reporting_currency;

Viewing net worth as of 30 Jun 2026 uses 30 Jun 2026's rates for every account — not today's. The historical net-worth curve is therefore reproducible: recomputing it a year from now gives the same shape it gave when first drawn.

Materialisation: month-end snapshots are stored in net_worth_snapshot with the rates used, so the trend chart doesn't recompute from the full ledger each time and so the figure shown last month is provably the figure that was shown last month.

7. Net-worth attribution: the decomposition

The "why did it change" breakdown, done in a way that reconciles exactly rather than approximately.

For any account or holding, value in the base currency is V_base = V_native × r, where r is the translation rate. Over a period from t₀ to t₁:

V_base(t₁) − V_base(t₀)
  = V_nat(t₁)·r(t₁) − V_nat(t₀)·r(t₀)

  = [ ΔV_nat · r(t₁) ]        ← native-currency change, valued at the closing rate
  + [ V_nat(t₀) · Δr ]        ← FX translation effect on the opening balance

This split is exact. There is no leftover cross-term — the ΔV_nat · Δr interaction is absorbed into the first bracket by valuing native change at the closing rate. That choice is what makes the FX line reconcile to the last decimal rather than approximately.

ΔV_nat then splits by cause, all in native currency:

Component Source
Net cash saved Σ transactions on cash accounts (income − expense)
Investment contributions Σ investment purchases net of redemptions
Market appreciation Δ holding value not explained by units bought or sold
Loan principal reduction Σ principal components of actual EMIs, plus prepayments
Asset revaluation Δ between successive manual valuation snapshots
FX translation V_nat(t₀) · Δr, from the bracket above
Unexplained The residual, displayed rather than absorbed

A non-trivial residual means something real: a missing statement, an unimported month, an unlinked transfer, a stale valuation. It is a data-quality signal, so hiding it would discard the most useful diagnostic the product has. Invariant I7.

8. Edge cases and their rulings

Case Ruling
Transaction in a currency other than the account's (AED card used in Thailand) Store amount/currency as the account posted it (AED). Keep the original THB amount and rate in original_amount / original_currency for reference. The bank's conversion is the truth; it's what actually left the account
Same-currency transfer (AED → AED) implied_rate = 1. No spread. Fee only
Rate missing for a transaction date Import blocks and fetches. Never defaults to 1.0, never uses today's rate
Statement predates the backfill window Extend the backfill; do not import against absent rates
Correcting a wrongly-dated transaction Re-fetch the rate for the corrected date and rewrite the frozen values. Logged in audit_log — this is the only circumstance in which frozen values change
Third reporting currency added later Backfill migration adds amount_<ccy> and populates from fx_rate history. One-off, planned for
Peg abandoned All source = 'derived_peg' rows identified and re-derived from a direct AED quote from the switch date forward. Historical derived rates remain correct for their dates
Investment priced in USD, held in an INR account Holding valued in USD, translated at the as-of rate. Contributes FX translation like any other foreign-currency asset
Refund of a foreign purchase months later Refund is a separate transaction at its own date's rate. The INR difference from the original is a genuine FX effect, not an error

9. Test cases

Enforced in testing-and-data-quality.html:

  1. Frozen flows. Import a transaction, advance the rate table by six months, re-run the period report. The INR figure is byte-identical.
  2. Peg derivation. AED/INR × 3.6725 = USD/INR for every date in the table, to 8 decimals.
  3. Carry-forward. A Sunday transaction uses Friday's rate and is flagged is_carried = true.
  4. Attribution reconciles. For a synthetic period with known flows and a known rate move, the components sum to the actual delta with residual exactly zero.
  5. Spread cost. A transfer with known legs produces the hand-computed spread cost.
  6. Toggle symmetry. amount_base ÷ amount_secondary = fx_rate_to_base ÷ fx_rate_to_secondary for every row, within rounding tolerance.
  7. No implicit conversion. A static check asserts that no report query multiplies amount by any rate — reports read frozen columns only.
