10 — API Contracts

One surface: the web app talks to the Python service over HTTP. Nothing else reaches the database — not the browser, not a second client (ADR-0013).

The contract is Pydantic models plus the OpenAPI schema FastAPI generates from them. The web app's TypeScript types are generated from that schema, so a change to a model changes the client's types in the same commit and every mismatched call site fails tsc immediately. There is no hand-written type on either side of the wire, and no schema-parity test to maintain — the generator is the check.

1. Type generation

# Pydantic models -> OpenAPI -> TypeScript types
cd web
npm run api:types
npm run api:types:check

The generator command runs uv run --project api --frozen python scripts/openapi.py locally, then @hey-api/openapi-ts 0.99.0 with only the @hey-api/typescript plugin. It commits the generated output under web/types/api/ and does not create an SDK, runtime client, validator, telemetry hook or anonymous OpenAPI route.

The repository pre-push gate and canonical verify skill run the drift check. A model change that is not reflected in the committed types fails before review without requiring Python in the web production image.

The service's own row types are hand-written Pydantic models, checked against the live schema by a test that introspects information_schema — a migration that changes a table without updating the model fails CI.

2. The route surface

The complete public set is GET /health, GET /auth/login and GET /auth/callback; the auth routes expose no financial data. Every other route requires a valid session cookie that resolves to an active server record for the pinned owner. Mutating cookie-authenticated requests also require an exact Origin match with WEB_ORIGIN; CORS is not the CSRF boundary. See ADR-0016.

GET /auth/callbackValidates flow context and Google's signed identity, binds the permitted seeded owner, and issues the revocable local session
POST /auth/logoutRevokes the exact current session record, then clears the session cookie. Replaying the old cookie is rejected
GET /householdReturns the authenticated owner's household id, name, owner display name and tax residency, configured reporting pair, whether that pair is locked, and currency display metadata. The browser cannot select a household id
PATCH /householdUpdates the household name, owner display name and tax residency, and the reporting pair. A locked pair is refused with the ADR-0002 backfill explanation (409); an identical or unknown pair is 422
GET /currenciesReturns every seeded currency row so Settings can offer the catalogue, never a hardcoded union
GET /accountsReturns the household's accounts, including closed ones, and Postgres-computed native totals grouped by class, country and currency. Money fields are decimal strings. Each account carries its typed identifier envelopes (bank_account, iban, card, folio or brokerage_account) with mask, activity and reveal availability only; no complete or normalized value is serialized
POST /accountsCreates an account. account_class is trigger-derived; the client never sends it. Institution picks must be shared seeds or this household's. Opening balance is a decimal string. An optional complete accountNumber is retained in the owner's local database with its normalized exact-match form and ordinary display mask. The retired mask-only compatibility input is rejected; source-masked evidence enters only through statement confirmation or legacy upgrade
PATCH /accounts/{id}Full replacement of the editable account fields. Closing sets closedOn and derives is_active; there is no delete. Changing the opening anchor clears the acknowledgment and rewrites the materialised current balance. Omitting accountNumber leaves every typed identifier untouched; deliberately supplying a complete replacement deactivates the prior identifier and writes the new owner-entered value
POST /accounts/{accountId}/identifiers/{identifierId}/revealOwner-only reveal for one household-scoped identifier. Returns revealed with its original source value and kind, or unavailable with source_mask_only when the source statement itself supplied no complete value. Successful responses carry Cache-Control: no-store and Pragma: no-cache
POST /account-identifiers/backfill/previewRead-only preview over completed imports for all household accounts or one optional accountId. It follows batch-to-document provenance, verifies the local storage path and SHA-256, and re-reads each PDF with the newest household layout carrying the imported layout's immutable name. One request-only password may be supplied and is never persisted. A previously unseen safe public issuer label may be proposed against the institution already bound by that completed import; ambiguous aliases and country conflicts still refuse. Results group complete, mask-only, missing, conflicting and unsupported evidence per account, mark identifier or alias upgrade eligibility, and expose only account/document UUIDs, fixed reason codes, counts, previewedAt and an expectedState digest over that timestamp, ordered provenance/version state and exact safe assessment. No institution name, filename, storage path, capture, amount or complete identifier is returned, and no row or document is changed
POST /account-identifiers/backfill/applyOwner-confirmed upgrade of one account from a fresh preview. It accepts the account UUID, request-only PDF password, previewedAt and expectedState; takes the household lock; and re-runs the same source, layout, resolver and digest checks. Stale state or any whole-account disagreement is refused. The apply records an eligible PDF issuer label as a household-confirmed alias for the completed import's existing institution. Complete agreed source evidence replaces the active legacy fingerprint with a plaintext local identifier and exact document/layout provenance through the normal identifier writer. A differing historical source mask may replace only its completed import's legacy mask when issuer, account type and currency agree, no other account matches the suffix, and every source for the account agrees; it remains mask-only and never gains invented digits. A current identity and alias are an idempotent unchanged result. The response contains only the account UUID and applied/unchanged status
GET /transactionsThe household ledger over the base table — transfer legs and duplicates stay visible and labelled (the one deliberate non-report reader; reports read v_transaction_reportable). Filters by account, category, type, date range, text, merchant, currency, country, amount range, tag, review state, classification provenance and source document; classifiedBy=unclassified is the “Needs a category” view. Results are sorted by a bounded field/direction contract and paged; money fields are decimal strings
POST /transactionsManual entry. Freezes amount_base/amount_secondary from the booked-date rate under the household row lock (spec B3.5); a missing rate refuses the save with the date named — never a fallback. A carried-forward rate stores its real date, flagged
PATCH /transactions/{id}Category and notes only — money is immutable (I1/I5). A category change stamps classified_by = 'user_manual' at confidence 1.000, reviewed (or unclassified at 0.000, queued, when cleared) and drops any rule id; a note-only edit that resends the unchanged category preserves the existing classification provenance. Split containers accept note edits only
GET /categoriesThe seeded taxonomy plus this household's categories, for pickers and Settings
POST /categoriesCreates a household category. A child inherits its parent's kind, and its bucket unless one is given; the tree stays two levels
PATCH /categories/{id}Bucket and activity on any category — the bucket is an editable default (ADR-0008); a seeded category keeps its name
GET /institutionsShared seeds plus this household's institutions
POST /institutionsCreates a household-scoped institution. Shared seeds stay suggestions
POST /investment-catalogue/securities/resolveResolves one visible shared or household security from an exact UUID, ISIN, or ticker/exchange pair. Name evidence is never auto-selected: one same-name candidate needs confirmation and several return a fixed ambiguity reason. Responses contain only safe catalogue fields and fixed state/reason codes; another household's UUID resolves as no exact identity.
POST /investment-catalogue/securities/{securityId}/manual-pricesAppends one owner-entered dated NUMERIC(20,6) price for a household-owned security. The input and output are decimal strings; the route creates or reuses its private owner_manual source mapping, records an accepted immutable snapshot, returns an identical retry unchanged, and refuses a different value for the same security/date without overwrite. Shared catalogue rows are readable but cannot receive household manual observations.
POST /investment-events/acquisitionsAppends one owner-entered purchase or recurring purchase through the database's atomic investment-event operation. The event date is a canonical YYYY-MM-DD JSON string, and client-supplied units, price and money are strict fixed-point strings. While holding the household lock, the server freezes reporting amounts from the stored dated FX rate; checked arithmetic overflow returns a fixed 422 and writes nothing. The client supplies an opaque UUID idempotency key and never supplies provenance or reporting values. Success creates one immutable event, one unit effect and one acquisition-origin lot, then returns the rebuilt holding units and exact lot basis. An identical retry returns the existing result; a conflicting key or any inconsistent field matrix writes nothing. Sales and every other cash lifecycle kind remain unavailable here.
POST /investment-events/{eventId}/correctionsAppends a complete owner-entered replacement for an acquisition while retaining the original event, effect and lot as immutable history. The request uses the same canonical date and exact-value boundaries, names the expected uncorrected state, and supplies a normalized nonblank reason that is screened against contextual secrets and complete private identifiers before storage. The operation locks that household event, and a later correction makes a new request stale; replaying the same UUID key and exact replacement remains idempotent. Rebuilds exclude the replaced effect and use the replacement, while another household's event is indistinguishable from a missing one. An event with confirmed cash funding cannot be corrected: V34 refuses the append atomically and preserves both event and allocation state. Later lifecycle events cannot be corrected through this Task 6 route.
POST /investment-funding/proposalsValidates an explicit purchase-funding decision without writing. Every amount is a positive fixed-point string, every named cash row must be an unallocated same-currency negative leaf, and the request must allocate each cash leaf in full without exceeding an acquisition's remaining capacity. Only the active leaf of an acquisition-correction chain is eligible; its correction-active state participates in the opaque confirmation digest. Transfer legs, split parents, investment-classified cash, mixed currencies and another household's references are refused with fixed non-enumerating errors. One event may use several cash leaves and one cash leaf may fund several events. A ready response returns the exact normalized allocation facts and digest; it never creates a link or changes reportable flows.
POST /investment-funding/confirmationsConfirms exactly one unchanged proposal under row locks through V33's atomic allocation function and V34's active-event guard. The client resends the complete allocation choice and its expectedState; changed cash classification, a new event correction, concurrent allocation or replay returns a fixed conflict and writes nothing. Success records only the server-selected funding role, preserves every cash leaf's prior type, and changes it to investment_buy. The final ordinary same-currency debit after a transfer chain is eligible; either transfer leg is not. Confirmed funding removes the duplicate spending leg without changing income or net worth.
DELETE /investment-funding/cash-transactions/{cashTransactionId}Unlinks every purchase-funding allocation for one household cash leaf through V34 and restores the exact transaction type recorded at confirmation. The database locks referenced investment events in deterministic UUID order before the cash leaf, matching confirmation and correction lock order. Another household's cash row and an unallocated or missing row are indistinguishable 404 responses. Other funded cash leaves remain linked, so unlink is exact rather than a recomputation from amount sign.
POST /parseMultipart file plus optional password, layout and account, and a stage flag that defaults to false. Detects the layout, extracts, normalizes, dedupes and reconciles. A dry run writes nothing. One identityResolution object is matched, needs_confirmation or ambiguous; it carries safe institution/account actions, candidates, masks, conflict codes and the correctable non-identity account prefill. There is no parallel account-proposal response. An unresolved result backed by exactly one account-number capture also carries a transient, opaque, household-bound proposalGroupKey; matched results and documents with conflicting captures carry null. The key is a domain-separated HMAC under the existing session secret, is never persisted, and lets the browser group confirmations without using filenames, masks alone or complete identifiers. Complete evidence tries normalized identity then the temporary legacy digest; suffix fallback is limited to one active account with the resolved institution and captured account type. Type, currency, issuer or selected-account conflicts cannot stage. A filename and the layout catalogue institution contribute nothing. The raw issuer and account captures remain transient.
POST /parse/accountOwner-protected multipart statement plus optional password and layout, and exactly one of an identity-free AccountCreate JSON form field or an existing household accountId. A new institution is an additional institution JSON form field; otherwise AccountCreate.institutionId is the explicit reuse decision. The service re-reads the statement and atomically creates or adopts the institution alias, account and statement-provenance identifier. It accepts no replacement identifier. Confirmation stages nothing and returns only the safe account representation.
POST /parse/identifier/revealOwner-protected multipart statement plus optional password and layout. It re-identifies and re-extracts the submitted PDF, returns only revealed(value, kind) or unavailable(source_mask_only), persists nothing, accepts no identifier text and sends Cache-Control: no-store. Ambiguous layout or account capture is refused.
POST /layouts/proposeOwner-protected multipart PDF plus optional password → an unsaved draft profile and raw extracted rows. An optional draft JSON field is validated as LayoutCreate and previews that edited draft against the same file instead of proposing again. Persists nothing in either mode (ADR-0012)
GET /layoutsThe household's saved layout profiles, including nullable accountType, highest version per name by default; ?allVersions=true returns every version
POST /layoutsSaves a mapped layout profile. Re-saving an existing name inserts version + 1 and never mutates an earlier version. Reserved metadata patterns each capture exactly one value. A layout declares complete identity with account_number or source-masked identity with account_number_masked, never both.
GET /import/{batch}The review screen's payload: the batch, the reconciliation verdict it was staged with, and its staged rows grouped by status, most-attention-needed first (statement-ingestion.html §10). Money fields are decimal strings and the frozen amount_base / amount_secondary travel with each row rather than being recomputed. Narration is redacted on the way out although the stored audit record is not. The period's isDerived is the flag the batch recorded at staging (V17) — true from the rows' own dates, false from the statement, null only for a batch staged before that column existed. It is never inferred: the two are indistinguishable afterwards, and guessing either way labels a provenance nobody observed (Invariant I7). A batch that never reconciled reads back as not reconciled rather than failing
PATCH /import/{batch}/rowsBulk row decisions. The vocabulary is exactly accepted and rejected; a row id outside the batch refuses the whole call rather than reporting a partial success, and a batch that is no longer awaiting_review is 409. Accepting a row staged duplicate is a confirmed-distinct override: its fingerprint is recomputed with the occurrence index advanced to the next index free of both the ledger and the batch's own other rows, because V10's unique (household_id, account_id, dedupe_hash) index means the colliding hash cannot commit unchanged. Deterministic, never a random suffix, so a later statement carrying both occurrences still recognises both. A rejected row keeps the fingerprint that recognised it. Accepting a row with no transaction type is 422, refused by V13's own check. Categorization arrives with the classifier
GET /import/{batch} — the proposalEach staged row also carries proposedCategoryId, proposedCategoryName, classifiedBy and classificationConfidence: the cascade runs at staging, after FX freezing and before the rows are written (statement-ingestion.html stages 6–7), so a batch arrives pre-classified and every row can say which rule decided it. It proposes only — nothing reaches the ledger without the review click, and the decision vocabulary stays exactly accepted and rejected. classificationConfidence is a string, as every NUMERIC on this wire is. proposedCategoryName is category.name and is deliberately not redacted: no path puts document text in that column, unlike the narration fields beside it
POST /import/{batch}/commitStaged rows become transaction rows, in one database transaction, re-verifying reconciliation. A card statement also writes its card_statement cycle in that same transaction, so the cycle and the rows land together or not at all: closing_balance is the batch's signed declared closing, and statement_balance its magnitude when owed, zero in credit (ADR-0010). A clash with a cycle already recorded for that card and period end is 409 and commits nothing. statement_date and payment_due_date are required by the table and never invented, so a statement that did not yield them commits its rows, writes no cycle, and returns cardStatementMissing naming what was absent; cardStatementId is the cycle written, or null
POST /import/{batch}/reparse-descriptionsPreview-first correction for a completed import after its layout learns a better row-assembly rule. The body names a newer version of the same layout, an optional transient password and apply (false by default). Before any write, the service verifies the content-addressed original, requires zero normalization failures and matched reconciliation, and proves every reparsed page, row number, date, amount, currency and original-currency pair identical to the immutable staged audit rows. Accepted staged rows must map one-to-one to unsplit ledger rows. Apply changes only the derived description_clean, is_reviewed and updated_at; raw narration, money, FX, dedupe, provenance and existing classification choices remain untouched. Changed rows are queued for reassessment. The response contains structural counts only, and a repeated apply writes nothing.
POST /import/{batch}/cancelAbandons a staged batch: an awaiting_review batch becomes cancelled and its staged rows are deleted. Not a reversal — a cancelled batch never committed, and a completed one cannot be cancelled at all (409, in V14's own words). What it recovers is the period: _refuse_second_staging already counts cancelled among the states that can no longer commit. The rows are deleted rather than left carrying a status because V7's reporting_pair_is_locked() counts every row in every table with amount_base beside household_id, and staged_transaction has both — rows left behind by a batch that can never commit would lock the household's reporting pair for good, which bites during onboarding. Cancelling twice, and any other state, are each 409 with the state named. It frees the file as well, without deleting it: the document row and its stored original stay, still named by the cancelled batch, and the duplicate check does not count a cancelled batch — so the same bytes can be uploaded and staged again, onto the same row
POST /card-statements/backfillWrites the card cycle for each committed card statement that has none — one committed before its layout could read the cycle's facts — by re-reading its stored original with the newest version of that layout and writing through the commit's own code. Returns written and skipped; each skipped statement carries its importBatchId and a structural reason: no layout to read it with, an original that will not open (a password-protected one is imported again) or cannot be read, or the facts its cycle needs that its original does not state. is_password_protected is not a reason on its own: it records that a password was offered at import, so the original is always tried. No fact is guessed (I7). One statement per transaction, and only statements without a cycle are read, so a second run writes nothing.
GET /rulesThe household's classification rules, in ascending priority — which is evaluation order, so the list reads as the cascade runs (classification.html §1)
POST /rulesCreates a rule. origin is always user_created and is not settable: a rule able to rewrite its own provenance could claim to be a seed rule. Refuses a rule with nothing to match on or nothing to decide, naming the half that is missing rather than reporting V19's constraint; marking a row a transfer candidate is something to decide. A regex pattern is compiled here and refused if it nests one quantifier inside another, because at match time that is a request that never returns while holding a connection. Money matchers are decimal strings. Creating a rule changes no existing row — rules never silently change past data
POST /rules/packLoads a shipped pack from db/seeds/rules/ as seed rules — the step POST /rules deliberately cannot perform, since origin is decided by what did the writing and not by what a body claims. A pack names each category by setCategorySlug, never by id, because V9 generates a different id in every database; the route resolves the slug against the household's own categories and the system seeds, preferring the household's own. One pack is one transaction: a slug nothing answers to refuses the whole load with 422 rather than leaving the rules before it behind. A household already holding seed rules refuses a second pack with 409 — nothing enforces name uniqueness, so a reload would silently double every rule in the cascade
PATCH /rules/{id}A full replacement of the editable fields, as PATCH /accounts/{id} is. origin, times_applied and last_applied_at are read-only. Editing a rule changes no existing row either; re-running the cascade is a separate, asked-for act
DELETE /rules/{id}Deletes a rule no row names. One that classified rows already in the ledger is 409 saying to deactivate it instead: those rows name it as the reason they are what they are, and V19's RESTRICT is what keeps that provenance from dangling (Invariant I6)
POST /rules/previewA candidate rule body in; the affected count, the count among them whose classified_by is unclassified, and a bounded sample of matching rows out. Writes nothing — no rule, no transaction. Counts rows that already carry an answer as well as unclassified ones, because it answers “what does this match” and not “what would change”: a rule written to cover a card payment must not read as matching nothing because that row was categorised by hand yesterday. Reads the base table, which is the deliberate non-report read GET /transactions already makes — a spending figure must exclude transfers, and this must not
GET /merchant-knowledgeLists the household's active, evidenced merchant and counterparty matchers. ?includeInactive=true includes immutable superseded and deactivated versions. It never returns source transaction narration or money
POST /merchant-knowledgeCreates a household-private counterparty, evidenced knowledge version and role-specific alias in one transaction. Merchants reuse the existing household catalogue by name or id; a provider can separately be a merchant and an intermediary. The body may scope a matcher by direction and account and set category, type or payment method. References must be visible to the household; full identifiers are refused in every persisted text field. A public sourceUrl cannot contain credentials or a private identifier and is stored as provenance but is never fetched, so this endpoint creates no SSRF or import-time egress path
PATCH /merchant-knowledge/{aliasId}Revises matcher, evidence and outcome by revoking the active evidence version and alias and appending their successors. The stable counterparty identity cannot be edited in place. Concurrent revisions lock the active version, so at most one successor is accepted
DELETE /merchant-knowledge/{aliasId}Deactivates the alias and revokes its evidence version; history is retained. The counterparty is deactivated only when it has no other active aliases. No transaction is reclassified as a side effect
POST /classifyRuns the cascade over the household's transactions whose classified_by is unclassified, and over nothing else: it can never overwrite user_manual, user_rule, merchant_alias, prior_match or seed_rule. Import and this route use the same loader for user rules, private knowledge, legacy aliases and bounded trusted priors. Priors come only from direct owner decisions or still-active user rules, stay within the posting direction and cannot propagate report-excluding types; conflicting equally strong priors and private-knowledge matches abstain. An alias-derived row is not promoted into a prior because an older transaction cannot prove its evidence is still active. ?preview=true reports what would change and writes nothing. Optional ruleId limits writes and counters to rows the complete cascade decides with that active household rule; a missing, foreign or inactive rule is 404, and a row claimed by an earlier-priority rule remains unclassified in this scoped run. It never runs as a side effect of creating or editing a rule or knowledge entry. Returns considered and changed. A run that applies a rule advances that rule's timesApplied, once per rule rather than once per row
GET /classification-review/groupsReturns the owner's unanswered classification questions grouped by stable account, direction, narration and proposed outcome. Recognised high-confidence rows whose stored classification already agrees, reviewed manual overrides, confirmed transfer legs and split containers are absent. A guarded source-description repair deliberately marks a changed manual row unreviewed, so that row re-enters the queue with its current choice preserved for comparison. Recognised-but-unapplied or changed outcomes remain actionable for guarded retrospective use; conflicting evidence, unresolved identities, low-confidence proposals and both stored and newly proposed report-excluding economic roles remain explicit. Each group carries at most 200 exact transaction ids for the guarded preview route, an opaque group key, explanation and proposed derived classification; it never returns money or raw document text. The scan is household-scoped and bounded at 5,000 candidates, reports when that bound is reached, and supports optional inclusive dateFrom/dateTo filters plus group pagination. This endpoint is read-only: remembering an answer still creates evidenced knowledge, and retrospective use still goes through preview then apply
POST /classification-runs/previewPersists an authenticated, one-hour correction preview for at most 200 explicitly named transactions. The body carries knowledgeVersionId, one bounded common reason, and items; each item carries only transactionId, partial derived changes, and an optional bounded reason. The derived allowlist is type, category, merchant, payment method, classification provenance/confidence, review flag, country, tags and exclusion flag. Originals, money, narration, source keys and timestamps are never accepted. The service reads and persists the complete V23 before/after state plus its private timestamp/source guards. Reviewed manual decisions, confirmed transfer legs, missing household rows, transfer types and no-op proposals are unresolved and do not enter the run scope; an unreviewed manual decision deliberately re-queued by the guarded description repair may enter, with the same complete-state and source guards. Returns the persisted runId, exact proposals and bounded changed/conflicted/unresolved counts and reasons; no transaction changes
POST /classification-runs/{id}/applyBody: one bounded idempotencyKey, and nothing else. Re-locks the persisted run and transactions and rechecks the household, active evidence version, expiry, complete prior derived state, updated_at, source identity, references, manual/transfer protections and correction chain. The sole permitted pre-preview history drift is a reviewed-to-unreviewed reset with every other derived field unchanged: this is the state a guarded source-description repair deliberately creates, so apply first appends that reset as its own immutable bridge event and then supersedes it. Any other drift conflicts. If any item conflicts, no transaction changes and no decision events are written. Otherwise every proposed state and its immutable decision event commit together. Repeating the same run and key returns the stored result; a key already claimed by another run is 409. It never accepts a replacement selection and never links or unlinks a transfer
POST /classification-runs/{id}/undoConditionally undoes an applied source run. Body: idempotencyKey and bounded reason; the client does not echo an expected snapshot. The service derives the guard from the source run and refuses an intervening transaction edit, changed source identity, confirmed transfer leg or later correction. Success creates a new run, reverse preview items and immutable decisions that supersede the source events, restoring the complete before-state (so category and type return together) without deleting history. The operation is atomic and idempotent
GET /transfersTransfers already decided — confirmed and rejected — filtered by status and account, newest first, paged. candidate is refused with 422: candidates are computed over committed transactions, not stored (ADR-0017). Money and rates are decimal strings
GET /transfers/candidatesScored unlinked pairs across the household's committed transactions, ranked, each carrying both legs, its score, its band and its proposedKind from transfers-and-reconciliation.html §3. Pairs below 0.50 are not listed. Bounded by dateFrom/dateTo on the debit's date, at most 366 days — the scan is the ledger joined against itself — and by default the 90 days ending at the ledger's latest row rather than today, so a ledger whose statements lag is not reported empty. A pair already rejected is not proposed again; a leg already linked is never proposed. Writes nothing — no transfer, no transaction update: scoring proposes, and only a request naming the pair links it
GET /transactions/{id}/transfer-candidatesRanked peers for one transaction, for manual linking, from the same scorer — a debit's peers are credits and a credit's are debits. Includes pairs below 0.50, because §3 makes those findable here and nowhere else. Another household's transaction is 404, never an empty list
POST /transfersLinks two named legs through confirm_transfer() — the one path that moves both legs' transfer_id and txn_type together (V20). Body: sourceTransactionId, destinationTransactionId, fromCandidate, optional notes. fromCandidate records match_method as auto with the scorer's confidence, or user_created with none; the score is recomputed here and never taken from the request. Refuses a leg another household holds (404), a pair in one account or the wrong way round (422), and a leg already confirmed elsewhere (409); a refusal writes nothing. Nothing calls this but a request naming both legs (ADR-0007). A cross-currency link stores the FX cost of multi-currency-and-fx.html §5 in NUMERIC, each figure derived from the stored one before it; a missing market rate leaves market, spread and cost blank rather than guessed, and a carried-forward one sets costIsApproximate (Invariant 7)
DELETE /transfers/{id}Releases both legs through unlink_transfer(), restoring each leg's type from its own sign. The row is kept as rejected, which is what stops the pair being proposed again. Another household's transfer, or none, is 404
GET /dashboardOne payload. ?asOf= defaults to today. It moves the rates and the card cycles, not the balances: net worth is the accounts' current balances at that date's rate, and a balance sheet on a past date is GET /networth's. Net worth is one SUM of signed balances over active accounts with include_in_net_worth, in both reporting currencies, with asset, liability and liquid figures as FILTERs on the same sum — no CASE, no subtraction (ADR-0010). Each balance is translated at the rate for the date viewed (multi-currency-and-fx.html §6): the date's own row when the table holds one, else the latest before it, filled forward as the table fills its own weekends and never interpolated; rates names each currency's rate, its real date and whether it is carried. A held currency with no rate at or before the date makes that reporting currency's figures null, listed in missing with the currency and the date — never a partial sum (I7). The route fetches no rate. Cards due: per card, the latest cycle ending on or before the date — statement balance, minimum due, due date, days remaining, whether paid in full, and utilisation at statement date as a human-readable percentage, absent when the cycle states no limit. Money is a decimal string throughout. This month and the trend: the as-of date's month through that date and the eleven months before it, oldest first, an empty month as zeros; thisMonth is the trend's last entry. Each gives income, spending and net in both reporting currencies and the savings rate in each, reading v_transaction_reportable and summing the frozen amount_base / amount_secondary — never the base table, never a rate (I3, I5). Income is the income rows; spending is every other reportable row with its sign turned, so a refund lowers it rather than counting as income; net is one SUM. The savings rate is net ÷ income as a human-readable percentage, null when income is zero or negative (finance-os.html F02).
GET /networth · GET /networth/attributionBalances on a date; the decomposition with its residual
POST /fx/backfill · GET /fx/{date}Fetch and inspect rates
GET /doctorThe data-quality report (testing-and-data-quality.html §5)
POST /recompute/{what}Balances, net worth, XIRR, holdings. Idempotent

Aggregation happens in Postgres, not in Python. The service issues the query and shapes the response; it does not pull rows into memory and reduce over them. Money arithmetic stays in NUMERIC.

3. Atomicity

Multi-step mutations are Postgres functions called by the service, not sequences of statements it orchestrates. apply_category_change updates the transaction, optionally creates a rule, optionally applies it retroactively and writes audit_log — all or nothing.

The rule is: if a failure halfway through would leave the ledger inconsistent, it belongs in one function in the database. The service's job is to decide whether to call it, not to hold the pieces together.

This is unchanged from before the backend existed, and deliberately so — it is the reason the invariants survive regardless of what language sits above them.

4. Import staging contract

The import path's only responsibility is to fill document, import_batch and staged_transaction correctly. Everything after that is the review screen's.

The staged row schema

# api/oneledger/schemas/staging.py
from datetime import date
from decimal import Decimal
from typing import Annotated, Any, Self

from pydantic import BaseModel, Field, model_validator

# Money is a Decimal all the way from the parser to the database, and a fixed-point string on
# the wire. A float here would already have lost precision before anyone could check.
Money = Annotated[Decimal, Field(max_digits=20, decimal_places=4)]
Rate = Annotated[Decimal, Field(gt=0, max_digits=20, decimal_places=10)]


class StagedTransaction(BaseModel):
    account_id: UUID
    booked_date: date
    value_date: date | None
    description_raw: str = Field(min_length=1)
    description_clean: str | None
    reference_raw: str | None

    amount: Money                        # signed, per Invariant I2
    currency: str = Field(min_length=3, max_length=3)
    original_amount: Money | None
    original_currency: str | None = Field(default=None, min_length=3, max_length=3)

    # frozen FX, computed before staging — named for the role, never for a currency
    fx_rate_date: date
    fx_rate_is_carried: bool
    fx_rate_to_base: Rate
    fx_rate_to_secondary: Rate
    amount_base: Money
    amount_secondary: Money

    dedupe_hash: str = Field(min_length=64, max_length=64)
    source_page_number: int | None
    source_row_number: int
    raw_row: dict[str, Any]

    @model_validator(mode="after")
    def translations_agree_with_the_stated_rate(self) -> Self:
        # The ledger's own precision: transaction.frozen_amounts_derive permits 0.0001 against
        # round(amount * rate, 4), and Postgres rounds half away from zero. A looser tolerance
        # here stages a row an owner can accept and the all-or-nothing commit must then reject.
        expected = (self.amount * self.fx_rate_to_base).quantize(
            Decimal("0.0001"), rounding=ROUND_HALF_UP)
        if abs(self.amount_base - expected) > Decimal("0.0001"):
            raise ValueError("amount_base is inconsistent with the stated rate")
        return self

    @model_validator(mode="after")
    def original_amount_and_currency_travel_together(self) -> Self:
        if (self.original_amount is None) != (self.original_currency is None):
            raise ValueError("original_amount and original_currency must be set together")
        return self

The model validators are the contract's teeth. A float that has lost precision, or an internally inconsistent FX translation, fails in the service where the error names the offending row — not in Postgres where it names a constraint.

Write sequence

The write sequence is: the service writes the original into the documents volume first, then writes document, import_batch and every staged row inside one database transaction. Original first, because a staged batch referencing a document that failed to write is worse than an orphaned file, which a sweep reclaims. The single transaction is what makes staging atomic — a failure leaves no partial batch to clean up.

Error contract

Every failure is a UI state. Each names what happened and what to do.

Condition What the user sees Database state
Duplicate document (sha256) "Already imported on 3 Aug 2026" with a link to that batch Unchanged
Layout not identified A layout picker listing the four, with the fingerprint scores Unchanged
Account not resolved An account picker, with "create a new account" inline Unchanged
Encrypted, no password A password prompt on that file only; other files continue Unchanged
Parse failure The row numbers that failed, with the raw text beside them Unchanged
Reconciliation mismatch The diagnostics panel, divergent row highlighted. Import blocked Unchanged — no staged rows
Missing FX rate, fetch fails "Rates unavailable for 3 dates" and a retry Unchanged
Network failure mid-write Retry; the write is idempotent on sha256 Rolled back

Nothing is written until the batch reconciles, which is why every failure row above leaves the database unchanged. That is stricter than the local importer's contract, which wrote a document row on parse failure.

6. Conventions

Money over the wire is a string.

{ "amount": "-310.0000", "currency": "AED", "amount_base": "-7421.4000" }

Never a JSON number — that would be an IEEE-754 float by the time it reached React. Parsed with decimal.js where arithmetic is unavoidable, which should be almost nowhere.

Dates are ISO-8601 date strings, not timestamps. A transaction happens on a date.

Percentages are stored and transmitted as the human-readable value — 15.2500 means 15.25%, never 0.1525. Chosen because it matches how the values are read and written everywhere else in the system, and mixing the two conventions is a reliable source of hundredfold errors.

Errors carry a code, so the UI can respond to a class of failure rather than pattern-matching on message text:

{
  "error": {
    "code": "RECONCILIATION_FAILED",
    "message": "Declared closing balance 12,450.00 but computed 12,140.00",
    "detail": { "delta": "-310.0000", "first_divergent_row": 47 }
  }
}
