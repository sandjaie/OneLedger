07 — Transfers and Reconciliation

The correctness feature that matters most in a two-country ledger.

Get this wrong and every spending figure in the product is inflated — potentially by more than actual spending, since a year of remittances can exceed a year of expenses.

1. The problem

   Emirates NBD Current                    HDFC NRO
   ───────────────────                     ────────
   03 Sep  −AED 5,000                      05 Sep  +₹111,000
           "TT REMITTANCE TO INDIA"                "INWARD REMIT ENBD"

Two rows in the ledger. One movement of money. Zero expense. Zero income.

Naive handling produces:

  • AED 5,000 of "spending" in September — the largest expense of the month.
  • ₹111,000 of "income" in September — inflating the savings rate.
  • A savings rate above 100%, or below zero, depending on which side you look at.
  • Total annual spending that bears no relation to reality.

The same applies to internal transfers, card payments, SIP debits and ATM withdrawals — which together are typically the largest category of transactions by value in a two-country life.

2. The model

A transfer is a first-class entity linking two transaction legs.

transfer
├── source_account_id          Emirates NBD Current
├── destination_account_id     HDFC NRO
├── source_transaction_id      the −AED 5,000 row
├── destination_transaction_id the +₹111,000 row
├── source_amount              5,000.00 AED
├── destination_amount         111,000.00 INR
├── transfer_date              2026-09-03
├── implied_rate               22.2000
├── market_rate                22.5500
├── fx_spread_cost_source      77.60 AED
├── explicit_fee_amount        26.25 AED
├── total_cost_source          103.85 AED
├── transfer_kind              remittance
├── provider                   'LuLu Exchange'
├── match_confidence           0.94
└── status                     confirmed

Both legs get transfer_id set and txn_type becomes transfer_out / transfer_in. The reporting view then excludes them automatically:

CREATE VIEW v_transaction_reportable AS
SELECT * FROM transaction
WHERE transfer_id IS NULL
  AND txn_type NOT IN ('transfer_in','transfer_out', ...);

The exclusion lives in the database, not in application code (Invariant I3). No future query can forget it, because the reports never read the base table.

Transfer kinds

Kind Example FX cost tracked
internal_same_currency ENBD Current → ENBD Savings No — rate is 1
remittance ENBD → HDFC NRO Yes — the headline case
card_payment ENBD Current → ENBD Credit Card No
loan_payment HDFC Savings → HDFC Home Loan No
investment_funding HDFC Savings → mutual fund purchase Only if cross-currency
cash_withdrawal ATM debit → cash account No

3. Detection

Automatic candidate generation over committed transactions, confirmed by the owner or an owner-delegated agent under ADR-0020. The agent may perform the routine review and confirmation without another owner click; ambiguous or competing peers are escalated. Scores alone never establish a transfer, and delegated actions retain their evidence.

The matching algorithm

Implemented in the Python service as transfers.py (ADR-0013) — called by the transactions screen over committed rows, including peers for manual linking (§6). The code below is the specification of the scoring and close to the implementation.

For each unmatched debit, find candidate credits within a window and score them.

def score_match(debit: Txn, credit: Txn) -> float:
    if debit.account_id == credit.account_id:      return 0.0
    if debit.amount >= 0 or credit.amount <= 0:    return 0.0

    score  = 0.0
    score += 0.35 * amount_score(debit, credit)     # FX-aware
    score += 0.25 * date_score(debit, credit)
    score += 0.20 * description_score(debit, credit)
    score += 0.15 * pair_history_score(debit.account_id, credit.account_id)
    score += 0.05 * rule_hint_score(debit, credit)
    return min(score, 1.0)

Amount (35%) — FX-aware. Same currency: exact match scores 1.0, tolerance for a deducted fee. Cross-currency: convert the source at the market rate for that date and compare.

def amount_score(debit, credit) -> float:
    src, dst = abs(debit.amount), abs(credit.amount)
    if debit.currency == credit.currency:
        diff = abs(src - dst) / src
        return 1.0 if diff < 0.001 else max(0.0, 1.0 - diff * 20)   # tolerate a fee

    expected = src * market_rate(debit.currency, credit.currency, debit.booked_date)
    diff = abs(expected - dst) / expected
    # Remittance spread is typically 0.5–3%; allow up to 5% before scoring zero
    return max(0.0, 1.0 - diff / 0.05)

The 5% tolerance is deliberate. Exchange houses take a spread; a strict match would miss every genuine remittance. Below 5% is a plausible transfer, above it is more likely a coincidence.

Where the source states what arrives. An outbound remittance's narration can carry the destination amount, its currency and the rate achieved (multi-currency-and-fx.html §5), read from the row's narration under the newest version of the layout that imported it — so a row imported before its layout learned to read them is read too. Where it does and the credit is in that currency, the amount is compared with the stated figure in one currency, with no market rate between them. A credit that arrives as stated, or short of it by at most 1% — a flat receiving charge — inside the kind's window is near-certain: its score is lifted into the high band as 0.90 + 0.10 × score, so the weighted sum still orders two such credits. The narration's own figures must reproduce the debit — amount × rate, within the same 1% — or they are not read. This is the one signal that reaches "high" before any pair history exists, and that band is pre-ticked, which is why its bound is a charge rather than the 5% an unstated remittance is allowed.

Date (25%). Same day scores 1.0, decaying over a window that varies by kind:

Kind Window Reason
Internal, same bank 0–1 days Usually instant
Domestic, cross-bank 0–3 days NEFT/IMPS settlement
Cross-border remittance 0–7 days Correspondent banking
Card payment 0–5 days Posting lag

Description (20%). Token overlap after cleaning, plus keyword signals — REMIT, TT, WIRE, TRANSFER, IMPS, NEFT, INWARD, OUTWARD. Counterparty name or partial account number appearing in the other leg's description is strong evidence.

Pair history (15%). If ENBD Current → HDFC NRO has been confirmed eleven times before, a twelfth is likely. This is why detection improves markedly after the first month.

Rule hint (5%). A classification rule with set_is_transfer_candidate and a counterparty_account gives a direct signal, which is how card payments and SIP debits become near-certain matches.

Thresholds

Score Presentation
≥ 0.90 Pre-ticked in review, grouped as "high confidence"
0.70 – 0.89 Shown, not pre-ticked, alternatives listed
0.50 – 0.69 Shown as a weak suggestion
< 0.50 Not shown; findable via manual linking

No score alone confirms a transfer. An owner-delegated agent may inspect the evidence and perform the confirmation. The current application still requires an explicit request naming both legs; an unattended policy is separate implementation work under ADR-0020.

One-sided transfers

Frequently only one leg is present — the destination account's statement hasn't been imported yet, or the account isn't tracked at all.

Handling:

  • Leg present, peer expected but absent → pending transfer, excluded from spending, listed as "awaiting the other side". Re-matched automatically on the next import.
  • Money confirmed as leaving the household (for example family support) → user marks an external transfer. Exclude it from consumption but include it in external household outflows, retained-income/savings-rate calculations and cash-availability planning. An untracked account alone does not establish that the money left the household.

A pending transfer older than 30 days is surfaced for resolution — it usually means a statement is missing, which is exactly the kind of gap that shows up later as an unexplained net-worth residual.

Household boundary and money in transit

The transfer exclusion protects consumption reports; it must not erase external support from household resource calculations. The external-outflow view reads confirmed external movements separately and combines them with consumption totals for retained income. It must not bypass I3 by inserting internal transfers into spending. Define and test the distinction in Phase 1.3 before Phase 1.4 reports it.

Show an internal transfer with different posting dates as pending/in transit until settlement. A verified position discloses the missing peer and coverage gap. Any estimated economic position that includes in-transit funds labels them separately, keeps them out of settled available cash, and removes them once settlement appears. Do not invent a bank posting or silently count both.

Failed and reversed transfers remain distinguishable from settled transfers. Re-matching proposes peers; confirmation follows the owner or delegated review policy in ADR-0020. See F01–F04 and scenarios P02/P04.

4. Credit card payments (Invariant I4)

The most common double-counting error, and worth stating separately.

15 Sep   ENBD Current      −AED 3,900   "CREDIT CARD PAYMENT"
15 Sep   ENBD Credit Card  +AED 3,900   "PAYMENT RECEIVED — THANK YOU"

This is not spending. The spending happened when the card was used, and each of those purchases is already in the ledger. Counting the payment as well double-counts every dirham.

Detection here is near-perfect because both legs are usually in the same bank, exact to the fils, and within a day. A seeded rule per card account provides the rule hint, pushing typical scores above 0.95.

Statement reconciliation makes it certain. Because card statement cycles are modelled (ADR-0009), a payment can be matched against a known statement balance rather than a fuzzy amount — and the card statement records whether it was paid in full.

Statement 25 Aug   balance due AED 3,900   due 15 Sep
Payment   15 Sep   AED 3,900               → paid in full ✓

5. Remittance cost analysis

The reporting payoff, and the reason transfers carry FX fields at all.

For each confirmed cross-currency transfer (method in multi-currency-and-fx.html §5):

implied_rate    = destination_amount ÷ source_amount     what you actually got
market_rate     = mid-market on transfer_date            what it was worth
fx_spread_pct   = (market − implied) ÷ market
fx_spread_cost  = source_amount × fx_spread_pct
total_cost      = fx_spread_cost + explicit_fee

Aggregated annually by provider:

2026 · Money moved to India

Provider          Sent (AED)    Fees    Spread   Total    Effective   Avg rate
──────────────────────────────────────────────────────────────────────────────
Bank wire (ENBD)      80,000     420     1,690    2,110      2.64 %      22.09
LuLu Exchange         70,000     315       910    1,225      1.75 %      22.31
Wise                  30,000     198        95      293      0.98 %      22.44
──────────────────────────────────────────────────────────────────────────────

Moving everything through the cheapest channel would have cost AED 1,764.
Difference: AED 1,864.

That last line is the product doing something genuinely useful. The information exists in no bank statement, and the cost is invisible precisely because it is embedded in a rate rather than itemised as a fee.

Where market_rate comes from: the mid-market rate for transfer_date from fx_rate (§3 of the FX doc). Where the date is a non-publication day, the carried-forward rate is used and the derived cost is flagged as approximate (Invariant I7).

6. Manual linking

Automatic matching will miss cases: unusual routings, split remittances, transfers spanning a statement boundary.

From the transactions screen: select a transaction → Link as transfer → the app proposes plausible peers ranked by score — the same scoring function the import pipeline uses, not a second implementation — with manual search available. On confirmation both legs update and the transfer record is written with match_method = 'user_created'.

Unlinking is supported and reverses cleanly: both legs return to their prior txn_type and category, and the transfer row is retained with status = 'rejected' so the matcher does not re-propose the same pair.

Split transfers — one AED 15,000 debit arriving as three separate INR credits — are handled by linking one source to multiple destinations. The transfer stores the total on each side, and each leg carries the transfer id.

7. Reconciliation beyond transfers

Transfer matching is one of several reconciliation checks. All of them exist to answer: is this ledger complete and correct?

Check Method On failure
Statement reconciliation opening + Σ rows = declared closing Blocks import (I8)
Account balance drift Computed balance vs latest statement balance Warns; offers an adjusting entry
Transfer completeness Pending transfers older than 30 days Lists them; usually a missing statement
Card statement coverage Gap in card statement periods Flags the missing month
Holding units Σ investment transaction units = holding units Blocks portfolio value display
Net worth attribution Components + residual = actual change Shows residual (I7)
Coverage Months with no imported statement per account Dashboard warning

The account-drift adjusting entry

When a computed balance disagrees with a bank statement's declared balance and the cause cannot be found, the resolution is an explicit adjustment transaction — never a silent edit of the opening balance.

30 Sep 2026   ENBD Current   −AED 12.50
              "Balance adjustment — reconciled to statement"
              txn_type: adjustment · category: Uncategorized · excluded from reporting

Visible, auditable, excluded from spending. If adjustments accumulate, that is itself the signal: something in the pipeline is systematically wrong.

8. Test cases

  1. A cross-currency remittance with a 2% spread is detected above 0.90 and neither leg appears in spending.
  2. A card payment is detected, and the card's statement is marked paid in full.
  3. Two similar-sized unrelated transactions on the same day are not linked.
  4. A one-sided transfer stays pending, is re-proposed when its peer imports, and links after explicit confirmation; settlement clears the in-transit presentation.
  5. Unlinking restores both legs and the spending figure changes accordingly.
  6. Split transfer: one debit, three credits, total cost computed across all legs.
  7. Annual remittance cost equals the sum of per-transfer costs, to the fils.
  8. A transaction cannot be a leg of two confirmed transfers (enforced by partial unique index).
  9. Removing the transfer link on a remittance increases reported spending by exactly the source amount — proving I3 is live rather than assumed.
