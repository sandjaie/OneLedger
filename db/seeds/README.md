# Seeds

Data a database needs that no migration writes. Applied by hand, once, against a database that
has already been migrated.

| File | What it is | How it is applied |
| --- | --- | --- |
| `institutions.sql` | The starter institution rows | `psql "$(scripts/dsn.sh)" -f db/seeds/institutions.sql` |
| `card-layout.json` | A `POST /layouts` body for the card statement layout | through the API, not `psql` — see below |
| `account-layout.json` | A `POST /layouts` body for the current-account statement layout | the same way |
| `passbook-layout.json` | A `POST /layouts` body for the passbook-style account layout | the same way |
| `ledger-layout.json` | A `POST /layouts` body for the password-protected ledger layout | the same way |
| `rules/*.json` | Packs of rule bodies, naming categories by slug | `POST /rules/pack`, once per household — see below |

## Neither profile carries an `institutionId`

Institution ids are generated by whichever database applied `institutions.sql`, so one committed
here fails its foreign key on another machine, or — worse — resolves to a different institution
that happens to hold that id.
`api/tests/test_seeded_layouts.py` validates every file in this directory through `LayoutCreate`
on every run and refuses one carrying an institution id, so a profile dropped in here needs no
test of its own.

## `card-layout.json`

A `statement_layout` row is household-scoped and is validated by `LayoutCreate`, so it is seeded
through `POST /layouts` rather than by an `INSERT`. A raw insert would bypass every rule that
model enforces — band ordering, sign-convention agreement, the quirks vocabulary, regex
compilation — and could store a profile the application refuses to save and cannot use. The
mapping UI supersedes this file entirely once it arrives; until then this is the same body that
UI would post.

`api/tests/test_seeded_layouts.py` holds every file in this directory to that: each is
validated through `LayoutCreate` on every test run, so a seeded profile cannot drift out of the
shape the endpoint accepts — and a layout added here is covered from the day it lands rather
than from the day someone writes it a test. It also refuses a profile carrying an
`institutionId`: `institutions.sql` inserts without ids, so every institution's key is whatever
`gen_random_uuid()` produced on the machine that applied it, and a key exported with a profile
either fails its foreign key elsewhere or, worse, resolves to a different institution. The
mapper UI sets it per household when it arrives.

Four of its values are not obvious, and each is measured rather than assumed.

**The balance anchors match a line of run-together figures, not a label.** The producer emits no
space characters between cells, so the statement summary extracts as one line of six figures
with no separator between them — `4,500.001,310.000.002,000.003,810.009,050.00` in the shape the
tests use. A regex anchored on the label cannot split them, which is the same reason
[statement ingestion](../../docs/design/statement-ingestion.html) calls word coordinates
mandatory for this producer. Each figure ends in exactly two decimal places, so
`\d[\d,]*\.\d{2}` segments the run deterministically; the patterns require exactly six figures on
their own line and capture the first and the fifth. The fifth is the total payment due. The sixth
is the current balance, which also carries any remaining installment principal and reconciles
against nothing.

**`continuationRule` is null.** With `no_date_and_no_amount` the last row absorbs every trailing
line of the document — 2,232 characters of page furniture in one `description_raw`. Off, the
longest description is 46 characters. The dropped lines are counted in `lines_unparsed` and
reported in the parse summary, so the loss is visible rather than silent (Invariant 7). This
card writes each transaction on one physical line; a layout whose narration genuinely wraps sets
the rule on.

**No statement period is captured.** The card's installment block prints each plan's original
purchase date, so the statement legitimately carries rows dated outside its own period — and
those instalment charges are part of the declared purchase total the anchors reconcile against.
Capturing the period would fail those rows and break the identity. `dateFormat` carries a
four-digit year, so the derived period is sound.

**Its four cycle facts read the words, not the raw run: `metadata_text:words`.** The statement date,
the payment due date, the minimum due and the credit limit sit in one summary block: a label line,
then a line of five values written with no space between cells. The credit limit comes first and is
printed as a whole number with no decimals, then the available credit, the two dates and the minimum
due, which extract as `2000010,950.0005/08/202630/08/2026190.50` in the shape the tests use. The
dates are fixed width and the minimum due ends the line, so those three could be read from the raw
run; the credit limit cannot, because nothing marks where it ends and the available credit begins.
The words can. The producer leaves 60 to 80 points between cells and each value sits under its own
label, so the quirk points this layout's metadata patterns at the words joined by single spaces.
That makes `\s+` between values right here, the one place in this directory where it is, while the
labels keep `\s*`. The balance anchors are untouched: they still read the raw run their six-figure
segmentation depends on. Measured across the 35 distinct card statements held locally: all four
facts capture and normalise on every one; the available credit never exceeds the limit, which a
wrong split would break; the due date falls 25 days after the statement date on every one; and the
minimum due never exceeds the total payment due. The limit less the available credit equals the
current balance on only some of them, because pending authorisations sit between the two, so that is
recorded rather than relied on.

Measured across the card statements held locally: every one of them reconciles `matched`, with
no row failing to normalize. Those files are git-ignored and never enter this repository, and
no figure from any of them appears in this one — the example above and the fixtures in
`api/tests/test_ingest_card_frame.py` are invented, and reproduce the arithmetic rather than
the amounts.

## `account-layout.json`

A current account, and the second producer this repository has met. Its statements print a
running balance, wrap their narration over several physical lines, and are the first here to
state their own period. Six of its values are measured rather than assumed.

**It writes no space character between cells, so every pattern uses `\s*` and never `\s+`.**
The same producer trait the card layout meets, and the same trap, reached from the other side:
here the patterns match *labels* rather than figures, and a single `\s+` between two words that
sit in different cells captures nothing at all. The statement period extracts as
`PERIOD OF01 Mar 2026to31 Mar 2026` and the column header as `DateDescriptionDebitsCreditsBalance`
— run-together in the shape the tests use. Written with `\s+`, the period capture fails on every
statement measured and the whole file is refused; the fingerprints score zero and the layout is
never identified at all.

**Its rows run newest first.** Nothing on the page says so, and both orders parse every row.
Read ascending, the running-balance walk breaks on twenty of the twenty-one statements measured;
the twenty-first is a five-day month with one transaction, which closes whichever way it is read
— so a single statement is not enough evidence to set this field, and the one that would have
been checked first is exactly the one that proves nothing.

**One `amount` band spans both money columns.** The header names two — debits and credits — but
the document draws no boundary between them, and the figures themselves state their direction: a
debit carries a leading `-`, a credit carries no sign. Across the statements measured the debit
figures' midpoints cluster at x≈315 and the credits' between x≈370 and x≈400, with nothing in
between to place a split on. `debit_credit_columns` reconciles every statement too, with the
split guessed at x=345, and was rejected for that reason: it discards each figure's own sign in
favour of a boundary the producer never draws, so a wider debit printed further left would be
read as a credit and the walk would break on a file nobody has seen yet. Under `signed` the sign
is read from the figure, and the band only has to be wide enough to hold both columns.

**The skip patterns are load-bearing, and only because the continuation rule is on.** With
`no_date_and_no_amount` and no skip patterns, 43 of the 307 rows measured absorb the page
footer's legend into their narration, and the last row of every page but the last also absorbs
the next page's repeated column header. Neither corrupts a figure, so every statement still
reconciles `matched` — which is what makes this worth writing down rather than noticing later.
Two patterns remove both. The legend's second line needs none: it sits in the date band, so the
description column is empty and the line is dropped and counted. Note that the patterns are
matched against the space-joined line, not the run-together raw text, which is why these two
alone among the profile's patterns use `\s+`.

**Unlike the card, it captures its statement period.** A current account prints no installment
block, so no row is dated outside the period the statement declares, and the captured bounds gate
the row dates instead of being derived from them. Both bounds come from one line and one capture
each, as `LayoutCreate` requires.

**An outbound remittance states what arrives, and three captures read it per row.** Its
narration carries the destination currency and amount and the rate achieved, run together in the
shape `YYY12500@.03200` ([multi-currency-and-fx](../../docs/design/multi-currency-and-fx.html)
§5). `remit_currency`, `remit_amount` and `remit_rate` are reserved metadata keys that the engine
reads from each row's joined narration rather than from the statement — the first match in the
statement at large would stamp one remittance onto every row — and they land in `raw_row`. The
transfer matcher asks the same question of each ledger row's narration under the newest version
of the layout that imported it, so a household's stored profile learns the keys only when this
file is posted again, which makes a new version — and from then on every row that profile ever
imported is read, the ones committed before it included. The
rate is written as source units per destination unit: across the statements measured, 30 of the
307 rows carry the shape, every one a debit, and on every one the stated amount times the stated
rate reproduces the debit to within 0.005%. The matcher checks that again on every read, because
a near-certain match built on a misread capture would be pre-ticked on the transactions screen. A
percentage in a narration (`@ 5%`) has no decimal rate after its `@` and is not read.

`rowStartRule` is `has_date`. No line of the statements measured carries a date without an
amount, so `has_date_and_amount` reads all of them identically; the two differ only on a line
neither has met, where `has_date` makes a row that fails to normalize and blocks the batch while
`has_date_and_amount` drops it into `lines_unparsed` and lets the rest reconcile without it.
`api/tests/test_ingest_account_frame.py` pins that difference, since nothing in the statements
themselves would catch a change to it.

Measured across the current-account statements held locally: all twenty-one reconcile `matched`,
307 rows, none failing to normalize, every period stated rather than derived. Those files are
git-ignored and never enter this repository, and no figure from any of them appears in it — the
fixtures in `api/tests/test_ingest_account_frame.py` are invented and reproduce the arithmetic
rather than the amounts.

## `passbook-layout.json`

A passbook-style account, and the third producer. It is the first here to declare **both**
balance anchors *and* a running balance, and the first whose statements end in forty lines of
prose. Four of its values are measured, and one of them cost a change to the engine.

**The cheque-reference column sits between the date and the narration, and its values print
left of their own header.** The `Chq No` header prints at x≈92 and its values at x≈86, while the
date ends at x≈81 — six points apart. A date band stretched to the narration column swallows
both into one cell, `dd-MM-yyyy` cannot read it, and every row carrying a cheque reference simply
never starts: an eleven-page statement yielded 25 rows instead of 240 before the band was split.
The column is mapped as `reference` rather than discarded, which is also what lets layer 2 of the
dedupe use it (spec §4.7).

**The closing block needed a new continuation rule, not a skip pattern.** Its statements end with
a legal notice, a legend and an end marker — forty-odd lines with no date and no amount, which is
the definition `no_date_and_no_amount` matches. Measured across the six statements, 246 such
lines were appended to 6 of 1,532 rows and took their narration past 1,400 characters, with every
statement still reconciling `matched`: nothing about the money was wrong, which is why it is
invisible without looking for it. Skipping them by pattern is not possible — there is no shared
phrase, and one pattern per paragraph would put a bank's own legal text in this repository.
Turning continuation off costs roughly a thousand rows their second narration line.

So `continuation_rule` gained a second member, **`blank_date_and_money_columns`** (M2 spec §7
item 13, owner decision of 10 September 2026). The distinction is geometric: wrapped narration
sits inside the description column and leaves the date and money columns *empty*, while a
paragraph set across the page fills them with text that merely fails to parse. On this corpus the
stricter rule rejects all 246 prose lines and drops 48 lines the looser one had appended — every
one of them page furniture (the address block, the scheme line, the period line, the repeated
column header and the `OPENING BALANCE` line), and not one of them narration. `reference` is
deliberately not among the columns it requires blank: this producer prints a reference fragment
beside the wrapped narration, and requiring every column but the description to be empty drops
276 of 1,639 continuation lines instead of 48.

**Both balance anchors are mapped even though a running balance is.** The walk proves the rows
agree with each other; the anchors prove they agree with two figures the statement states
independently. Dropping the closing anchor is not free — reconcile then takes the terminal
running balance as the closing, and a statement whose own two figures disagree has nothing left
to disagree with.

**The balance band's right edge is measured, not rounded.** A branch code prints immediately
beside the balance, and a band that reaches it joins the two into a cell that is not a number —
every row then carries no balance and the statement is refused. Its left edge is what separates
credit from balance; between the two the exact value does not matter, and
`api/tests/test_ingest_passbook_frame.py` pins the edges that do.

`rowStartRule` is `has_date`, for the reason `account-layout.json` gives.

Measured across the passbook statements held locally: five of the six reconcile `matched`, 1,532
rows, none failing to normalize, every period stated. **The sixth is refused, and correctly.** One
balance figure on it is missing its integer part in the document's own text layer — the
characters are literally spaces, so no band and no tolerance can recover them — and Invariant I8
refuses a statement it cannot verify rather than walking past the row. Those files are git-ignored
and never enter this repository, and no figure from any of them appears in it.

## `ledger-layout.json`

The fourth producer, and the only one that ships its statements **encrypted**. Four of its
values are measured, and one of them corrected a rule in the specification.

**The password comes from the owner, and from nowhere else.** `POST /parse` takes it as a form
field and `/import` asks for it per file (slice 1.2 task 2a); it lives in the request that used
it and is on the never-store list. No profile field, no environment variable and no seed carries
it — a layout says a statement *is* encrypted only by needing one, and
`document.is_password_protected` is the only record that a file did.

**It writes no space anywhere** — not between cells and not inside labels. The column header
extracts as `DateNarrationChq./Ref.No.ValueDtWithdrawalAmt.DepositAmt.ClosingBalance` and the
period as `StatementFrom:01/01/2025To:31/03/2025`, so every pattern is written against the
run-together form. This is the third producer here to do it and the most thorough about it.

**Its rows carry a two-digit year, and that forces everything else.** A profile whose
`date_format` has one must capture both period bounds, because windowing a two-digit year
against a period derived from those same dates is circular — so unlike the card layout, this one
cannot leave the period derived to escape a row dated outside it. And it has such rows: the
year-end interest and the tax deducted on it are booked on **1 January**, one day after the
period the statement declares, and valued 31 December inside it. Six such rows across four of
the six statements failed the period gate, and because they sit at the *end* of the statement,
dropping them left a consistent prefix that still reconciled `matched` — a statement short two
money-bearing rows reporting itself correct. Only `blocks_staging` stopped it.

That is recorded as M2 spec §7 item 14 and the gate is corrected there: **a row booked outside
the captured period is the statement's own when its value date falls inside**. The statement
wrote both dates, so nothing is invented and no tolerance is guessed; a row with neither date
inside still fails, and a layout mapping no value date is unaffected.

**Its page furniture needs patterns, not geometry.** Because the producer runs whole lines
together into single words, each footer line is one long word whose midpoint lands in the
narration column — the closing summary, the bank's own name, the balance footnote and the
registered-office line all read as wrapped narration however the bands are drawn. Seven
patterns remove them, none naming an institution. The stricter continuation rule is still
needed alongside: it is what rejects the header block the producer repeats at the top of every
page, whose account-detail lines run across the money columns. Without it the longest narration
on the six statements doubles, from 120 characters to 240.

**One line of furniture is left, knowingly.** The repeated header block carries the account
holder's locality on a line of its own, centred in the narration column, and it reaches the last
row of each page — 47 of 611 rows gain that one word. It is skipped by no pattern here because
the only pattern that would match it is the owner's own address, which does not belong in a
seed file, and no band separates it from real narration: both are single words centred in the
same column. It carries no figure and changes no balance.

Measured across the encrypted statements held locally: all six reconcile `matched`, 611 rows,
none failing to normalize, every period stated. Those files are git-ignored and never enter this
repository; the fixture in `api/tests/test_ingest_ledger_frame.py` is invented, including its
password, and reproduces the arithmetic rather than the amounts.

## `rules/` — the classification packs

A pack is applied the same way a layout is and for the same reason: the request model enforces
everything `classification_rule`'s columns cannot — that a rule matches something and decides
something, that a money matcher is an exact decimal, that a regex compiles and cannot backtrack
catastrophically — and an `INSERT` would bypass all of it.

It goes to **`POST /rules/pack`**, not `POST /rules`, and the file is the whole body:

```bash
curl -sS -X POST http://localhost:8000/rules/pack -H 'Content-Type: application/json' \
     --data @db/seeds/rules/banking-narration.json
```

**`POST /rules` cannot load a pack, and that is deliberate.** It stamps `origin` as
`user_created` and refuses to be told otherwise, because a rule that could name its own
provenance could claim to be a seed rule — and seed rules sit at a different step of the
cascade (`docs/operations/classification.html` §1). `origin` is decided by what did the
writing. `POST /rules/pack` is the writer that means `seed`.

**A pack names categories by `setCategorySlug`, never by id.** Category ids are generated by
whichever database applied V9, so an id committed here means nothing in another one — the same
trap `institutionId` is on a layout. The route resolves each slug against the household's own
categories and V9's system seeds, preferring the household's own where both answer.

**A pack belongs to the household that loads it, and loads once.** Unlike `category`, there is
no shared seed row: `classification_rule.household_id` is `NOT NULL`, so applying a pack creates
that household's own rules, and the owner may edit or deactivate any of them afterwards. A
household that already holds seed rules refuses a second pack with `409` — nothing enforces
name uniqueness, so a second load would silently double every rule in the cascade. One pack is
one transaction: a slug nothing answers to refuses the whole load rather than leaving the rules
before it behind.

`api/tests/test_seeded_rules.py` holds every file in this directory to that shape on every run,
and to three things only it can check: that no rule carries an id, that every slug it names is
one V9 actually creates, and that no pattern names an institution, a currency or a country.
That last one is ADR-0012 for the half `scripts/check-identifiers.py` cannot see — it guards
identifiers in source files, and a pattern inside a JSON seed is neither.

### `banking-narration.json`

Thirty-seven rules, and the line they all sit on: **a pack describes what a bank writes about
itself, never which bank wrote it.** Salary and arrears credits, interest in both directions,
tax deducted, the fee vocabulary, cash withdrawal and deposit, the transfer narrations, standing
instructions and instalments, reversals and chargebacks. No merchant appears, because a merchant
list is a list of names and this repository does not hold one; merchant rules are the owner's
own, written from Settings › Rules as they meet them.

That is the whole reason the first-import classification rate will be lower than
`classification.html` §7's ≥ 70% target, which assumed the 120-rule regional merchant packs.
Those are Phase 2. Owner decision, 10 September 2026.

**Every priority is above 100.** A user rule already beats a seed rule by being an earlier
cascade step, so the numbers cannot change the outcome — but a seed rule numbered at or below
the user default would read, to anyone scanning the list, as outranking rules it can never
outrank. The bands are deliberate: 400 income, 410 interest and dividends, 420 tax, 430 fees,
440 cash, 450 transfer candidates, 460 instalments, 470 reversals.

**Two rules match `INTEREST` in opposite directions**, and that is the point: interest credited
is investment income and interest charged is debt service. The direction matcher is what tells
them apart, and it is why a rule's amount bounds read the magnitude while its direction reads
the sign.
